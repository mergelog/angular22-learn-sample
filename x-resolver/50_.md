
何を返すセレクタか
編集中の実験情報（infoData）に対して、バリデーションエラーが1つでもあるかを調べ、なければ true（保存してよい） を返す合成セレクタです。

行ごと

```ts
export const selectExperimentFormValidity = createSelector(
  selectExperimentInfoData,    // state.experiments.info.infoData（編集中の実験データ）
  selectExperimentInfoErrors,  // state.experiments.info.errors（フィールド名 → エラー のマップ）
  (infoData, errors): boolean => {
    if (!infoData || !errors) {
      return true;             // どちらか未取得なら「妥当」扱い＝保存を止めない
    }
    const error = Object.keys(infoData)      // infoData のトップレベルキーだけを列挙
      .find(key => errors[key]);             // errors に truthy な値があるキーを1つ探す
    return !error;                           // 見つからなければ（undefined）→ true
  });
```

find なので全件は見ない。最初の1件が見つかった時点で打ち切り、「エラーあり」と判定します。

対応する state
errors の初期値は common-experiment-info.reducer.ts:58 で


errors: { model: null, execution: null }
更新経路は2つ：

setExperimentFormErrors({errors}) — 丸ごと差し替え。編集キャンセル時などに null を入れてクリア（例: experiment-info-task-model.component.ts:79）
setExperimentErrors({[field]: errors}) — 該当フィールドだけマージ（同:83）
setExperimentFormErrors({errors: null}) が飛ぶと errors が null になるので、冒頭ガードの !errors → true はそのクリア状態を「エラーなし」として通すためのものです。

使われ方
すべて Effects の保存ガードです。common-experiments-info.effects.ts:455 ほか4か所で


concatLatestFrom(() => [..., this.store.select(selectExperimentFormValidity)]),
filter(([, , , valid]) => valid),
不正な状態なら API 呼び出しに進ませない、という使い方。UI 側のボタン活性ではなく、Effect 側での最終防衛線になっています。

設計上のポイント
走査の基準が infoData 側：errors 側ではなく infoData のキーを回すので、infoData に存在しないキーのエラーは無視されます。表示・編集対象になっているデータに対応するエラーだけを見る、という意図。
メモ化：createSelector なので infoData と errors の参照が変わらない限り再計算されません。reducer が全てスプレッドで新オブジェクトを作っているため、参照比較が正しく機能します。
find + ! より some の否定のほうが意図は明快：return !Object.keys(infoData).some(key => errors[key])。find はキー文字列を返すので、理屈の上では空文字キーが falsy に潰れます（実データでは起きない）。既存コードとして問題はありませんが、読み手には some のほうが「存在チェック」と伝わります。

> createSelectorした変数をまたcreateSelectorの第一引数にする入れ子のような使い方がどういうことなのか理解できない

createSelector が返すものがセレクタ関数そのものだから、というのが答えです。入力と出力が同じ形をしているので、そのまま次の入力に差せます。

セレクタの正体
セレクタは「state 全体を受け取って、その一部（または計算結果）を返す関数」です。


type Selector<T> = (state: RootState) => T;
index.ts:27 の experiments は、まさにそのままの関数です。createSelector すら使っていません。


export const experiments = state => state.experiments ?? {} as ExperimentState;
そして createSelector(...) が返すのも、同じく (state) => 値 という関数です。だから入力にも出力にもなれる。ここが「入れ子にできる」理由です。

createSelector が組み立てているもの

createSelector(入力A, 入力B, (a, b) => 計算結果)
これは、だいたい次の関数を作っています。


function 新しいセレクタ(state) {
  const a = 入力A(state);   // 入力セレクタに state をそのまま渡す
  const b = 入力B(state);
  return 計算(a, b);        // その結果を projector に渡す
}
つまり createSelector の第1引数以降は「state をどう渡すか」ではなく「projector の引数をどこから取ってくるか」の指定です。state は全ての入力セレクタに丸ごと渡されます。

このファイルでの連鎖

state
  └ experiments(state)              → state.experiments
      └ experimentInfo(state)       → state.experiments.info
          ├ selectExperimentInfoData(state)   → ....info.infoData
          └ selectExperimentInfoErrors(state) → ....info.errors
              └ selectExperimentFormValidity(state) → boolean
store.select(selectExperimentFormValidity) を呼ぶと、この木が根まで降りていって、下から値が返ってきます。

入れ子にせず1発で書くと、こうなります。等価ですが、state.experiments.info という構造を直接知ってしまっています。


// 入れ子にしなかった場合
export const selectExperimentFormValidity = createSelector(
  (state: any) => state.experiments?.info?.infoData,
  (state: any) => state.experiments?.info?.errors,
  (infoData, errors) => { /* 同じ中身 */ }
);
分ける理由は2つ
1. state の形を知る場所を1か所に閉じ込める

state.experiments という位置を知っているのは experiments だけ、.info を知っているのは experimentInfo だけです。ストアの構造を変えても、書き換えるのは根に近い数行だけで済みます。

2. メモ化が段階ごとに効く

createSelector が作る関数は、入力セレクタの結果が前回と === で一致したら、projector を再実行せず前回の返り値をそのまま返します（キャッシュは直前の1件のみ）。

具体例。state.experiments.view.metricsLoading だけが変わったとします。


state           変わった（新しいオブジェクト）
experiments     変わった
experimentInfo  → state.experiments.info は前回と同じ参照 → 前回値を返す（再計算なし）
selectExperimentInfoData     入力(experimentInfo の結果)が同じ → 再計算なし
selectExperimentFormValidity 入力2つとも同じ → projector を呼ばず前回の boolean を返す
store.select() は結果が変わらなければ購読側に流さないので、無関係な state 変更でコンポーネントが再描画されません。これは1発で書いた版では得られません（state が変わるたび projector が走る）。

もう1つ。selectExperimentFormValidity は experimentInfo を2つの経路から呼びますが、メモ化のおかげで 2回目はキャッシュを返すだけです。

落とし穴
メモ化は「入力の参照が同じ」に依存しているので、毎回新しいオブジェクトを返すセレクタは下流のメモ化を壊します。


export const experiments = state => state.experiments ?? {} as ExperimentState;
//                                                        ^^ 毎回新しい {}
state.experiments が未定義の間は、呼ばれるたびに別の {} が返るので、下流は毎回再計算されます。index.ts:30 の


createSelector(experiments, state => (state?.view ?? experimentsViewInitialState) as ExperimentsViewState)
はフォールバックが定数（experimentsViewInitialState）なので、こちらは参照が安定していて問題ありません。フォールバック値は定数にする、が定石です。

> 可読性を考えると入れ子のやりすぎも問題ありそう

同意見です。ただ、実害が出るのは「深さ」そのものより別のところだと思います。

深さは案外コストが低い
このファイルの4段（experiments → experimentInfo → selectExperimentInfoData → selectExperimentFormValidity）のうち、上3段はどれも state を1階層掘るだけです。名前を見れば中身を読む必要がない。読む側が実際に読むのは末端の projector だけで済みます。

パススルーの段は、深くても読解コストがほぼ増えません。

実際にコストが上がるパターン
途中の段にロジックが入る — 「掘るだけ」に見える名前なのに変換や分岐をしている。全段を開かないと結果が分からなくなります。
feature をまたぐ — index.ts:68 の selectSelectedModelSettings は experiments 配下の selectOutputSettings と、models / core の selectModelId・selectSelectedProjectId を混ぜています。ファイルを跨ぐので追跡は一段重い。
名前が構造を裏切る — selectXxx が実は加工済み、など。
型が効いていない — このファイルの主因はこれです。

export const experiments = state => state.experiments ?? {} as ExperimentState;  // state が暗黙 any
export const experimentsView = createSelector(experiments, state => (state?.view ?? experimentsViewInitialState) as ExperimentsViewState);
//                                                                                                               ^^^^ キャストで型を戻している
根が any なので、各段で as を書いて型を復元しています。型推論が繋がっていれば「この段が何を返すか」はエディタが教えてくれるのに、キャストだと書いた人の主張を信じるしかない。入れ子を追う作業が手作業になるのは、深さではなくこれが原因です。

判断の線引き
私の基準は「その段に名前を付ける価値があるか」です。

2か所以上から使われる → 段にする価値あり（experimentInfo は多数の子から使われている）
名前が中身を正確に表す → 段にする価値あり
1か所からしか使われず、名前も selectFooBarData 程度の情報量しかない → インライン化したほうが読みやすい
selectExperimentFormValidity は、名前だけで「フォームが妥当か」と分かり、Effects の4か所から使われているので、段として妥当です。逆に一度きりの中間セレクタを名前だけ作って挟むのは、追跡の階段を1段増やすだけになりがちです。
