## 3. 第1回: 応答順・要求の識別・エラー

### R01 — GET と PUT の間に順序・世代管理がない

**指摘:** `exhaustMap` は GET 同士の重複を抑え、`concatMap` は PUT 同士を並べる。しかし二つの Effect は独立しており、GET と PUT は同時に進められる。`loadDashboardSuccess` は無条件に `dashboard` 全体を置換する。

根拠: [cafe-status.effects.ts](src/app/feature/cafe-status/state/cafe-status.effects.ts) L44–79、[cafe-status.reducer.ts](src/app/feature/cafe-status/state/cafe-status.reducer.ts) L41–45、L56–68。

反例:

1. T01 が「提供済」の取得済み一覧を表示している。
2. 再読み込みの GET が「提供済」を含むスナップショットを作る。
3. GET の応答待ち中に T01 を「片付け中」で保存し、PUT 成功が先に返る。Store の T01 は「片付け中」になる。
4. 古い GET の成功が後に返る。Store の T01 は「提供済」へ戻る。

擬似バックエンドは要求処理時に応答内容を作った後で応答を遅らせる。デフォルトの遅延もランダムな 500〜1,000ms なので、例えば GET が 1,000ms、100ms 後の PUT が 500ms ならこの順序になり得る。再読み込み中にもフォームの保存を止める条件はない。

根拠: [cafe-backend.interceptor.ts](src/app/core/backend/cafe-backend.interceptor.ts) L62–95、[cafe.config.ts](src/app/core/config/cafe.config.ts) L35–39、[cafe-info-header.ts](src/app/webapp-common/cafe-tables/dumb/cafe-info-header/cafe-info-header.ts) L79–88、[cafe-table-output.html](src/app/webapp-common/cafe-tables/containers/cafe-table-output/cafe-table-output.html) L2–9。

影響: 一覧と詳細は同じ値を表示し続けても、その共有値自体が保存前へ巻き戻る。「同じ Store を読む」ことは「最新の値を維持する」ことを保証しない。

確認: 実際の Reducer に取得開始・更新開始・更新成功・古い取得成功を順に適用し、`片付け中 → 提供済` の巻戻りを確認した。HTTP と UI を通した再現テストではなく、応答順の成立条件は Effects・Interceptor・テンプレートの読取りで確認した。

改善案: GET と PUT の実行順を調整する、保存より前に始めた GET の応答を失効させる、API のリビジョンで古い応答を拒否する、といった整合性の規則が必要。単に GET の演算子だけを変更しても、別の PUT Effect との関係は解決しない。

資料への対応: §3 と §9 に保証の限界を追記し、§6 にスナップショット作成・更新と遅延応答の時点の違いを追記した。

### R02 — 一件の番号が通信中・キュー待ちの全件を表せない

**指摘:** `updateTable` の dispatch ごとに `updatingTableNumber` が上書きされる。通信は `concatMap` で待たされるが、Reducer の番号更新は待たされない。詳細の `saving` は「この単一番号と表示中の番号が一致するか」だけで決まる。

根拠: [cafe-status.reducer.ts](src/app/feature/cafe-status/state/cafe-status.reducer.ts) L51–73、[cafe-status.effects.ts](src/app/feature/cafe-status/state/cafe-status.effects.ts) L62–79、[cafe-table-output.html](src/app/webapp-common/cafe-tables/containers/cafe-table-output/cafe-table-output.html) L6、[cafe-info-header.ts](src/app/webapp-common/cafe-tables/dumb/cafe-info-header/cafe-info-header.ts) L79–88。

反例:

1. T01 の保存を開始する。番号は `T01`。
2. 応答前に T02 へ移動して保存する。T02 はキュー待ちだが、番号は `T02`。
3. T01 へ戻る。T01 の保存が未完了でも `saving === false` となり、再度保存できる。
4. 要求順が `T01(A) → T02(B) → T01(C)` になり、番号は `T01`。
5. A の成功で番号が一致して `null` になる。B・C が残っていても更新中を表示できない。

影響: 保存ボタンの二重送信防止は同じフォームに留まる通常操作では効くが、対象を切り替えて戻る操作では効かない。番号の比較では、同じテーブルに対する A と C を識別できない。

確認: 実際の Reducer に上記の三件の要求と最初の成功を適用し、後続二件が残る順序でも `updatingTableNumber === null` になることを確認した。画面操作による再現は行っておらず、ボタンが許可される条件はテンプレートと `save()` で確認した。

改善案: 要求 ID を持たせ、テーブルごとの未完了要求数や要求の状態を管理する。完了時は該当する要求だけを取り除く。テーブル番号一件や boolean 一件では、複数件のキューを正確に表せない。

資料への対応: §3 の State 表を「最後に dispatch された要求の番号」と明確化し、§3 と §9 にキュー・二重送信の制約を追記した。

### R03 — 古い失敗が後の成功で消えない

**指摘:** `updateError` は要求の dispatch 時には消されるが、更新成功時には消されない。先に複数件が dispatch され、その後に先行要求が失敗すると、後続要求の dispatch による消去は既に終わっている。

根拠: [cafe-status.reducer.ts](src/app/feature/cafe-status/state/cafe-status.reducer.ts) L51–74、[base-cafe-table-output.ts](src/app/webapp-common/cafe-tables/containers/cafe-table-output/base-cafe-table-output.ts) L33–35。

反例:

```text
要求: T01(A) → T02(B) → T01(C) を先に dispatch
結果: A が失敗 → B が成功 → C が成功
最終状態: T01 は C の成功値、updateError は A の失敗
```

影響: T01 の表示値が更新済みでも、T01 の詳細に以前のエラーが出続ける。エラーを表示対象の番号で絞る処理は、別テーブルへの誤表示は防ぐが、同じテーブルの古い要求との混同は防がない。

確認: 実際の Reducer に上記の要求・結果を適用し、最後の成功後にも A の `updateError` が残ることを確認した。

改善案: エラーも要求 ID や世代と関連付け、同じ対象の後続成功で旧エラーを無効化する。すべての成功で無条件に消すと、別テーブルの失敗まで消すため、対象と要求の対応を保つ必要がある。

資料への対応: §3 と §9 に、単一の番号付きエラーが要求の世代まで識別しているわけではないことを追記した。

## 4. 第2回: 取得時点・フォーム・バックエンドの整合性

第1回の追記後、成功した場合のデータまで整合するか、NgRx の外にある状態との境界に見落としがないかを再確認した。

### R04 — 部分更新した dashboard は同一時点のスナップショットではない

**指摘:** 更新成功時に変わるのは `tables` の対象行だけ。`generatedAt`、`seats`、`staff`、他の行は変わらない。擬似バックエンドの PUT は `advance(now)` で全テーブルを進め、条件によって当日の来客数も増やすので、応答行以外にも変化が起き得る。

根拠: [cafe-status.reducer.ts](src/app/feature/cafe-status/state/cafe-status.reducer.ts) L56–65、[cafe-simulation.store.ts](src/app/core/backend/cafe-simulation.store.ts) L106–111、L122–142、L179–184。

例: 前回 GET のあとで空きテーブルに来客を登録すると、その行は更新されるが、`seats.usedToday` は前回 GET の集計を保持する。ヘッダの取得時刻も前回のままである。

影響: 画面全体を「一つの取得時点のスナップショット」と説明すると不正確になる。対象行だけを更新すること自体は実装上の選択であり、全体を同一時点に揃える必要があるかは仕様判断になる。

確認: 実際の Reducer を動かし、部分更新後も `generatedAt` が変わらず、`seats` と他の行の参照が維持されることを確認した。

改善案: 全体の整合性が必要なら PUT 後に全体を再取得する、更新応答に集計を含めるなどの方式を選ぶ。部分更新を保つなら、全体取得時刻と行更新時刻の区別を明示する。再取得を追加する場合も R01 の応答順を合わせて扱う。

資料への対応: 既にあった §9 の制約に加えて、§3 の更新規則にも部分更新であることを明記した。

### R05 — 入力保護が保存成功後の補正値の反映も止める

**指摘:** Header の Angular `effect()` はテーブル番号を監視しており、同じ番号の値が変わってもフォームをリセットしない。これは入力途中の値を守るが、成功応答も同様に扱う。`save()` は通知のみで、成功通知を受けて編集を終了する入力・処理はない。

根拠: [cafe-info-header.ts](src/app/webapp-common/cafe-tables/dumb/cafe-info-header/cafe-info-header.ts) L30–35、L57–88、[cafe-simulation.store.ts](src/app/core/backend/cafe-simulation.store.ts) L387–403。

例: 定員 2 人のテーブルへフォームから 3 人を送ると、バックエンドは 2 人に補正する。一覧の確定値は 2 人になるが、入力欄は 3 人のまま残り、再保存時もその入力を送る。

影響: 「成功応答を正本にする」という原則が適用されるのは共有する表示値であり、フォーム値まで一致させる実装ではない。入力欄を成功後も保持することが期待どおりかは、コードだけから決められない。

確認: 同じ番号の入力更新でフォームを保持する既存のテストと、成功・失敗を区別するフォーム同期がない実装を確認した。補正付き保存成功から再保存までの UI 再現は行っていない。

改善案: 保存成功時に編集を終了するか、補正値を反映するかを決める。同期する場合は、保存後に追加編集した入力を失わないよう、対象要求と編集時点を確認する必要がある。

資料への対応: §5 に API の補正とフォーム保持の具体例を追記した。入力保護を無条件に良い挙動として評価せず、保存後の扱いと分けて説明した。

### R06 — PUT の手動更新で来客の状態が初期化されない

**指摘:** `updateTable()` は `table.status`・人数・金額などを個別に書き換える。一方、空きへの DELETE は `enterState()` を呼び、来客 ID・着席時刻・注文関連の状態も消す。自律遷移の退席処理にも来客 ID の消去がある。PUT で空きや片付け中に変える経路には同じ消去がない。

根拠: [cafe-simulation.store.ts](src/app/core/backend/cafe-simulation.store.ts) L115–156、L222–249、L387–392。

反例: 来客 ID がある「提供済」の T01 を PUT で「空き」に変えると、返る値は `status = '空き'`、`people = 0` だが、元の `guestIds` が残る。同じテーブルを DELETE で空きに戻した場合は `guestIds = []` になる。

影響: フロントエンドが API 応答をそのまま確定値として採用しても、その応答の項目間の整合性まで保証されるわけではない。同じ業務上の遷移を複数の可変更新経路が扱うために生じている。

確認: 実際の `CafeSimulationStore` を DI コンテキストで生成し、乱数を固定して来客のいる「提供済」から PUT と DELETE を実行した。

```text
更新前:     people = 1, guestIds = [G0001]
PUT 空き:   people = 0, guestIds = [G0001]
DELETE:     people = 0, guestIds = []
```

改善案: 自律遷移・手動更新・空きへの初期化で必要な整合性処理を共通化する。任意の状態へ移す手動更新も、来客・着席時刻・進行中の注文をどう扱うか一つの規則に従わせる。

資料への対応: §6 と §9 に更新経路による差を追記した。「バックエンドが正本」という所有責任の説明と、正本の内容が常に整合するという保証を区別した。

## 5. 検証結果と資料の再確認

関連する既存テストを次のコマンドで実行した。

```bash
yarn test --watch=false \
  --include='src/app/feature/cafe-status/state/*.spec.ts' \
  --include='src/app/webapp-common/cafe-tables/**/*.spec.ts' \
  --include='src/app/feature/view-json/*.spec.ts'
```

結果: **9 ファイル・85 テストが成功。** 通常の取得・保存、API 応答の採用、失敗時の入力保持、URL 連動、二件の更新の直列処理などを確認できた。

R01〜R04 は TypeScript の実装を一時的に JavaScript へ変換して実際の Actions / Reducer を呼び出し、R06 は実際のサービスを生成して確認した。検証コードを恒久的なテストとして追加してはいない。既存テストの成功は、これらの特殊な応答順や操作の組合せが正しく扱われることを意味しない。

資料の再確認では次も照合した。

- `@ngrx/signals` / `signalStore()` の利用はなく、`CafeSimulationStore` は通常の DI サービスである。
- URL の選択、NgRx の取得済み値、FormGroup の入力途中の値を別の所有責任として説明している。
- 図の応答経路を HTTP/API 経由で表し、分割変更は API を呼ばないことを明記した。
- route provider の登録から、離脱時の確実な破棄・初期化やブラウザ永続化を推定していない。
- State に古い値が残ることと、エラー時に一覧 Grid が表示されることを混同していない。
- SignalStore 未使用、JSON 画面のローカル状態、DELETE / POST の画面側経路の未実装を、将来の設計方針として断定していない。

最終版の資料には R01〜R06 の指摘と制約を反映した。実装側の問題や仕様判断はこのレビューで解決したものではなく、上記の根拠・再現条件・改善案とともに残している。
