
# プロジェクト理解資料 作成Plan

## 目的

新規参画者が、既存コード・設定・ドキュメント・テスト・変更履歴等を根拠として、プロジェクトを段階的かつ正確に理解できる資料を作成する。

最初から詳細を網羅しない。

以下の順序で理解を深める。

1. 全体像を知る
2. 何をするシステムかを知る
3. どこに何があるかを知る
4. 実際にどのように動くかを知る
5. 代表的な処理をコード上で追えるようにする
6. 横断的な設計を理解する
7. なぜ現在の構造になっているかを、確認できる範囲で理解する
8. 実際の開発作法を理解する

資料を作ること自体を目的にしない。

新規参画者の理解に寄与しない詳細資料は作成しない。

作成場所:

`x-start-docs`

ファイル名:

`{2桁連番}_適切なファイル名.{拡張子}`

連番は実際の作成順とする。

## 基本規約

* 指定がない場合は Markdown で作成する。
* 内容に応じて HTML、Mermaid、シーケンス図、CSV 等を使用してよい。
* 初学者が誤った理解をしないことを最優先する。
* 確認できていない内容を事実として記載しない。
* 判断できない内容は「不明」とする。
* 合理的に推測できても確定できない内容は「推測」であることを明記する。
* 一般的な設計やベストプラクティスを、このプロジェクト固有の仕様として記載しない。
* ディレクトリ名、クラス名、関数名だけから責務を断定しない。
* ライブラリや機能が存在することと、実際に使用されていることを区別する。
* 現在使われている実装、過去の実装、サンプル、試験的コード、未使用コードを可能な限り区別する。
* 業務仕様と、コードから観測できる現在の挙動を混同しない。
* 設計理由をコードの形から推測して事実として記載しない。

## 調査基準

各資料は、可能であれば調査時点のブランチまたはコミットを基準とする。

各資料の「まとめ」に以下を記載する。

`調査基準: branch / commit`

取得できない場合は「不明」とする。

これにより、後からコードが変更された場合に「どの時点の構成を説明している資料か」が判断できるようにする。

## 調査の基本順序

資料作成時は、いきなり大量のコードを読み始めない。

原則として以下の順で確認する。

1. 関連する既存ドキュメント
2. 設定・構成ファイル
3. エントリーポイントおよび主要コード
4. 利用箇所・呼び出し関係
5. テストコード
6. 必要に応じて変更履歴
7. 必要な場合のみ一般的な外部資料

現在の実装を説明する場合は、現行コード・設定・実際の利用箇所を重視する。

「なぜこの設計になっているか」を説明する場合は、設計資料、Decision Record、Issue、変更履歴等の明示的な根拠を重視する。

既存ドキュメントだけで断定せず、現在のコードと矛盾していないか確認する。

外部資料は一般仕様を理解するための補助として使用し、プロジェクト固有仕様の根拠にはしない。

## 事実・推測・不明

以下を明確に区別する。

### 事実

コード、設定、既存資料、テスト、変更履歴等から直接確認できる内容。

### 推測

複数の根拠から合理的に考えられるが、確定できない内容。

必ず推測であることを明記する。

### 不明

現在参照できる情報だけでは判断できない内容。

無理に補完しない。

「おそらく一般的にはこうである」という理由だけで推測へ昇格させない。

## 既存資料との重複禁止

既存資料に十分な説明が存在する場合、同じ内容を再作成しない。

その場合は、

* 何が書かれているか
* どこを読めばよいか
* 現在のコードと整合しているか

を簡潔に示し、既存資料を参照する。

この資料群は既存資料を置き換えるものではない。

新規参画者が既存情報へ到達するための入口としても機能させる。

## 資料種別

1つの資料の中で目的の異なる文章を混在させない。

必要に応じて以下の種別を使い分ける。

### 理解資料

背景、構造、理由、関係性を理解するための資料。

### 手順資料

実行、ビルド、テスト等、具体的な作業を行うための資料。

### 参照資料

一覧、対応表、用語、配置場所等を調べるための資料。

各資料の冒頭の「まとめ」に資料種別を記載する。

## 各資料の冒頭

各資料は、H1タイトルの直後に必ず表形式の「まとめ」を置く。

「まとめ」より先に本文を書かない。

基本形式:

| 項目           | 内容                 |
| ------------ | ------------------ |
| 資料種別         | 理解資料 / 手順資料 / 参照資料 |
| この資料で分かること   | この資料の目的            |
| 今理解すべきこと     | この段階で覚える内容         |
| 今は理解しなくてよいこと | 後続資料へ回す内容          |
| 主な根拠         | 主に確認した情報           |
| 調査基準         | branch / commit    |

必要な場合のみ項目を追加してよい。

## 根拠

重要な説明には可能な限り根拠を持たせる。

根拠として利用できるものの例:

* ソースコード
* 設定ファイル
* API定義
* スキーマ
* テスト
* 既存ドキュメント
* Decision Record
* Issue
* 変更履歴

資料末尾には必要に応じて、

`## 主な根拠`

を設ける。

ファイルパスだけで分かりにくい場合は、対象のクラス、関数、設定キー等も示す。

行番号はコード変更で陳腐化しやすいため、必要な場合を除いて固定的な行番号への依存は避ける。

## 専門用語

ドメイン固有または技術固有の専門用語を使用し、説明不足になる可能性がある場合は、

`### ○○とは`

という短い説明を設ける。

ただし、その時点で理解する必要のある粒度に留める。

用語説明のために本題が見えなくならないようにする。

後続資料で詳しく扱う場合は、その旨を記載する。

## 情報量

1つの資料へ情報を詰め込みすぎない。

その資料を読んだ直後に覚えておくべき内容を優先する。

詳細を省略する場合は、省略していることを明記する。

同じ説明を複数資料へコピーしない。

既存資料で十分な内容は参照する。

理解確認テスト・問題は作成しない。

## 1ファイルの責務

原則として1ファイル1テーマとする。

別テーマの詳細が必要になった場合、その場ですべて説明せず後続資料へ分離する。

ただし、数行で説明できる内容を無理に独立ファイル化しない。

「ファイル数を増やすこと」と「理解しやすくすること」を混同しない。

## インタラクティブHTML

俯瞰図等をインタラクティブHTMLで作成する場合も、操作しなければ意味が分からない資料にしない。

初期表示だけで主要構造を理解できること。

クリック・ホバー等は詳細確認の補助として使用する。

可能な限り単体で閲覧できる構成を優先し、不必要な外部依存を増やさない。

## 作成単位

チェックされていない資料のうち、上から1つだけを対象とする。

1資料について、

調査
→構成決定
→作成
→敵対的レビュー
→即時修正
→完成

まで行う。

完成するまで次の資料へ進まない。

資料作成後、このPlanの対象項目を `[x]` に変更する。

資料1ファイルの作成に伴う、このPlanのチェック更新は「次の資料作成」には含めない。

後続調査によって過去資料の誤りが判明した場合は、過去資料を即時修正する。

## 作成不要の判断

チェック項目であっても、対象となる仕組みが存在しない場合や、既存資料で十分な場合は新規資料を作成しない。

その場合は、

`[x] N/A - 理由`

として完了扱いにしてよい。

「チェック項目が存在するから」という理由だけで資料を作成してはならない。

# 敵対的レビュー

各資料完成前に必ず実施する。

「この資料には誤りがある」と仮定し、反証する視点で確認する。

最低限、以下を確認する。

* 存在しない仕組みを想像で追加していないか
* 一般論をプロジェクト固有仕様として記載していないか
* 名前だけから責務を推測していないか
* 一部のコードだけを見て全体構造と判断していないか
* 古いコードや未使用コードを現在の実装と誤認していないか
* 依存関係に存在するだけの機能を「使用中」と判断していないか
* 「検索で見つからなかった」だけで「存在しない」と断定していないか
* 業務仕様をコード上の現在挙動だけから断定していないか
* 設計理由を後付けで創作していないか
* 既存資料が古い可能性を確認したか
* 重要な例外経路を無視していないか
* 初学者が別の意味に受け取る表現がないか
* 現時点では不要な詳細を書きすぎていないか
* 同じ説明を既存資料や他資料と重複させていないか
* 資料を独立させるほどの内容が本当にあるか
* 過去資料との矛盾がないか
* 同じ用語を資料間で異なる意味に使用していないか
* 調査基準となるコードの時点が分かるか

問題が見つかった場合は、その場で資料を修正する。

敵対的レビューそのものを別資料として作成する必要はない。

修正後の資料を完成版とする。

# 作成する資料一覧

## Phase 1: 入口

* [ ] アーキテクチャ登場要素一覧

  システムを構成する主要な要素を役割単位で整理する。

  この段階では内部実装に入り込まない。

  主に、

  * 誰が利用するか
  * どのシステム・アプリケーションが存在するか
  * 主要なデータ保持先は何か
  * 外部との接点は何か
  * それぞれ何を担当するか

  を整理する。

  「何が登場するプロジェクトなのか」を把握することを目的とする。

* [ ] 俯瞰図 レベル1

  インタラクティブHTMLで作成する。

  システム境界、利用者、主要な外部要素、主要な関係を中心にする。

  技術詳細や内部クラス構造には入らない。

  初見の人が一画面で大雑把な全体像を把握できることを優先する。

* [ ] このプロジェクトは何をするためのものか

  技術構成ではなく、利用目的・業務の観点から説明する。

  主に、

  * 誰が利用するか
  * 何を扱うか
  * 何を確認するか
  * 何を操作するか
  * 何が結果として得られるか

  を整理する。

  コードだけでは業務上の意図を判断できない場合は「不明」とする。

## Phase 2: 基礎情報

* [ ] 既存ドキュメント一覧と読む優先度

  README、docs、設計資料、開発手順、API仕様、Decision Record等を探索する。

  各資料について、

  * 何が書かれているか
  * 新規参画者がいつ読むべきか
  * 他資料との関係
  * 現在のコードと整合している可能性

  を整理する。

  更新日時だけで最新と判断しない。

* [ ] フォルダ構成

  説明付きtree構造を作成する。

  全ファイルを列挙しない。

  主要ディレクトリについて、

  * 何を置く場所か
  * 主な責務
  * 初期理解で読む必要があるか

  を整理する。

* [ ] ローカル開発・基本動作確認

  既存資料および設定から、通常の開発に必要な基本操作を整理する。

  確認できる場合は、

  * 依存関係の準備
  * Build
  * Test
  * Start
  * Debug

  の基本経路を確認する。

  既存手順書が十分な場合は、新たに詳細手順を複製せず参照する。

* [ ] 実行環境一覧

  開発、テスト、本番等、確認できる環境を整理する。

  主要要素について、

  * どこで動くか
  * 何と接続するか
  * 環境によって何が変わるか

  を整理する。

  確認できない環境については推測しない。

## Phase 3: ドメイン理解

* [ ] ドメインカテゴリ一覧

  プロジェクトで扱う主要な業務領域・概念を整理する。

  この段階では詳細仕様に入りすぎない。

  「どのような種類の情報や業務を扱うシステムか」を理解することを目的とする。

* [ ] カテゴリ別ドメイン仕様

  前資料で整理したカテゴリについて必要なものから詳細化する。

  カテゴリごとに内容量が多い場合は別ファイルとする。

  コード上の挙動と業務上の正式仕様を区別する。

  正式仕様を確認できない場合はその旨を記載する。

* [ ] 主要用語・概念

  この段階までに頻出し、今後の資料理解に必要な用語を整理する。

  すべての用語を収集するのではなく、理解を妨げるものに限定する。

  最終的な用語集は後で再整理する。

## Phase 4: 設計上の前提

* [ ] 設計上の主要な制約・品質目標

  確認可能な範囲で、

  * 技術上の制約
  * 組織・運用上の制約
  * 性能
  * 可用性
  * セキュリティ
  * 保守性
  * 拡張性

  等のうち、アーキテクチャに実際に影響しているものを整理する。

  一般的に重要だからという理由で項目を埋めない。

  根拠がないものは「不明」とする。

* [ ] 俯瞰図 レベル2

  インタラクティブHTMLで作成する。

  レベル1の主要要素について一段階だけ詳細化する。

  主に、

  * 内部の主要な責務
  * 主要な依存関係
  * 主要な通信
  * データ保持位置

  を示す。

  クラス単位まで分解しない。

  詳細化しても理解に寄与しない要素は展開しない。

## Phase 5: コード解析 初級

* [ ] アプリケーション起動経路

  起点となるコードから主要な初期化までを追う。

  どこからアプリケーションが開始され、主要機能がどのように組み立てられるかを理解する。

  業務処理の詳細には入らない。

* [ ] 画面・機能とコード配置の対応

  主要な画面または機能について、

  「利用者から見える機能」

  と

  「コード上の配置」

  を対応付ける。

  新規参画者が、修正対象を探し始められる状態を目標とする。

* [ ] 主要データ・モデル一覧

  プロジェクト理解に重要なデータだけを整理する。

  すべての型、項目、テーブル等を列挙しない。

  主要データ同士の関係が重要な場合は簡単な図を使用する。

## Phase 6: 代表ユースケース解析

* [ ] 代表ユースケース 1

  代表的なユーザー操作または処理を1つ選び、開始から完了まで実コードを追跡する。

  例:

  画面操作
  →入力受付
  →内部処理
  →外部通信またはデータ取得
  →結果受信
  →状態・データ更新
  →画面または呼び出し元への反映

  実際の構造が異なる場合は実装に従う。

  一般的なアーキテクチャパターンへ無理に当てはめない。

* [ ] 代表ユースケース 2

  1本目とは異なる処理経路を理解する必要がある場合のみ作成する。

  1本目とほぼ同じ構造の場合は作成しない。

## Phase 7: コード解析 中級

* [ ] 状態管理で使用している機能

  状態管理に関連する仕組みについて、実際に使用している機能を調査する。

  インストール・定義されているだけのものを「使用中」と判断しない。

  「使用していない」と記載する場合は、全体検索等により十分な根拠を確認する。

  判断できない場合は「未使用」ではなく「確認できず」とする。

* [ ] 状態管理の分割方式

  状態がどの単位で管理されているかを整理する。

  例:

  * アプリケーション全体
  * 機能単位
  * 画面単位
  * 局所的な状態

  実際のコード構造から判断する。

* [ ] 状態管理の基本経路

  代表的な状態変更について、

  変更の起点
  →処理
  →状態更新
  →状態参照
  →利用箇所への反映

  を追跡する。

* [ ] 層ごとの責務

  このプロジェクトを説明する場合、どのような「層」で整理することが適切かを調査する。

  一般的なレイヤー名称を先に決めてコードを当てはめない。

  実際の、

  * 責務
  * 依存方向
  * 呼び出し関係
  * データ受け渡し

  から分類する。

* [ ] 外部通信のアーキテクチャ

  外部通信について、

  * どこから開始されるか
  * どこに通信処理が置かれているか
  * データ変換がどこで行われるか
  * 結果がどのように利用側へ戻るか

  を整理する。

* [ ] エラー処理のアーキテクチャ

  エラー発生から最終的な処理までの経路を調査する。

  存在するものについて、

  * 通信エラー
  * 入力エラー
  * 業務上のエラー
  * 共通処理
  * 個別処理
  * ログ
  * 利用者への通知
  * リトライ
  * 復旧

  等を確認する。

  存在しない仕組みを一般論で補完しない。

* [ ] 認証・権限制御

  対象となる仕組みが存在する場合のみ作成する。

  主に、

  * 認証状態をどこで判断するか
  * 権限をどこで判断するか
  * 表示制御と処理制御をどこで行うか

  を理解する。

* [ ] その他の横断的な仕組み

  プロジェクト全体で繰り返し利用される重要な仕組みが存在する場合のみ整理する。

  例として、

  * ログ
  * Validation
  * Cache
  * Configuration
  * Feature Toggle
  * Internationalization
  * Observability

  等が考えられるが、存在確認前から項目を埋めない。

## Phase 8: テスト・ビルド・デリバリー

* [ ] テスト構成

  実際に存在するテストを種類別に整理する。

  それぞれ、

  * 何を確認しているか
  * どこに配置されているか
  * どのように実行するか
  * どの程度利用されているか

  を確認する。

* [ ] ビルド・検証・デリバリー経路

  コード変更から成果物が作られるまでの主要な経路を整理する。

  確認できる範囲で、

  変更
  →自動検証
  →Build
  →Artifact
  →Deploy

  等の流れを整理する。

  実際の構成に存在しない工程を補完しない。

## Phase 9: 設計意図と開発履歴

* [ ] 重要な設計判断

  現在の構造を理解する上で重要な設計判断を整理する。

  設計資料、Decision Record、Issue、変更履歴等に根拠が存在するものだけを対象とする。

  可能な場合は、

  * 判断時の状況
  * 採用した方針
  * 理由
  * 検討された代替案
  * 結果として生じた制約

  を整理する。

  設計理由を現在のコードから逆算して創作しない。

* [ ] 明文化されている開発ルール

  開発者向け資料、設定、Contribution Guide等から、

  * コーディング規約
  * Branch
  * Commit
  * Review
  * Test
  * Build
  * Release

  等について明示されているルールを整理する。

* [ ] 開発履歴から読み取れる実際の作業作法

  変更履歴から実際の変更傾向を分析する。

  例:

  * 変更単位
  * 一緒に修正されるファイル
  * 機能追加時の典型的な変更範囲
  * テスト追加の傾向
  * リファクタリングの進め方

  以下を必ず区別する。

  **確認できた事実**

  履歴から直接確認できるもの。

  **根拠付き推測**

  複数の履歴から傾向として考えられるもの。

  **不明**

  十分な根拠がないもの。

  少数のCommitだけから「このプロジェクトでは必ずこうする」と一般化しない。

  個人の能力、意図、性格等について推測しない。

* [ ] 既知のリスク・技術的負債・注意点

  明確な根拠が存在するものだけを整理する。

  例:

  * Deprecatedな構造
  * 移行途中の実装
  * 重複した方式
  * 既知の制約
  * 未完了の移行
  * 明示された技術的負債

  コードが複雑に見えるという理由だけで「技術的負債」と断定しない。

## Phase 10: 最終整理

* [ ] 用語集

  これまでの資料に登場した重要なドメイン用語・技術用語を整理する。

  辞書を作ることが目的ではない。

  プロジェクト内で会話・コード・資料を理解するために必要な用語へ限定する。

* [ ] 不明事項一覧

  調査しても判断できなかった事項を整理する。

  以下を区別する。

  * コードをさらに調べれば分かる可能性がある
  * 既存資料が必要
  * 実行環境の確認が必要
  * 関係者への確認が必要

  不明事項を推測で埋めない。

* [ ] プロジェクト理解マップ

  これまで作成した資料への入口となる最終インデックスを作成する。

  例:

  * まず読む
  * ドメインを理解する
  * コードを探す
  * 処理を追う
  * アーキテクチャを理解する
  * 開発作業をする
  * 設計意図を調べる

  新しい詳細説明を追加する資料ではない。

  「何を知りたいときに、どの資料を見るか」が分かることを目的とする。
