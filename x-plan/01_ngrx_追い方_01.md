> dispatchしたら createFeature の onで作られたところにまずとびますか?

はい、先に走ります。dispatch → reducer（onのハンドラ） → 状態更新 → effects の順です。

順序の根拠
store.dispatch(action) はまず ActionsSubject に action を流します。それを購読しているのが @ngrx/store の State で、そこで reducer が実行されます。実装はこういう形です:


// @ngrx/store の State クラス（概略）
stateAndAction$.subscribe(({ state, action }) => {
  this.next(state);          // ① reducer 結果の新 state を配る
  scannedActions.next(action); // ② その後 action を横流し
});
@ngrx/effects の Actions は ② の ScannedActionsSubject から来ます。つまり effects が action を受け取る時点で、reducer はすでに実行済み・state は更新済みです。

このコードでの具体的な流れ
loadUsers() を dispatch した場合:

users.reducer.ts:19 の on(loadUsers, ...) が動き、isLoading: true の新しい state ができる
selectors 経由で isLoading を見ている画面が更新される
users.effects.ts:11 の ofType(loadUsers) が通過し、API 呼び出しが始まる
レスポンスが loadUsersSuccess({ users }) になって dispatch され、また 1 に戻る（今度は users.reducer.ts:20 の on）
補足 2 点
on は「飛び先」ではなく分岐結果: createReducer は action.type をキーにしたハンドラの表を作っており、dispatch のたびに登録済み reducer が全部呼ばれます。該当する on がない reducer は state をそのまま返すだけです。デバッガでブレークを張れば、最初に止まるのは確かに該当の on のコールバック内です。
effects が dispatch した action も同じ経路: 特別扱いはなく、loadUsersSuccess もまた reducer が先、という同じ順序を辿ります。
