Angular公式の現在のスタイルガイドは、実際に「Smart/Dumb に分けろ」とは書いていません。代わりに、**Component / Directive のコードは画面表示に関係する責務へ寄せ、UIがなくても成立するコードは別ファイルへ出す**、という方針です。公式も具体例として「フォームの検証ルール」「データ変換」を外へ分離することを挙げています。([Angular][1])

一番分かりやすいのは、参画予定のシミュレーション画面っぽい例で見ることです。

### まず、分離していない例

例えばこういうComponentがあったとします。

```ts
@Component({
  selector: 'app-simulation-condition',
  templateUrl: './simulation-condition.html',
})
export class SimulationConditionComponent {
  private readonly http = inject(HttpClient);

  readonly temperature = signal(100);
  readonly pressure = signal(50);

  readonly running = signal(false);
  readonly result = signal<number | null>(null);

  run(): void {
    // 業務ルール
    if (this.temperature() < 0 || this.temperature() > 300) {
      alert('温度が範囲外です');
      return;
    }

    if (this.pressure() < 10 || this.pressure() > 100) {
      alert('圧力が範囲外です');
      return;
    }

    // API用データへの変換
    const request = {
      temp_celsius: this.temperature(),
      pressure_kpa: this.pressure(),
    };

    this.running.set(true);

    // API通信
    this.http.post<{ predictedYield: number }>(
      '/api/simulations',
      request
    ).subscribe({
      next: response => {
        this.result.set(response.predictedYield);
        this.running.set(false);
      },
      error: () => {
        this.running.set(false);
      }
    });
  }

  getYieldLabel(value: number): string {
    if (value >= 95) {
      return '良好';
    }

    if (value >= 80) {
      return '注意';
    }

    return '要改善';
  }
}
```

動きます。

しかし、このComponentにはかなり違う種類の仕事が混在しています。

```text
SimulationConditionComponent

├─ 入力欄の状態を持つ              ← UI
├─ ボタンを押されたことを処理する   ← UI
├─ 温度の許容範囲を判断する         ← 業務ルール
├─ 圧力の許容範囲を判断する         ← 業務ルール
├─ API形式に変換する               ← データ変換
├─ HTTP通信する                    ← データアクセス
├─ Loading状態を管理する           ← UI
└─ 歩留まり表示ラベルを決める       ← UIなのか業務ルールなのか要検討
```

Angular Style Guide が問題視しているのは、主にこの状態です。

「これはSmart ComponentだからOK」「これはDumbだからNG」という分類ではありません。

---

### 業務ルールを外へ出す

まず、UIがなくても意味を持つものを取り出します。

```ts
// simulation-condition.ts

export interface SimulationCondition {
  temperature: number;
  pressure: number;
}
```

```ts
// simulation-condition-validation.ts

import { SimulationCondition } from './simulation-condition';

export function validateSimulationCondition(
  condition: SimulationCondition
): string[] {
  const errors: string[] = [];

  if (condition.temperature < 0 || condition.temperature > 300) {
    errors.push('温度は0〜300の範囲で指定してください');
  }

  if (condition.pressure < 10 || condition.pressure > 100) {
    errors.push('圧力は10〜100の範囲で指定してください');
  }

  return errors;
}
```

これにはAngularが一切登場しません。

```ts
validateSimulationCondition({
  temperature: 350,
  pressure: 50
});
```

ブラウザがなくても動きます。

つまりこれは、

> UIから独立できるロジック

の典型です。

公式Style Guideが例示している「form validation rulesを別関数・クラスへ出す」というのは、まさにこの発想です。([Angular][1])

---

### API用の変換も外へ出せる

バックエンドがこういう形式を要求しているとします。

```ts
export interface SimulationRequest {
  temp_celsius: number;
  pressure_kpa: number;
}
```

Component内で毎回変換するのではなく、

```ts
export function toSimulationRequest(
  condition: SimulationCondition
): SimulationRequest {
  return {
    temp_celsius: condition.temperature,
    pressure_kpa: condition.pressure,
  };
}
```

としておく。

これもAngularとは無関係です。

Angular公式が「data transformations」も外へ出せる例として挙げているのはこの種の処理です。([Angular][1])

### HTTP通信もServiceへ

```ts
@Injectable({
  providedIn: 'root',
})
export class SimulationService {
  private readonly http = inject(HttpClient);

  run(condition: SimulationCondition) {
    const request = toSimulationRequest(condition);

    return this.http.post<SimulationResult>(
      '/api/simulations',
      request
    );
  }
}
```

ここまで来るとComponentはかなり変わります。

```ts
@Component({
  selector: 'app-simulation-condition',
  templateUrl: './simulation-condition.html',
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class SimulationConditionComponent {
  private readonly simulationService = inject(SimulationService);

  protected readonly temperature = signal(100);
  protected readonly pressure = signal(50);

  protected readonly running = signal(false);
  protected readonly result = signal<SimulationResult | null>(null);

  protected readonly errors = computed(() =>
    validateSimulationCondition({
      temperature: this.temperature(),
      pressure: this.pressure(),
    })
  );

  protected run(): void {
    if (this.errors().length > 0) {
      return;
    }

    const condition: SimulationCondition = {
      temperature: this.temperature(),
      pressure: this.pressure(),
    };

    this.running.set(true);

    this.simulationService.run(condition).subscribe({
      next: result => {
        this.result.set(result);
        this.running.set(false);
      },
      error: () => {
        this.running.set(false);
      },
    });
  }
}
```

このComponentを日本語で読むと、

```text
画面に入力された温度
画面に入力された圧力

↓
現在エラーがあるか表示する

「実行」が押された
↓
エラーがあれば実行しない
↓
SimulationServiceへ実行を依頼
↓
実行中表示
↓
結果が来たら画面へ表示
```

となります。

かなり「画面の司令塔」に近くなっています。

ここがAngular Style Guideの言う

> focused on presentation

の感覚です。([Angular][1])

ただし、重要なのは「Componentにはロジックを書いてはいけない」ではありません。

### Componentに残してよいロジックもかなりある

例えば、

```ts
protected readonly showResultPanel = computed(() =>
  this.result() !== null && !this.running()
);
```

これはComponentに置いて全く不自然ではありません。

なぜなら、

> 結果パネルを表示するか

という完全にUIの都合だからです。

これも。

```ts
protected toggleDetails(): void {
  this.detailsOpened.update(value => !value);
}
```

当然Componentでいい。

これも。

```ts
protected selectRow(id: string): void {
  this.selectedRowId.set(id);
}
```

UI上の選択状態なのでComponentでいい。

さらに、

```ts
protected readonly buttonText = computed(() =>
  this.running()
    ? 'シミュレーション実行中...'
    : 'シミュレーション実行'
);
```

これもUI表示そのものなのでComponentでいいでしょう。

つまり、

```text
Componentにif文を書くな
Componentにcomputedを書くな
Componentに状態を持たせるな
```

ではありません。

---

### 境界を見る一番簡単な方法

この質問をするとかなり判断できます。

> 「Angular画面がなくなっても、このロジックは意味があるか？」

たとえば、

```ts
temperature >= 0 && temperature <= 300
```

がシステムの業務ルールなら、

```text
Angularがなくても必要
Reactでも必要
CLIでも必要
バックエンドでも意味がある

→ Component外
```

一方、

```ts
selectedRowId.set(id);
```

は、

```text
一覧画面で選択中の行を表示するため

→ UI固有
→ Component
```

です。

これがかなり強力な判断基準です。

### 少し微妙なのが「表示用データ変換」

例えば、

```ts
protected readonly displayYield = computed(() =>
  `${this.result()?.predictedYield.toFixed(1)}%`
);
```

これはComponentにあっても構いません。

「95.12345という値を95.1%と画面表示する」という**presentation concern**だからです。

ところが、

```ts
function classifyYield(value: number): YieldRank {
  if (value >= 95) return 'A';
  if (value >= 90) return 'B';
  return 'C';
}
```

というランクが、実際の業務上の判定ならComponentから出したほうがよい。

つまり同じ「変換」でも、

```text
95.123 → "95.1%"
             ↑
          表示都合

95.123 → Aランク
             ↑
          業務ルール
```

では意味が違います。

前者はUI。

後者はDomainです。

### Smart/Dumbとの最大の違い

昔ながらのSmart/Dumb思想だと、ざっくり、

```text
SimulationPageComponent
  ↓ Smart
Store / Serviceへアクセス
  ↓
SimulationFormComponent
  ↓ Dumb
input/outputだけ
```

のように分類します。

しかしAngular Style Guideの現在の考え方なら、そこまで形式的には要求していません。

例えば、

```ts
export class SimulationPageComponent {
  private readonly service = inject(SimulationService);

  readonly data = this.service.data;
}
```

というComponentがあっても構わない。

逆に「Dumb Componentだから」という理由で、巨大な業務ロジックをComponentへ入れたらおかしい。

見るべきなのは、

```text
Smartか？
Dumbか？
```

より、

```text
このロジックは
「画面を成立させるためのロジック」なのか？

それとも
「画面がなくても成立するロジック」なのか？
```

です。

---

実務では、私は次のように覚えておくのが一番分かりやすいと思います。

```text
Component / Directive に残す

・表示する
・隠す
・選択する
・開く / 閉じる
・クリックを受ける
・input/outputをつなぐ
・表示用computed
・UI固有の一時状態
・Service / Storeを呼ぶきっかけ


外へ出す

・業務ルール
・入力値の意味的な検証
・計算
・データ変換
・API通信
・永続的な状態管理
・複数画面で共有できる処理
・Angularがなくても成立する処理
```

この理解なら、**「Smart/Dumbをやめた」のではなく、「Smart/Dumbという二分類に縛らず、責務の境界そのものを見るようになった」**と捉えるとかなり正確です。

特にClearML Webのような巨大Angularプロジェクトを読むときは、この視点が有効です。「このComponentがSmartかDumbか」を判定するより、**Component内の各メソッドを1個ずつ見て『これはUI責務か、それとも外へ出せるロジックか』と判定する**方が、現在のAngular Style Guideに近い読み方になります。
