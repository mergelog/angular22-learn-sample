完全な世界共通ルールではありませんが、かなり広く使われているのが **Conventional Commits** という規約です。

ポイントとして、よく見る `fixed:` は慣習的な書き方で、Conventional Commits の正式な代表形は **`fix:`** です。

基本形はこうです。

`<type>(<scope>): <description>`

たとえば、

`fix: ログイン時の例外を修正`

`feat: ユーザー検索機能を追加`

`refactor: API呼び出し処理をServiceへ分離`

scope を付けるなら、

`fix(auth): トークン期限切れ時の処理を修正`

`feat(experiment): 実験一覧にフィルターを追加`

という形です。

代表的なバリエーションはこのあたりです。

| type        | 意味            | 例                           |
| ----------- | ------------- | --------------------------- |
| `feat:`     | 新機能追加         | `feat: CSVエクスポート機能を追加`      |
| `fix:`      | バグ修正          | `fix: 一覧画面の表示崩れを修正`         |
| `docs:`     | ドキュメントのみ      | `docs: READMEに起動手順を追加`      |
| `refactor:` | 動作を変えないコード整理  | `refactor: 重複処理をServiceへ移動` |
| `test:`     | テスト追加・修正      | `test: UserServiceのテストを追加`  |
| `chore:`    | 雑務・保守作業       | `chore: 不要ファイルを削除`          |
| `style:`    | コードの意味を変えない整形 | `style: インデントを修正`           |
| `perf:`     | パフォーマンス改善     | `perf: 一覧取得処理を高速化`          |
| `build:`    | ビルド関連         | `build: Angularのビルド設定を変更`   |
| `ci:`       | CI/CD関連       | `ci: GitHub Actionsを追加`     |
| `revert:`   | コミット取り消し      | `revert: "feat: CSV出力を追加"`  |

特に実務では、まずこの6つを覚えておけば十分です。

`feat:`
`fix:`
`refactor:`
`docs:`
`test:`
`chore:`

この中で少し分かりづらいのが `chore:` と `refactor:` です。

たとえば、

`chore: package.jsonの不要なscriptを削除`

これは機能そのものを整理しているわけではなく、プロジェクトのメンテナンスなので `chore:`。

一方、

`refactor: Component内のAPI処理をServiceへ移動`

は、外から見た動作は同じだけれど内部構造を改善しているので `refactor:` です。

Angular案件なら、こんな使い分けがかなり自然です。

```text
feat(experiments): 実験一覧にステータス絞り込みを追加

fix(experiments): ページ遷移後にフィルターが消える問題を修正

refactor(experiments): フィルター処理をcomputedへ移動

test(experiments): フィルター処理のテストを追加

docs: ローカル起動手順を更新

chore: 未使用dependencyを削除
```

さらに Conventional Commits には破壊的変更を表す書き方もあります。

```text
feat(api)!: Experiment APIのレスポンス形式を変更
```

`!` が「後方互換性のない変更」を表します。

また、本文の末尾に

```text
BREAKING CHANGE: Experiment.idをnumberからstringへ変更した
```

と書く方法もあります。

実際のところ、Git自体には何の決まりもありません。

つまり、

`fixed bug`

`修正`

`ログイン直した`

でもGitとしては全く問題ありません。

ただし Conventional Commits にしておくと、履歴を見たときに非常に読みやすくなります。

たとえば、

```text
feat: add experiment filter
fix: restore selected tab
refactor: simplify router guard
docs: update setup guide
chore: remove unused package
```

と並んでいれば、「どんな種類の変更だったのか」が `git log` を一目見ただけで分かります。

さらにこの形式は semantic-release などと組み合わせると、

`feat:` → minor version

`fix:` → patch version

`BREAKING CHANGE` → major version

のようにバージョンアップを自動判定することもできます。

なお、よく見かけるものの Conventional Commits の基本typeではないものもあります。

```text
hotfix:
security:
deps:
update:
cleanup:
wip:
fixed:
add:
change:
```

プロジェクト独自ルールとして使うのは問題ありません。ただ、特に理由がなければ、

`fixed:` → `fix:`
`add:` → `feat:`
`cleanup:` → `refactor:` または `chore:`

あたりに寄せた方が、他の開発者にも意味が伝わりやすいです。

今のように個人開発やAngular/ClearMLのコードリーディング用コミットも多いなら、私はかなりシンプルに

```text
feat:
fix:
refactor:
docs:
test:
chore:
```

の6種類＋必要なときだけ `build:` `ci:` くらいに絞るのが扱いやすいと思います。特に `swc: plan作成` のような独自prefixを使っている場合も、`docs(swc): plan作成` や `chore(swc): plan作成` のように **scope側へプロジェクト内分類を持たせる**方法があります。
