再度、指摘が発生しました。前回よりかなり良くなっていましたが、**大規模案件の実戦用チェックリストとしては、まだ重要な抜けがありました**。

まず前提を更新します。2026年9月24日時点では `@ngrx/store`、`@ngrx/signals` ともに **22.0.1 が最新**です。前回、一部の根拠にv21や古いEvents RFCを使っていたため、現行NgRx 22基準で再確認しました。([npm][1])

今回見つかった主な修正点は次の5点です。

1. **Action/Eventの受け手を1か所だと思ってはいけない。** 1つのNgRx Actionを複数Reducer・複数Effectが受けることがあります。公式ESLintガイドでも「1 Actionから複数Effectを起動する」構成が示されています。したがって「Effectを見つけたから終わり」ではなく、**全 `on(Action)` / 全 `ofType(Action)` を検索**するのが基本です。([NgRx][2])
2. SignalStore Eventも同様で、`withReducer` / `withEventHandlers` だけではありません。`Events.on(...)` はStore外でも利用できます。したがって **Event creatorの参照をプロジェクト全体で探す**必要があります。([GitHub][3])
3. SignalStore Eventsには**スコープ**があります。`provideDispatcher()` や `toScope()` があるため、同じEventでも「どのInjector階層に届くか」を確認しないと経路を誤認する可能性があります。([NgRx][4])
4. `withState → patchState` と考えるのは狭すぎました。Stateは `patchState` のほか、`withReducer`、Entity updater、独自featureからも更新されます。
5. `Model` は「必ず追う場所」ではなく、**型境界を越えたときに追う場所**です。特にSelector読解なら `State → Domain Model`、Effect/APIなら `Action payload → DTO → Domain Model` という順序になります。

以上を反映した、これを最終版とします。

## 大規模案件「遭遇したら次に何を追うか」最終版

| 遭遇したもの                        | 最初に追う                 | 次に追う                            | 特に注意                                         |
| ----------------------------- | --------------------- | ------------------------------- | -------------------------------------------- |
| `store.dispatch(A())`         | **Aの定義**              | 全`on(A)`＋全`ofType(A)`           | Actionは複数箇所が反応できる                            |
| `createAction(A)`             | payload型              | dispatch元＋Reducer＋Effect        | producer / consumer両方向                       |
| `createActionGroup()`         | 対象Event               | 使用箇所                            | group全体ではなく対象Action一本を追う                     |
| `props<T>()`                  | **T**                 | dispatch時の実値                    | Domain/DTO/ViewModelのどれか確認                   |
| `createReducer()`             | `initialState`＋State型 | 各`on()`                         | State全体像を先に掴む                                |
| `on(A, ...)`                  | **A**                 | Aの全dispatch元                    | 「なぜこの変更が起きる？」                                |
| `createEffect()`              | **`ofType()`**        | Service / selector / 出力Action   | Effectの入力と出力を両方見る                            |
| `ofType(A)`                   | A定義                   | Aのdispatch元                     | 起動原因                                         |
| `map(() => B())`              | **B**                 | BのReducer＋Effect                | Actionチェーン継続                                 |
| `catchError(...B())`          | Failure Action        | Reducer / Effect / UI           | エラー経路                                        |
| `dispatch:false`              | `ofType()`            | `tap`先                          | Router/Storage/log等                          |
| `concatLatestFrom()`          | Selector              | SelectorのState                  | Action以外の依存を確認                               |
| `createFeatureSelector<S>()`  | **S＝Feature State**   | initialState → State内型          | Domain Modelより先にState                        |
| `createSelector()`            | 入力Selector全部          | 元State → 使用側                    | データの派生経路                                     |
| `store.select()`              | Selector定義            | Stateまで逆上り                      | 読取り経路                                        |
| `selectSignal()`              | Selector定義            | Stateまで逆上り                      | ObservableかSignalかは二次的                       |
| `createFeature()`             | reducer / State       | 自動生成Selector                    | Featureのまとまり                                 |
| `provideState()`              | Feature / reducer     | 登録場所                            | lazy routeかrootか                             |
| `provideEffects()`            | Effect                | 登録場所                            | root/feature双方で登録可能 ([NgRx][5])              |
| `createEntityAdapter<T>()`    | **T**                 | EntityState → reducer           | 正規化State                                     |
| `adapter.setAll/updateOne...` | 対象Entity              | 呼出Action                        | Entity更新経路                                   |
| `signalStore()`               | 中の`withXxx`一覧         | State / method / event          | Storeの設計図                                    |
| `withState()`                 | State型                | **全Writerを探す**                  | patchStateだけではない                             |
| `patchState()`                | 変更property            | computed / UI                   | State変更の結果側                                  |
| `withMethods()`               | 対象method              | 呼出元＋内部処理                        | Command入口                                    |
| `rxMethod()`                  | **誰が呼ぶか**             | pipe → Service → State更新        | static値/Signal/Observableを入力可能 ([GitHub][6]) |
| `withComputed()`              | 元Signal               | 使用側                             | 派生State                                      |
| `withEntities<T>()`           | **T**                 | updater → `entities()`利用側       | Entity系State                                 |
| `eventGroup()`                | 対象Event＋payload型      | **全参照箇所**                       | Event定義であって発火処理ではない                          |
| `injectDispatch(group)`       | group/Event           | event consumer全部                | Event発火側                                     |
| `Dispatcher.dispatch(E())`    | **E**                 | reducer / handler / `Events.on` | Event発火側                                     |
| `Events.on(E)`                | **E**                 | Eの発火元                           | Store外にも存在し得る                                |
| `withEventHandlers()`         | `events.on(...)`      | Service → 出力Event               | SignalStoreの副作用側                             |
| `withReducer()`               | `on(Event, ...)`      | Event発火元＋変更State                | SignalStoreの同期State変更                        |
| `signalStoreFeature()`        | **実装へ入る**             | 中の`withXxx`                     | 抽象化を剥がす                                      |
| 独自`withFoo()`                 | **Definitionへ飛ぶ**     | State/Methods/Events            | 名前から推測しない                                    |
| `provideDispatcher()`         | Provider位置            | 子Injector                       | **Event scope確認**                            |
| `toScope()`                   | 対象scope               | Dispatcher階層                    | Eventの到達範囲確認                                 |
| Angular `signal()`            | Writer                | computed/effect/template        | `.set/.update`だけでなく外部featureも確認              |
| Angular `computed()`          | 中で読むSignal            | 使用側                             | 派生経路                                         |
| Angular `effect()`            | 中で読むSignal            | 外部副作用                           | NgRx Effectとは別物                              |
| `input()`                     | 親template `[x]`       | 親値                              | 親→子                                          |
| `output()`                    | `.emit()`             | 親template `(x)` → handler       | 子→親                                          |
| Angular `model()`             | 親`[(x)]`              | 親Signal                         | 双方向。Domain Modelとは別                          |
| `toSignal()`                  | Observable            | その上流                            | RxJS→Signal境界                                |
| `toObservable()`              | Signal                | pipe                            | Signal→RxJS境界                                |
| Service method                | 戻り型                   | HTTP / mapper                   | 外部境界                                         |
| `HttpClient`                  | Response DTO          | mapper / Effect                 | Backendとの境界                                  |
| Facade                        | **中身**                | dispatch / Store method         | Facadeで追跡を止めない                               |
| Router Store Action           | Effect / Reducer      | Router起点                        | Component発火とは限らない                            |

NgRx Storeについては、dispatchされたActionは**Reducerが先、その後Effects**という実行順であることも現行公式ガイドで確認できます。([NgRx][7])

ただし、コードリーディングするときは実行順どおり、

`Action → Reducer → Effect`

と一本ずつ読む必要はありません。

むしろActionを発見したら、

```text
                 Action
              ↙    ↓    ↘
        Reducer   Effect   Effect
           ↓        ↓        ↓
         State    API     Router
```

のように、**そのActionに反応している全箇所を一度洗い出す**方が大規模案件では安全です。

SignalStore Eventsも同じです。

```text
                    Event
             ↙        ↓        ↘
      withReducer   Handler   Events.on
           ↓           ↓         ↓
         State        API      任意処理
```

さらに現在のEventsではDispatcherにscopeがあるため、

```text
Event
 ↓
どこでdispatch？
 ↓
provideDispatcher() はある？
 ↓
どのInjector scope？
 ↓
誰までEventが届く？
```

まで見る。

ここは今回の再レビューで追加した中でも特に重要です。大規模AngularではComponent単位・Feature単位でProvider scopeが変わるため、**「同じEvent名だからこのhandlerに必ず届く」とは決めつけない**方が安全です。([GitHub][8])

そして、質問の発端だった「Modelを見るタイミング」については、最終的にこう整理するのが一番正確です。

```text
createFeatureSelector
  ↓
Feature State型
  ↓
initialState
  ↓
そのStateの各property
  ↓
必要になったところでDomain Model


Effect
  ↓
Action payload
  ↓
Service
  ↓
API DTO
  ↓
mapper
  ↓
Domain Model


Selector
  ↓
State
  ↓
Domain Model
  ↓
ViewModel
  ↓
Component
```

つまり、**Modelファイルを見つけたら読む**ではなく、

> 「今追っているデータの型が別の意味の型へ変わったところで型定義を見る」

です。

これが大規模案件ではかなり強いです。

最終的に、迷子になったときの判断軸はこの6問で十分です。

1. **誰がこれを起こした？**
2. **同じAction/Eventを他に誰が受けている？**
3. **今流れているデータの型は何？**
4. **ここでStateの何が変わる？**
5. **その変更を誰が読む？**
6. **この処理・Eventの有効範囲はどこ？**

今回の二度目の敵対的レビューでは、特に **「1 Action/Event = 1 consumerではない」** と **「SignalStore Eventsにはscopeがある」** の2点が前回不足していました。

この2点まで入れた今回版なら、NgRx / SignalStoreが混在する大規模案件で使う「追跡の基本表」としてかなり安全な形になったと判断します。
