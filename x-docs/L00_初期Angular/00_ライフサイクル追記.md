公式 Lifecycle ガイドと現行APIを基準に、**「何回動くか」「何と結びつけて覚えるか」**を追加しました。`afterRenderEffect` は通常のライフサイクルとは区別して「関連API」として入れるのが分かりやすいです。`DestroyRef` と `takeUntilDestroyed()` も破棄処理の理解につながるので追加しています。 ([Angular][1])

| **フェーズ**        | **メソッド / API**          | **実行タイミング**                             | **学習ポイント**                                                        |
| --------------- | ----------------------- | --------------------------------------- | ----------------------------------------------------------------- |
| 作成              | `constructor`           | Angular がコンポーネントをインスタンス化するとき            | Angular固有ではなく **JavaScript / TypeScript のコンストラクター**。DIした値の受け取りなど。 |
| 変更検知            | `ngOnChanges`           | `input` が変更されるたび                        | **初回も実行され、`ngOnInit` より先**。変更前・変更後の値を `SimpleChanges` で確認できる。     |
| 変更検知            | `ngOnInit`              | `input` の初期値が設定された後に **1回**             | 初期化処理。初期 `input` を使った処理を置ける。                                      |
| 変更検知            | `ngDoCheck`             | このコンポーネントが変更検知されるたび                     | Angular標準では検知できない独自変更を確認するとき。**頻繁に呼ばれるので重い処理は避ける**。               |
| Content         | `ngAfterContentInit`    | 投影されたコンテンツの初期化後に **1回**                 | `ng-content` / `contentChild()` 側と結びつけて覚える。                       |
| Content         | `ngAfterContentChecked` | 投影コンテンツがチェックされるたび                       | 頻繁に実行される。通常は使用頻度低め。                                               |
| View            | `ngAfterViewInit`       | 自分のビューと子ビューの初期化後に **1回**                | `viewChild()` / `viewChildren()` 側と結びつけて覚える。                      |
| View            | `ngAfterViewChecked`    | 自分のビューがチェックされるたび                        | 頻繁に実行される。通常は使用頻度低め。                                               |
| レンダリング          | `afterNextRender`       | **次回**、アプリ全体のDOMレンダリング完了後に **1回**       | DOMサイズ取得など。「次のレンダリング後に一度だけ」。                                      |
| レンダリング          | `afterEveryRender`      | アプリ全体のDOMレンダリングが完了するたび                  | DOM連携など。「レンダリング後に毎回」。                                             |
| レンダリング<br>関連API | `afterRenderEffect`     | Signal依存でEffectが dirty になり、レンダリングが完了した後 | **Signal連動のレンダリング後Effect**。`effect()` よりDOM操作向き。                  |
| 破棄              | `ngOnDestroy`           | コンポーネントが破棄される直前に **1回**                 | timer・イベントなどの後始末。                                                 |
| 破棄<br>関連API     | `DestroyRef`            | コンポーネントなどの破棄時                           | `ngOnDestroy` の代わりに `onDestroy()` で後始末を登録できる。                     |
| 破棄<br>RxJS連携    | `takeUntilDestroyed()`  | コンポーネントなどの破棄時にObservableを自動解除           | RxJSの購読解除では現在かなり重要。`ngOnDestroy` に手動 `unsubscribe()` を書く量を減らせる。   |

### 特にセットで覚える

| **これ**                 | **一緒に覚えるもの**                     |
| ---------------------- | -------------------------------- |
| `ngOnChanges`          | `input()` / `@Input`             |
| `ngAfterContentInit`   | `ng-content` / `contentChild()`  |
| `ngAfterViewInit`      | `viewChild()` / `viewChildren()` |
| `afterNextRender`      | 次のDOMレンダリング後に1回                  |
| `afterEveryRender`     | DOMレンダリング後に毎回                    |
| `effect()`             | Signal変更に反応する副作用                 |
| `afterRenderEffect()`  | Signal変更 → DOMレンダリング → 副作用       |
| `ngOnDestroy`          | 後始末                              |
| `DestroyRef`           | `ngOnDestroy` の関数型に近い代替手段        |
| `takeUntilDestroyed()` | RxJS購読を破棄時に自動終了                  |

### `effect()` と `afterRenderEffect()` の違い

`effect()`

Signal変更
↓
Effect実行

`afterRenderEffect()`

Signal変更
↓
Angularがレンダリング
↓
Effect実行

つまり、**Signalの値に反応するだけなら `effect()`、DOMへ反映された後の状態を扱いたいなら `afterRenderEffect()`** と覚える。

特に今の学習状況なら、`ngAfterContentInit → contentChild()`、`ngAfterViewInit → viewChild()`、`ngOnDestroy → takeUntilDestroyed()` の3本を関連付けると、単なる暗記ではなく実装としてつながります。

なお `afterNextRender` / `afterEveryRender` はクラスのライフサイクルメソッドではなく、アプリ全体のレンダリング完了後に動く standalone function です。また `afterRenderEffect` は Signal 依存が dirty のときにレンダリング後実行され、DOMアクセス向けに `earlyRead → write → mixedReadWrite → read` のフェーズも持ちます。 ([Angular][2])
