# コンポーネント間コネクション(Inter-component connection)技術選定

Angularでの画面作成時の技術選定で、結局動作としては機体動作だけど
「それ使わないでこっち使った方が後々拡張性があるのに」とか
「ここはこうだからこれ一択でしょ」みたいな懸念が発生しそうで怖い。
そこでここでは、設計の助けになるような基本的な技術選定フローを示す。

--- 以下は作成したAIの解答をそのまま貼ったもの

かなり作り直した方がよいです。添付の複数レビューで共通していた核心は、**「APIを横一列に並べるのではなく、責務・所有権・ライフサイクルを先に決める」**ことでした。

またAngular 22公式を照合すると、レビュー中の主張には採用すべきものと、そのまま採用すべきでないものが混在していました。以下はそれを整理した、実務で毎回確認することを想定した版です。

# Angular 22 UI構成・コンポーネント連携 技術選定フロー

最初に覚えておきたいのは、これです。

> **Component / input / ng-content / @if / @defer は競合する選択肢ではない。**

たとえば普通に、

```html
@if (visible()) {
  <app-panel>
    <app-chart />
  </app-panel>
}
```

と書けます。

この中では、

```text
@if          = いつ表示するか
app-panel    = UI境界
ng-content   = 誰が中身を所有するか
app-chart    = 子Component
```

という別々の問題を同時に解決しています。

したがって、技術選定も「一問一答」ではなく、次の順序で行います。

## 1. 最上位：まず責務を決める

| 自問                             | 第一候補             | 判断基準                                      | 危険信号                  |
| ------------------------------ | ---------------- | ----------------------------------------- | --------------------- |
| 独立したUI責務として名前を付けられるか？          | `Component`      | 独立した状態・表示・API・テスト境界を持つ                    | 「HTMLが10行を超えたから」だけで分割 |
| UIそのものではなく、既存要素へ振る舞いを追加したいか？   | `Directive`      | permission、focus、resize、tooltip、keyboard等 | 振る舞いだけなのにComponentで包む |
| Componentへ共通の振る舞いを静的合成したいか？    | `hostDirectives` | 複数Componentへbehaviorを組み込む                 | runtimeで付け替えたい場合      |
| 単なるHTML構造・セマンティクスか？            | HTML要素           | `section`、`article`、`div`等                | 何でもComponent化         |
| DOMを増やさずAngularテンプレートを束ねたいだけか？ | `ng-container`   | Angular上だけの構造                             | 再利用部品として扱う            |

AngularではDirectiveは再利用可能なbehaviorをカプセル化する正式な仕組みで、`hostDirectives` はComponent/Directiveへの静的なbehavior compositionです。runtime追加用ではありません。([Angular][1])

ここで重要なのは、

> **「何回使うか」ではなく「独立した責務か」**

です。

一度しか使わないComponentでも意味がありますし、3箇所に似たHTMLがあるだけで無理に共通Component化する必要もありません。

---

# 2. データ・状態をどうつなぐか

次に「誰がstateを所有するか」を決めます。

| 自問                             | 第一候補                          | 典型例                             | 注意                       |
| ------------------------------ | ----------------------------- | ------------------------------- | ------------------------ |
| 親が所有する値を子へ渡すだけか？               | `input()`                     | `waferId`, `status`, `config`   | 子へ親stateの管理責務まで渡さない      |
| 子で起きた事実を利用側へ知らせるか？             | `output()`                    | `selected`, `closed`, `deleted` | 業務状態を何階層もrelayしない        |
| 子自身が1つの値を変更し、親にも同期するUI APIか？   | `model()`                     | `opened`, `page`, `value`       | domain stateの所有者を曖昧にしない  |
| 兄弟2つ程度がstateを共有するか？            | 共通親へlift                      | Filter → ResultTable            | 無理にStoreへ上げない            |
| feature内の離れた複数Componentが共有するか？ | feature Service + Signal/RxJS | selected experiment等            | root serviceへ全部集めない      |
| 状態遷移・derived state・副作用が複雑か？    | SignalStore / NgRx Store等     | 大規模feature state                | 単純local stateまでStore化しない |
| application/domain全体で共有するか？    | Store / domain service        | auth、project state等             | 「便利だからglobal」にしない        |

`output()` のAngularイベントはDOMイベントのようにbubbleしません。そのため、階層を越えて何段も中継し始めたら、単なる`output()`の問題ではなくstate ownerを再検討するサインです。([Angular][2])

`model()` はAngular公式でも「ユーザー操作でComponent自身が値を変更し、それを親へ反映する」二方向Component APIとして位置付けられています。したがって「modelは危険だから極力禁止」というレビューは強すぎます。ただし業務データの所有権まで双方向にするのは避けた方が安全です。([Angular][3])

# 3. Formかどうかを先に確認する

ここは前版で大きく抜けていました。

| 自問                                                | 第一候補                                                      |
| ------------------------------------------------- | --------------------------------------------------------- |
| 単なるComponentの双方向値か？                               | `model()`                                                 |
| Angular 22の新規Signal中心アプリでcustom form controlを作るか？ | Signal Forms + `FormValueControl` / `FormCheckboxControl` |
| 既存Reactive Formsに合わせるcustom controlか？             | 既存設計に従い `ControlValueAccessor` 等                          |
| 大規模既存Reactive Forms画面か？                           | 原則として既存Reactive Formsを維持                                  |
| 単純な小規模フォームか？                                      | Signal Forms / Reactive / Template-drivenをプロジェクト方針で決定     |

Angular 22ではSignal FormsはStableです。一方で公式も、既存Reactive Formsアプリやproduction stabilityを重視する場合はReactive Formsを堅実な選択肢として残しています。([Angular][4])

Signal Formsのcustom controlでは`FormValueControl`のprimary valueとして`model()`を使用できます。つまり、

```text
model() と Forms
```

は排他的ではありません。([Angular][5])

ここはレビュー間でも意見が割れていましたが、Angular 22公式に合わせるならこの整理が安全です。

# 4. 「中身を外から渡す」場合

ここが `ng-content` と `ng-template` の本当の分岐です。

| 自問                                      | 第一候補                | 具体例                            |
| --------------------------------------- | ------------------- | ------------------------------ |
| 利用側が完成した具体的HTMLを所有するか？                  | `ng-content`        | Card本文、Panel header            |
| header/body/actions等のsemantic slotが必要か？ | `ng-content select` | Card、Dialog shell              |
| 受け側からデータを渡して描画させたいか？                    | `TemplateRef`       | Table cell                     |
| 0回/N回、受け側の都合で生成したいか？                    | `TemplateRef`       | row renderer、Accordion content |
| 開くまでComponentを生成したくないか？                 | `TemplateRef`等      | lazy tab content               |
| 描画方法そのものを利用側へ委ねたいか？                     | `TemplateRef`       | cell renderer                  |
| 単純な固定レイアウトslotか？                        | `ng-content`        | header / footer                |

最も使える覚え方は、

```text
ng-content
= 完成した「中身」を渡す

TemplateRef
= 「作り方」を渡す
```

です。

さらに、

```text
ng-content
= 利用側がcontentを所有

TemplateRef
= 受け側が「いつ・何回・どんなcontextで展開するか」を決められる
```

という差があります。

`TemplateRef`ではcontextも渡せます。

```html
<ng-template #cell let-row="row">
  {{ row.name }}
</ng-template>
```

受け側が、

```html
<ng-container
  [ngTemplateOutlet]="cell"
  [ngTemplateOutletContext]="{ row: currentRow }"
/>
```

とできます。([Angular][6])

# 5. `ng-content` を選ぶ前の必須チェック

これは毎回見た方がよいです。

| 質問                                | YESなら                                |
| --------------------------------- | ------------------------------------ |
| 中身へ受け側からrow等のcontextを渡したい？        | `TemplateRef`を検討                     |
| 中身を開くまで生成したくない？                   | `ng-content`ではなくTemplate fragmentを検討 |
| 受け側が0回/N回生成したい？                   | `TemplateRef`                        |
| 単なるlayout slot？                   | `ng-content`                         |
| header/body/footerのsemantic slot？ | `ng-content select`で問題なし             |

特にこれは強いルールにして構いません。

> **`ng-content` 自体を `@if` / `@for` / `@switch` で条件付きにして、投影contentの生成を抑制しようとしない。**

Angular公式は明確に避けるよう指示しており、placeholderを隠していてもprojected contentは生成されます。条件付き生成にはtemplate fragmentを使用します。([Angular][7])

またprojected contentは投影先ではなく、**宣言した側のviewに所属する**という点も重要です。([Angular][7])

一方、

> `ng-content select` は非推奨だから避ける

までは言えません。Angular 22でも正式なmulti-slot projectionとして文書化されています。([Angular][7])

---

# 6. `ng-template` ファミリーは一まとめで覚える

前版では別々の技術のようになっていましたが、こう整理します。

| API                                     | 意味           |
| --------------------------------------- | ------------ |
| `<ng-template>`                         | 描画レシピを定義     |
| `TemplateRef<T>`                        | そのレシピをTSから扱う |
| `NgTemplateOutlet`                      | template上で展開 |
| `ngTemplateOutletContext`               | 展開時のデータを渡す   |
| `ViewContainerRef.createEmbeddedView()` | TSから展開       |

つまり、

```text
ng-template
      ↓
TemplateRef
      ↓
ngTemplateOutlet
```

という1つの技術ファミリーです。([Angular][6])

汎用Tableなどでは、

```ts
TemplateRef<{ $implicit: Row }>
```

のようにcontextを型付けできる設計を優先します。

`TemplateRef<any>` が大量に流れ始めたら黄色信号です。

# 7. 子Componentを直接操作する必要があるか

ここも前版に追加します。

| 自問                                 | 第一候補                            | 例                          |
| ---------------------------------- | ------------------------------- | -------------------------- |
| 自分のtemplate内の子へimperative APIを呼ぶか？ | `viewChild()`                   | focus、scroll、chart refresh |
| 投影された子Componentを取得したいか？            | `contentChild()`                | selected tab               |
| 投影された子群を管理したいか？                    | `contentChildren()`             | Tabs、Menu、Columns          |
| DOM elementそのものが必要か？               | `viewChild(... ElementRef ...)` | measure等                   |

たとえば、

```html
<app-tabs>
  <app-tab />
  <app-tab />
  <app-tab />
</app-tabs>
```

で`TabsComponent`がTab群を協調制御するなら、

```ts
tabs = contentChildren(TabComponent);
```

は非常に自然な設計です。

Angular 22ではsignal-based queryが推奨され、queryはComponent境界を越えません。([Angular][8])

ただし、

> `viewChild()`で子の普通のstateを直接書き換える

ようになったら黄色信号です。

値なら`input()`、イベントなら`output()`をまず疑います。

# 8. Componentの種類を切り替える場合

ここはかなり重要な修正です。

前版の、

> 2種類くらいなら`@if`

ではなく、

> **候補Component集合をcompile-timeに知っているか**

で決めます。

| 状況                                        | 第一候補                                                            |
| ----------------------------------------- | --------------------------------------------------------------- |
| 常に同じComponent                             | `<app-child />`                                                 |
| A/Bのような静的条件                               | `@if`                                                           |
| table/chart/wafer等、候補が静的に分かる              | `@switch`                                                       |
| Component class自体がruntime valueとして来る      | `NgComponentOutlet`                                             |
| registry/plugin等からComponent型が届く           | `NgComponentOutlet`                                             |
| ComponentRef・生成位置・生成タイミングをimperativeに管理する | `ViewContainerRef.createComponent()`                            |
| Angular view階層外へ生成する                      | standalone `createComponent()` + hostElement、通常はCDK Overlay等も検討 |

例えば、

```ts
type ViewType = 'table' | 'chart' | 'wafer';
```

なら、

```html
@switch (viewType) {
  @case ('table') {
    <app-table />
  }
  @case ('chart') {
    <app-chart />
  }
  @case ('wafer') {
    <app-wafer-map />
  }
}
```

がまず候補です。

Angular 22の`@switch`にはunion typeのexhaustive checkingもあります。([Angular][9])

対して、

```ts
rendererComponent: Type<unknown>;
```

のようにComponent型そのものがデータなら、

```html
<ng-container *ngComponentOutlet="rendererComponent" />
```

が自然です。

現在の`NgComponentOutlet`はinputs、content、injector、component instanceなども扱えます。([Angular][10])

# 9. `ViewContainerRef.createComponent()` の正確な位置付け

ここもレビューを整理すると重要です。

```text
NgComponentOutlet
= templateから宣言的に動的Componentを出す

ViewContainerRef.createComponent()
= TSから、現在のViewContainer位置に
  Componentをimperativeに生成する

createComponent()
= 既存ViewContainerに属させず
  hostElement等も含め自分で制御する
```

Angular 22公式はこの3つを明確に区別しています。`ViewContainerRef.createComponent()` は現在のView階層内へのinline UIにも正式に使えます。([Angular][10])

さらにAngular 22では、

```ts
inputBinding()
outputBinding()
twoWayBinding()
```

を使い、動的生成時にもtemplateに近い形でbindingsを指定できます。([Angular][10])

したがって、

> createComponentはOverlay専用

ではありません。

# 10. Routerを使う基準

「画面かどうか」では判断しません。

| 自問                            | YESならRouter候補 |
| ----------------------------- | ------------- |
| URLを直接開きたい？                   | Router        |
| ブックマークしたい？                    | Router        |
| リロード後に同じ状態へ戻したい？              | Router        |
| 戻る・進む対象？                      | Router        |
| Deep Linkしたい？                 | Router        |
| 権限・Resolver・lazy route単位にしたい？ | Router        |

したがって、

```text
タブ = Routerではない
```

ではありません。

たとえば、

```text
/project/123/overview
/project/123/experiments
/project/123/artifacts
```

ならタブUIでもRouterが自然です。

Angularはnested routeによって、ページ全体ではなく**部分ViewだけをRouterで切り替える**ことを正式にサポートしています。([Angular][11])

---

# 11. 遅延読み込みは別軸

ここもComponent構成とは分離します。

| 自問                                | 第一候補                      |
| --------------------------------- | ------------------------- |
| 初期画面に不要なUIコードか？                   | `@defer`                  |
| viewportへ来た時点で必要か？                | `@defer (on viewport)`    |
| 操作されて初めて必要か？                      | `@defer (on interaction)` |
| URL単位でFeature全体を遅延するか？            | Router lazy loading       |
| 重いService/libraryを利用時まで読み込みたくないか？ | `injectAsync()`           |
| 単なる開閉だけか？                         | `@if`                     |

重要なのは、

```text
@defer = 重いから
```

ではなく、

```text
@defer =
初期renderに不要なコードを
初期bundleから外せるか
```

です。([Angular][12])

そして、

```html
@defer (when show()) {
  <app-chart />
}
```

は一度ロードされた後、

```text
show() = false
```

へ戻ってもplaceholderには戻りません。

つまり、

```text
開閉制御 → @if

初回loadを遅らせる → @defer
```

です。([Angular][12])

Angular 22ではService側にも`injectAsync()`が追加され、重いService dependencyをlazy-loadできます。([Angular][13])

---

# 12. 制御フローは最後に別判定する

ここが今回の再設計でかなり重要です。

| 状況                   | 技術             |
| -------------------- | -------------- |
| 条件表示                 | `@if`          |
| 複数variant            | `@switch`      |
| 配列反復                 | `@for`         |
| template内計算結果へ名前を付ける | `@let`         |
| DOM無しの構造化            | `ng-container` |
| 初期ロードから外す            | `@defer`       |

これらは、

```text
Component
ng-content
TemplateRef
input/output
Router
```

の代わりではありません。

**直交する別軸**です。

# 最短判断フロー

前版のように一直線にはしません。

```text
① まず「何の問題か」を分類する
│
├─ UI境界
│    ├─ UIそのもの → Component
│    └─ 振る舞いだけ → Directive
│
├─ State
│    ├─ 親→子 → input
│    ├─ 子→利用側 → output
│    ├─ 局所的双方向 → model
│    └─ 遠距離共有 → Parent / Service / Store
│
├─ Content
│    ├─ 完成HTMLを渡す → ng-content
│    └─ 描画方法を渡す → TemplateRef
│
├─ Component type
│    ├─ 固定 → <app-child>
│    ├─ 静的候補 → @if / @switch
│    ├─ runtime Type → NgComponentOutlet
│    └─ imperative生成 → ViewContainerRef / createComponent
│
├─ Navigation
│    └─ URL・履歴対象 → Router
│
└─ Form
     └─ Form architectureに統合
        → Signal Forms / Reactive Forms
```

そして**その後に**、

```text
表示条件？        → @if
繰り返し？        → @for
DOM不要？         → ng-container
初期load不要？    → @defer
Overlay？         → Material/CDK
```

を重ねます。

この二段構えなら、

> 「`ng-content` と `@if`、どっち使えばいい？」

という本来比較すべきではないものを比較する事故がなくなります。

最後にAngular 22固有で一つ覚えておくと、**OnPushはv22からデフォルト**になっています。したがって新規Angular 22コードでは「小ComponentにするとOnPushを書きまくらなければならない」という感覚も変わっています。([Angular][14])

今回の版なら、ClearML Webのコードリーディングでもかなりそのまま使えます。たとえば`ng-template`を見た瞬間に「文法」ではなく、**「なぜここは完成HTMLではなく描画レシピを渡す必要があるのか？」**と設計意図から読めるようになります。
