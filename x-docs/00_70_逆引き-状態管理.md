# RxJS / NgRx / Signal系 逆引き辞書

対象は Angular 22.1.x / RxJS 7.8.x / NgRx 22.x。
以下の「推奨」は用途に応じた選択指針です。`—` は直接対応するAPIを挙げていない意味であり、実現不可能という意味ではありません。

前提として、NgRx列では **`[Store]` = 従来の @ngrx/store + Effects**、**`[SignalStore]` = @ngrx/signals** と区別します。SignalStoreはNgRx製品ですが、Action駆動を必須としません。`withMethods` や `rxMethod` によるメソッド駆動が可能です。 ([NgRx][1])

本文の **Effect / Effects は NgRx の副作用処理**、**`effect()` は Angular のAPI**です。共有ServiceやSignalStoreの共有範囲・寿命はproviderの配置で決まり、Service化するだけでアプリ全体の単一状態になるわけではありません。 ([Angular][14])

RxJS欄では、Observableを作る関数を **`[func]`**、`source$.pipe(...)` に渡すoperatorを **`[pipe]`**、値の通知と現在値の保持を担うObservableを **`[Subject]`** と表記します。

## よくある誤解の訂正

まず `combineLatest` と `computed()` は別物です。

`combineLatest` は**時間軸上を流れる複数Observableを合流**します。一方 `computed()` は**現在存在するSignal状態から派生値を計算**します。NgRx Store内の状態Aと状態Bから状態Cを作るなら、Effect内でObservableを `combineLatest` するよりSelectorを合成するのが通常は適切です。外部ストリームや処理途中のObservableの結合には `combineLatest` 等を使います。これはNgRx ESLintルールが示すStore selectorの設計指針であり、あらゆるObservable結合をSelectorに置き換えるという意味ではありません。 ([NgRx][2])

`forkJoin` も正確に覚える必要があります。

> 全入力が「最低1回emit」して「complete」したら、各入力の最後の値をまとめて1回だけemitする。

です。

RxJS 7.8.xでは、1つでも**一度もemitせずcompleteすると、その時点で `forkJoin` 自体も値を出さずcomplete**します。`forkJoin([])` も値を出さず即completeします。値をemitせずcompleteする入力やerrorになる入力がなくても、1つでも永久にcompleteしなければ待ち続けます。また1つがerrorになれば全体もerrorになり、他の入力からunsubscribeします。個々の失敗も結果として集めたい場合は、各入力の内側で `catchError` によって値へ変換します。 ([RxJS][3])

`take(1)` と `first()` も似ていますが契約が違います。`take(1)` は値が来れば1件取得し、値なしでsourceがcompleteしても正常終了します。条件で選ぶには `first(predicate)` を使い、該当値がないままsourceがcompleteすると、default値を指定していない限り `EmptyError` になります。`first()` は条件なしの最初の1件です。どちらもsourceが値を出さずcompleteもしなければ待ち続けます。期限が必要なら `timeout` を使い、期限超過を代替値へ変える場合はさらに `catchError` 等で `TimeoutError` を処理します。 ([RxJS][4])

## `concatLatestFrom` はこう覚える

```text
Actionが来た
  ↓
そのActionのタイミングで
factoryを評価して参照Observableを購読する
  ↓
参照先が同期的に値を出した場合のみ
その最新値とActionを組み合わせる
```

`withLatestFrom` と違ってObservable factoryを**遅延評価**することが本質です。

NgRx 18で `@ngrx/effects` からのexportは削除されたため、import元は、

```ts
import { concatLatestFrom } from "@ngrx/operators";
```

です。 ([NgRx][5], [v18移行ガイド][15])

`withLatestFrom` も参照先全てが少なくとも1回emitするまではsourceの通知を出力しません。その間のsourceの値は保留されず失われます。`concatLatestFrom` はsourceの通知ごとに参照先を購読するので、**その購読で同期emitしなければ、そのActionは後段へ流れません**。HTTP、`delay` 付きselector、初回通知が非同期になった `toObservable(signal)` などを渡しても値を待ってくれません。参照先を遅延生成するoperatorであって、非同期結果を待つoperatorではありません。 ([RxJS][16], [NgRx実装][17])

通常のStore selectorのように購読時に現在値を同期emitする参照先に使います。非同期処理の完了を待ちたい場合は、`switchMap` / `concatMap` 等の内側で処理し、必要なら結果をActionと組にします。

## 非同期競合・エラー処理で失敗しやすい点

`switchMap` が行うのは以前の内部Observableからのunsubscribeです。`HttpClient` は購読解除を進行中の通信の中断につなげますが、一般のPromiseや、解除処理を実装していないObservableの実処理まで止まる保証はありません。サーバーで既に実行された更新を元に戻す機能もありません。 ([RxJS][18], [Angular][19])

`concatMap` は内部Observableがcompleteしなければ次へ進まず、入力が速すぎると待ち行列が増えます。`mergeMap` は既定で同時実行数が無制限で、出力順も入力順とは限りません。`exhaustMap` が捨てる入力は後から再実行されず、抑制範囲も同じ購読内だけなので、サーバー側の重複実行対策の代わりにはなりません。 ([RxJS concatMap][20], [mergeMap][21], [exhaustMap][22])

継続してActionやメソッド呼び出しを処理したい場合、`take(1)` / `first()` / `catchError` の配置に注意します。

- NgRx Effectの外側に `take(1)` を置くとEffect全体がcompleteし、以後のActionを処理しなくなります。
- 外側の `catchError(() => EMPTY)` や `catchError(() => of(failureAction))` も、置き換えたObservableがcompleteするとEffect全体が終了します。通常はHTTP等の内部Observableで捕捉し、失敗Actionを返します。
- `rxMethod` でも未処理errorはメソッド全体の処理パイプラインを終了させます。接続したObservableがcompleteしても、その接続だけが終了し、`rxMethod` 自体は別の入力を受け取れます。失敗し得る内部Observableでは `catchError`、または `@ngrx/operators` の `tapResponse` を使って処理を継続させます。 ([NgRx Effects][23], [rxMethod][24])

`retry` はerror時の**再購読**で、成功しない処理を自動的に成功させるものではありません。引数なしの `retry()` は無制限です。書き込みの再実行は重複更新を起こし得るため、回数・待ち時間・対象エラーに加えて冪等性も確認します。 ([RxJS][25])

## Resource系の整理

| API              | 主な用途                                          |
| ---------------- | ------------------------------------------------- |
| `resource()`     | AngularのResourceを作る基本API                    |
| `rxResource()`   | **Observableをデータ源**にしたResource            |
| `httpResource()` | `HttpClient` ベースのHTTP Resource                |
| `debounced()`    | debounceされた値を表す **Resource**。experimental |

`resource` / `debounced` は `@angular/core`、`rxResource` は `@angular/core/rxjs-interop`、`httpResource` は `@angular/common/http` からimportします。`rxResource` に渡すObservableのfactoryは、Angular 22では **`stream` オプション**です。 ([Angular rxResource][6], [RxResourceOptions][26], [httpResource][27], [debounced][28])

`resource()` の通常の `loader` は `PromiseLike<T>` を返しますが、それだけではなく、値またはerrorを表すSignalを返すstreaming loader（`stream` オプション）もサポートしています。`loader` と `stream` は同時には指定できません。したがって、

> `resource = Promise`、`rxResource = Observable`

と完全に二分するのは不正確です。

正しくは、

> **既存ObservableをResourceとして扱いたい → `rxResource()`**

です。`resource` / `rxResource` / `httpResource` はAngular 22でstable、`debounced()` はexperimentalです。 ([Angular resource][7], [rxResource][6], [httpResource][27], [debounced][28])

Resource系は読み取り向けです。`resource()` はパラメータ変更時や破棄時に `abortSignal` へ中断を通知しますが、実際の通信等を中断するにはloader側でそのsignalを `fetch` に渡すなどの対応が必要です。`rxResource()` は以前のObservableの購読を解除し、`httpResource()` は以前のHTTP要求を中断します。POST/PUT等のmutationには `HttpClient` を直接使い、必要な競合制御を組み合わせます。 ([Angular resource][7], [Resourceガイド][29], [rxResource実装][30], [httpResourceガイド][13])

`httpResource()` は既定でHTTP GETを行う、リアクティブな読み取り向けAPIです。リクエスト設定で `method` や `body` も指定できますが、参照パラメータ変更による再実行・中断が起き得るため、mutationには使いません。

状態を読む際は次の契約に注意します。

- ロード状態を読むAPI名は `isLoading()`、結果は `value()`、エラーは `error()` です。
- `resource()` / `rxResource()` / `httpResource()` は `defaultValue` を省略すると、初期値などが `undefined` になり得ます。`defaultValue` は初期状態やparams変更によるloading中に返す値であり、エラー時の代替値ではありません。通常、`reload()` によるreloading時は以前の値を保持します。
- **エラー状態の `value()` は例外を投げます**。`hasValue()` で利用可能な値を確認してから読みます。
- `params` が `undefined` なら読み取りを実行せずidleになります。`rxResource` の `stream` が値を一度も出さずにcompleteすると `NG0991` エラーになります。特に `catchError(() => EMPTY)` で握りつぶすとこの状態になり得ます。 ([Angular Resource][31], [Resourceガイド][29], [RxResourceOptions][26])

Angular 22ではResourceを順に依存させるため、子Resourceの `params` で受け取るコンテキストの `chain()` を使えます。`resource.chain()` というメソッドではありません。

```ts
const child = resource({
  params: ({ chain }) => chain(parentResource),
  loader: ({ params: parent }) => loadChild(parent),
});
```

`chain(parentResource)` は親が `resolved` または `local` のときだけ値を返し、親のloading・idle・errorを子の状態へ伝播します。親の値自体が `undefined` になり得る場合は、値をオブジェクトで包まずparamsとして直接返します。`{ parent: undefined }` は定義済みparamsなので、子のloaderが誤って実行されるためです。 ([Resourceガイド][29])

## `linkedSignal()` の位置

これは `computed()` と分ける必要があります。

```text
computed()
    ↓
元状態から自動的に決まる
    ↓
読み取り専用

linkedSignal()
    ↓
元状態から初期値・再計算値が決まる
    ↓
しかし自分でも set() できる
```

Angular公式も `linkedSignal` を「reactive computationによって初期化・リセットされる writable signal」と定義しています。 ([Angular][8])

NgRx 22ではSignalStoreに **`withLinkedState`** があり、計算関数または `linkedSignal` を返して派生と手動更新を両立できます。依存元変更時に以前の選択を維持したい場合は、`linkedSignal` の `source` / `computation` 形式で `previous` を使い、維持する条件を明示します。 ([NgRx][32])

Signalの `equal` の既定値は `Object.is` で、RxJSの `distinctUntilChanged()` の既定比較は `===` です。いずれもオブジェクトの深い比較ではありません。同じ参照のオブジェクトや配列を直接変更すると変更が伝わらない原因になるため、状態更新では新しい参照を作ります。 ([Angular][33], [RxJS][34])

`computed()` の計算中に例外が発生すると、その例外も計算結果と同様にメモ化されます。依存Signalが更新されて再評価されるまでは、何度読み取っても例外が再throwされます。RxJSのerrorによるストリーム終了とは異なり、依存Signalの変更後の再評価で復旧できます。

## `debounced()` はSignalそのものではない

表ではSignal系の列に置いていますが、

```ts
import { debounced, signal } from "@angular/core";

// コンポーネントやServiceのconstructor等、注入コンテキスト内。
const query = signal("");
const debouncedQuery = debounced(query, 300);

// 値は debouncedQuery() ではなく debouncedQuery.value() で読む。
```

の戻り値は `Signal<string>` ではなく、

```text
Resource<string>
```

です。

ここは分類上「Signalエコシステム」に置いているだけで、`debounceTime` と完全な一対一対応ではありません。待機中も `value()` は直前の確定値を返し、`isLoading()` / `status()` で待機状態を確認できます。experimental APIでもあります。 ([Angular][9])

## `toSignal()` / `toObservable()`

`toSignal()` は作成時に即subscribeします。同じObservableについて何度も `toSignal()` を作るべきではなく、生成したSignalを再利用します。同期emitが保証される `BehaviorSubject` などなら `requireSync: true` を利用できます。 ([Angular][10])

`initialValue` / `requireSync` を指定しない場合、初回emitまでは `undefined` です。`requireSync: true` は同期emitがなければ実行時エラーになります。sourceのerrorはSignalを読む際にthrowされ、sourceのcomplete後は最後の値を保持します。通常は作成時の注入コンテキストの破棄に合わせてunsubscribeされます。 ([Angular][10])

`toObservable()` は少し特殊です。初回値は同期的に通知される場合も、非同期になる場合もあるため、どちらか一方のタイミングに依存する設計は避けます。

```text
subscribe
  ↓
初回値は同期emitの場合も
非同期emitの場合もある

以降
  ↓
Signal変更
  ↓
effect
  ↓
非同期通知
```

そのため、

```text
set(1)
set(2)
set(3)
```

と同一安定化期間内に連続更新すると、途中の1と2ではなく最後の3だけがObservableへ流れます。 ([Angular][10])

イベントを1件ずつ必ず処理したい場合、この変換をイベントキューとして使わず、元のObservableやSubjectから処理します。`rxMethod` はSignalを直接受け取れ、通常のSignal変更に応じてreactive chainを実行します。ただしSignalはObservableやイベントキューと同じ意味で更新履歴を保存するものではありません。同一安定化期間内の連続更新も個別イベントとして必ず処理したい場合は、ObservableやSubjectなどのイベント源を使います。注入コンテキスト内で `store.load(query)` のように接続できます。`store.load(query())` なら、その時点の値を1回渡すだけです。 ([NgRx][24])

## 注入コンテキストと購読の寿命

`toSignal`（既定の自動cleanup使用時）/ `toObservable` / Resource系 / `effect` / `afterRenderEffect` は、通常、コンポーネントやServiceのフィールド初期化・constructor内で作成します。`ngOnInit` やクリックハンドラー自体は注入コンテキストではないため、そこで作成するなら事前に取得した `Injector` を対応するオプションへ渡します。 ([Angular interop][10], [DI][35], [Resource options][36], [Effect][37])

`takeUntilDestroyed()` の引数省略も注入コンテキストが前提です。外側で取得した `DestroyRef` を渡せば、その外でも使用できます。**購読を終えるのは、渡した `DestroyRef` のスコープが破棄された時**です。root Serviceの寿命は呼び出し元コンポーネントの寿命とは異なります。 ([Angular][38])

`rxMethod` にSignalやObservableを接続した購読は、SignalStore等の作成時に使われたInjectorの破棄に合わせてcleanupされます。したがって寿命は呼び出し元ではなく、どのInjectorに紐付いているかで決まります。 ([NgRx][24])

内部Observableも破棄時に解除するには、通常 `switchMap` 等の**後ろ**に置きます。前に置いた場合、sourceのcompleteだけでは内部Observableが終わらないことがあります。

```ts
// 事前に取得した destroyRef を使用する例。
source$
  .pipe(
    switchMap((value) => load$(value)),
    takeUntilDestroyed(destroyRef),
  )
  .subscribe();
```

`switchMap` はsourceがcompleteしても実行中の内部Observableのcompleteを待つため、破棄通知をその後段へ置いて内側を含む購読全体へ適用します。内側で別に寿命を管理する設計も可能です。 ([Angular実装][40], [RxJS実装][18])

## `effect()` と `afterRenderEffect()`

`effect()` はSignal変更に応じて外部副作用を行うためのものですが、**状態Aから状態Bを同期するための代替 `computed()` として使わない**のが基本です。

DOMを直接読む・書く必要がある処理には `afterRenderEffect()` があります。AngularがDOMを更新した**後**に実行され、追跡したSignalが変われば再実行されます。毎回の描画後に無条件で呼ばれるAPIではありません。一度だけの初期化なら `afterNextRender()` を使います。いずれもサーバーでは実行されず、hydrationの完了保証もありません。 ([Angular][11], [Effectガイド][37])

`afterRenderEffect()` は `earlyRead` → `write` → `mixedReadWrite` → `read` の順にphaseを実行します。DOMの書き込みは `write`、読み取りは `read` に分け、読み書きの混在による不要なlayout再計算を避けるのが基本です。effect内で開始したタイマー・購読・イベントリスナー等は自動では片付かないため、`onCleanup` 等に解除処理を登録します。 ([Angular][37])

状態の派生には `computed()`、DOMを必要としない通常の外部副作用には `effect()` を使い、`afterRenderEffect()` はDOMの読み書きが必要な場合に限定します。

## `shareReplay` と `computed()` は対応させない

「共有・memoize」という印象が似ているだけで、両者の契約は異なります。

```text
shareReplay
  = Observable購読・上流処理を共有し
    過去のemitを後続subscriberへreplay

computed
  = Signal依存計算をlazyに評価しmemoize
```

`computed()` がmemoizedだからといって、`shareReplay` のSignal版ではありません。RxJS公式も `shareReplay` をReplaySubjectによるmulticast/replayとして定義しています。 ([RxJS][12])

RxJS 7.8.xの `shareReplay()` は既定でバッファ数が無制限、`refCount: false` です。`shareReplay(1)` でも `refCount` はfalseなので、購読者が0人になっても未完了の上流購読が残ります。購読者がいなくなったら未完了の上流も止めたい場合は、`shareReplay({ bufferSize: 1, refCount: true })` を使います。ただし、その後の再購読は上流処理を再実行します。 ([RxJS][12])

**成功してcompleteした値のキャッシュは `refCount: true` でも残ります**。`shareReplay` 自体はTTL、手動invalidate、stale-while-revalidate等を提供するキャッシュ機構ではありません。必要なら `share` のreset設定、Observableの再生成、Store、専用キャッシュ層等を組み合わせます。また、メソッド呼び出しごとに `http.get(...).pipe(shareReplay(...))` を作り直すと、呼び出し間では共有されません。同じ共有Observableを保持して再利用します。 ([RxJS][12])

## 最後に覚える判断軸

最初はここから逆引きするのが良いです。

| 問題                                             | まず考えるもの                                                                                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「今の値」は何か                                 | [`signal()`](#signal-angular) / [`Store`](#store-ngrx) / [`SignalStore`](#signalstore-ngrx)                                                                    |
| 「今の値」から何を計算するか                     | [`computed()`](#computed-angular) / [`Selector`](#selector-ngrx)                                                                                               |
| 時間とともに通知が複数流れる                     | RxJS                                                                                                                                                           |
| 非同期処理が重なったらどうするか                 | [`switchMap()`](#switchmap-pipe) / [`mergeMap()`](#mergemap-pipe) / [`concatMap()`](#concatmap-pipe) / [`exhaustMap()`](#exhaustmap-pipe)（すべて **[pipe]**） |
| Actionを中心に状態遷移を管理したい               | [`NgRx Store`](#store-ngrx) + [`Effects`](#effects-ngrx)                                                                                                       |
| Signalベースで構造化した状態管理が欲しい         | [`NgRx SignalStore`](#signalstore-ngrx)                                                                                                                        |
| reactiveな読み取り + loading/value/errorが欲しい | [`Resource系`](#resource-angular)                                                                                                                              |
| Observable世界とSignal世界を接続したい           | [`toSignal()`](#tosignal-angular) / [`toObservable()`](#toobservable-angular) / [`rxResource()`](#rxresource-angular)                                          |

つまり最上位では、

**Signal系 = 現在値と依存関係**

**RxJS = 時間軸上の通知・非同期処理の合成と競合制御**

**NgRx Store = Actionを軸とするアプリ状態管理**

**NgRx SignalStore = Signalを軸とする構造化された状態管理**

この4つは排他的な選択肢ではありません。例えばSignalStoreで現在状態を持ち、`rxMethod` とRxJSで非同期競合を制御するなど、責務に応じて組み合わせます。SignalStoreもEvents pluginによるイベント駆動を選べます。 ([NgRx][24], [Events][39])

## RxJS関数・operatorの基本的な使い方

以下の `source$` は処理元のObservable、`a$` / `b$` は合流するObservableを表します。変数名末尾の `$` はObservableであることを表す慣例です。`[func]` は関数として呼び出し、`[pipe]` は `source$.pipe(...)` 内で使います。

<a id="behaviorsubject-rxjs"></a>

### RxJS: `BehaviorSubject` [Subject]

`BehaviorSubject` は必ず初期値を持ち、現在値を保持するObservableです。購読を始めると、その時点の最新値がすぐ1件流れ、以後は `next()` で更新するたびに全subscriberへ新しい値が流れます。Service内で小規模な共有状態を持つ場合に使えますが、外部には `asObservable()` で公開し、型として `next()` を隠します。

```ts
@Injectable({ providedIn: "root" })
export class CounterService {
  private readonly countSubject = new BehaviorSubject(0);
  readonly count$ = this.countSubject.asObservable();

  increment(): void {
    this.countSubject.next(this.countSubject.value + 1);
  }
}
```

値を同期的に読むには `.value` または `getValue()` を使えます。ただしerror後はどちらもthrowし、complete後の新規subscriberは保持値を受け取らず即completeします。コンポーネント内だけの単純な現在値ならAngularの `signal()` の方が簡潔で、状態遷移や派生状態が増えるならStoreやSignalStoreも検討します。

<a id="map-pipe"></a>

### RxJS: `map()` [pipe]

sourceが通知する値を1件ずつ別の値へ変換します。配列の `map` と似ていますが、Observableから届く将来の通知それぞれに処理が行われます。ObservableやPromiseを返しても自動では購読・待機・平坦化されないため、非同期処理には `switchMap` 等を使います。変換関数がthrowすればストリームはerrorで終了します。

```ts
const priceWithTax$ = price$.pipe(map((price) => Math.floor(price * 1.1)));
```

<a id="combinelatest-func"></a>

### RxJS: `combineLatest()` [func]

複数Observableの最新値を組み合わせて受け取ります。すべての入力が少なくとも1回通知した後、いずれかが通知するたびに最新値を流します。入力の1つが一度もemitせずcompleteすると、全体も値を出さずcompleteします。1つがerrorになれば全体もerrorになります。

```ts
combineLatest([a$, b$]).subscribe(([a, b]) => {
  // a と b はそれぞれの最新値
});
```

<a id="combinelatestwith-pipe"></a>

### RxJS: `combineLatestWith()` [pipe]

sourceに他のObservableの最新値を加えるpipe operatorです。動作は `combineLatest` と同じで、全入力の初回通知が揃うまでは何も流れません。初回emit前に入力がcompleteした場合やerror時の契約も `combineLatest` と同じです。既に `source$.pipe(...)` と書いている処理へ追加したい場合に読みやすくなります。

```ts
a$.pipe(combineLatestWith(b$)).subscribe(([a, b]) => {
  // a$ または b$ が通知するたび、両方の最新値を受け取る
});
```

<a id="forkjoin-func"></a>

### RxJS: `forkJoin()` [func]

複数処理すべての完了を待ち、各入力の最後の値をまとめて1回だけ流します。購読時に全入力を購読するため、複数のHTTP GETを並行実行し、全部揃ってから画面を作る用途に向きます。完了しないObservableがあると結果も出ません。1つでも値なしでcompleteすれば全体も値なしでcompleteし、1つでもerrorになれば全体もerrorとなって他の入力からunsubscribeします。個別の失敗も集めるなら各入力の内側で `catchError` を使います。

```ts
forkJoin({ user: user$, posts: posts$ }).subscribe(({ user, posts }) => {
  // 両方が完了した時点で一度だけ実行
});
```

<a id="zip-func"></a>

### RxJS: `zip()` [func]

各Observableの1件目同士、2件目同士というように、同じ順番の値を組にします。片方だけ先に何件届いても、相手側の対応する値が来るまで待ちます。速い側の未対応値は内部に保持されるため、通知頻度の差が長く続く無限ストリーム同士には向きません。「常に最新値」ではなく「対応する順番」が重要な場合に使います。いずれかの入力がcompleteし、その入力に未使用の値がなくなると、以後は組を作れないため全体もcompleteします。

<a id="zipwith-pipe"></a>

### RxJS: `zipWith()` [pipe]

sourceと他のObservableを順番ごとに組にするpipe operatorです。`a$.pipe(zipWith(b$))` は、`zip(a$, b$)` と同様に `[aの1件目, bの1件目]`、`[aの2件目, bの2件目]` と流します。

<a id="merge-func"></a>

### RxJS: `merge()` [func]

複数Observableの値を組にせず、到着した順に1本へ流します。クリックとキー操作を同じ「ユーザー操作」として処理する場合など、入力元を区別せず同じ処理へ合流させたいときに使います。入力の型が異なる場合も合流できますが、出力はそれらのunion型になるため、必要なら合流前に `map` で共通の型へ揃えます。

```ts
merge(click$, keydown$).subscribe((event) => handleInput(event));
```

<a id="mergewith-pipe"></a>

### RxJS: `mergeWith()` [pipe]

sourceへ他のObservableの通知を到着順に合流するpipe operatorです。`a$.pipe(mergeWith(b$))` は値を配列にせず、`a$` と `b$` の通知をそのまま1本のObservableへ流します。

<a id="concat-func"></a>

### RxJS: `concat()` [func]

Observableを指定順につなぎます。最初のObservableが完了してから次を購読するため、最初が完了しなければ次は始まりません。前のObservableがerrorになると後続には進みません。複数の既存Observableを順番に実行したい場合に使います。

```ts
concat(first$, second$).subscribe(); // first$ 完了後に second$ を購読
```

<a id="concatwith-pipe"></a>

### RxJS: `concatWith()` [pipe]

sourceの完了後に別のObservableへつなぐpipe operatorです。`first$.pipe(concatWith(second$))` と書くと、先に `first$` の全通知、その後に `second$` の通知が流れます。

<a id="withlatestfrom-pipe"></a>

### RxJS: `withLatestFrom()` [pipe]

sourceの通知だけを処理のきっかけにし、その時点における他のObservableの最新値を添えます。参照先だけが更新されても通知しない点が `combineLatest` との違いです。参照先がまだ一度も通知していない間に来たsourceの値は出力されません。

```ts
saveClick$.pipe(withLatestFrom(formValue$)).subscribe(([event, formValue]) => {
  // クリック時点のフォーム値で保存する
});
```

<a id="concatlatestfrom-pipe"></a>

### NgRx: `concatLatestFrom()` [pipe]

NgRx Effectで、Actionが来た時点に参照先factoryを評価し、その最新値をActionへ添えます。常時購読する `withLatestFrom` と違い、selectorにActionの値を渡して参照先を決められます。参照先は購読時に同期的に値を出せるStore selectorなどを使います。同期emitしない参照先を待つoperatorではなく、そのActionが出力されないため、HTTPの完了待ちには使いません。import元の `@ngrx/operators` は別packageなので、利用するNgRxと同じmajor版を別途導入します。

```ts
actions$.pipe(
  ofType(PageActions.opened),
  concatLatestFrom(() => store.select(selectCurrentUser)),
  // [action, user] を後段で受け取る
);
```

<a id="switchmap-pipe"></a>

### RxJS: `switchMap()` [pipe]

sourceの値ごとに内部Observableを作り、新しい値が来ると以前の内部Observableの購読を解除して最新へ切り替えます。検索条件や画面IDが変わったとき、古い結果を採用したくない読み取り処理に向きます。購読解除済みの処理結果は後段へ流れませんが、サーバーですでに始まった更新の取消しやロールバックは保証しないため、POST/PUT等では安易に使いません。

```ts
const results$ = query$.pipe(switchMap((query) => search$(query)));
```

<a id="mergemap-pipe"></a>

### RxJS: `mergeMap()` [pipe]

sourceの値ごとに作った内部Observableを並行して購読します。どの処理も取り消したくない一方、完了順が入力順と異なってよい場合に向きます。必要なら第2引数で同時実行数を制限します。長時間完了しない内部Observableを無制限に増やさないようにします。いずれかの内部Observableのerrorを未処理にすると全体がerrorになります。

```ts
items$.pipe(mergeMap((item) => saveItem$(item), 3)); // 最大3件を並行処理
```

<a id="concatmap-pipe"></a>

### RxJS: `concatMap()` [pipe]

sourceの値を待ち行列に入れ、1件の内部Observableが完了してから次を開始します。保存順序を守りたい処理に向きますが、内部処理が完了しないと次へ進まず、入力が多いと待ち行列が増えます。

```ts
saveRequests$.pipe(concatMap((request) => save$(request)));
```

<a id="exhaustmap-pipe"></a>

### RxJS: `exhaustMap()` [pipe]

内部Observableの実行中に来た後続のsource通知を捨てます。送信ボタンの連打を無視する用途など、「実行中の1件を最後まで優先し、後続を予約もしない」場合に使います。内部Observableが完了しなければ以後の入力を永久に無視します。処理完了後の新しい通知は再び受け付けます。ただし抑制できるのは同じsource Observableの同一購読内だけで、サーバー側の重複防止には冪等キー等を別途用意します。内部errorを未処理のままにすると全体が終了し、以後の入力を受け取れません。

```ts
submitClick$.pipe(exhaustMap(() => submitForm$()));
```

<a id="debouncetime-pipe"></a>

### RxJS: `debounceTime()` [pipe]

通知後、指定時間だけ次の通知が来なければその値を流します。待機中に次が来るたびタイマーをやり直すため、文字入力が止まってから検索する用途に向きます。すべての値を残したい処理には使いません。

<a id="throttletime-pipe"></a>

### RxJS: `throttleTime()` [pipe]

最初の通知を流した後、指定時間内の後続通知を抑制します。スクロールやマウス移動のような高頻度イベントを一定間隔に抑える用途に向きます。既定では期間末尾の値は流れません。末尾も必要なら第3引数のconfigへ `{ leading: true, trailing: true }` を渡します（第2引数はschedulerです）。

```ts
import { asyncScheduler, throttleTime } from "rxjs";

source$.pipe(
  throttleTime(300, asyncScheduler, { leading: true, trailing: true }),
);
```

<a id="scan-pipe"></a>

### RxJS: `scan()` [pipe]

前回までの計算結果と今回の通知値から次の状態を作り、通知のたびに途中結果を流します。配列の `reduce` と似ていますが、完了時に一度だけではなく各段階を受け取れます。

```ts
const total$ = value$.pipe(scan((total, value) => total + value, 0));
```

<a id="startwith-pipe"></a>

### RxJS: `startWith()` [pipe]

購読されるたび、sourceより先に指定値を同期的に流します。初回値がないObservableを `combineLatest` へ渡す場合や、画面に初期表示用の値をすぐ出したい場合に使います。sourceの内部状態を書き換えるものではありません。

<a id="filter-pipe"></a>

### RxJS: `filter()` [pipe]

条件が `true` になった通知だけを後段へ通し、それ以外を捨てます。値が条件を満たすまで待って後から復活させる処理ではありません。TypeScriptの型ガードをpredicateにすると、後段の型も絞り込めます。

```ts
const users$ = nullableUser$.pipe(
  filter((user): user is User => user !== null),
);
```

<a id="distinctuntilchanged-pipe"></a>

### RxJS: `distinctUntilChanged()` [pipe]

直前に流した値と今回値を比較し、同じなら今回値を捨てます。既定比較は `===` なので、内容が同じ別オブジェクトは異なる値として流れます。必要な場合だけ比較関数を渡します。

<a id="take1-pipe"></a>

### RxJS: `take(1)` [pipe]

最初の1件を流した直後に購読を完了します。sourceが1件も出さず完了した場合も正常完了するため、「値がなくてもよい1回取得」に向きます。sourceが通知も完了もしなければ待ち続けます。

<a id="first-firstpredicate-pipe"></a>

### RxJS: `first()` / `first(predicate)` [pipe]

`first()` は最初の値、`first(predicate)` は条件に合う最初の値を流して完了します。該当値なしでsourceが完了すると、default値を指定していない限りerrorになるため、「条件を満たす値が必ず必要」という契約を表せます。

<a id="catcherror-pipe"></a>

### RxJS: `catchError()` [pipe]

上流で発生したerrorを受け取り、返したObservableへ処理を切り替えます。代替値を流す、失敗Actionへ変換する、処理を終える、別のerrorを投げ直す、といった回復方針をここで決めます。Effectなど継続利用する外側のストリームを終了させないよう、通常は失敗し得る内部Observableに置きます。

```ts
request$.pipe(catchError((error) => of({ kind: "failed", error })));
```

<a id="retry-pipe"></a>

### RxJS: `retry()` [pipe]

errorが起きたとき上流を最初から購読し直します。`count: 2` は初回に加えて最大2回再試行する意味です。上流にある `tap` 等の副作用も再実行されます。書き込み処理は重複実行の危険があるため、回数・待機時間・再試行対象とAPIの冪等性を確認します。

<a id="sharereplay-pipe"></a>

### RxJS: `shareReplay()` [pipe]

同じObservableを複数箇所から購読したときに上流購読を共有し、保持した直近値を後から来たsubscriberにも再生します。HTTP結果などを共有したい場合は、生成した共有Observable自体をフィールド等に保持して再利用します。購読者が0人なら未完了の上流も解除したい場合は `refCount: true` を明示します。

```ts
readonly user$ = this.http.get<User>("/api/user").pipe(
  shareReplay({ bufferSize: 1, refCount: true }),
);
```

`refCount: true` でも、HTTPのように成功してcompleteした結果のキャッシュは残ります。未完了の上流はsubscriberが0になると解除され、後の購読で再実行されます。errorは保持されず、後の購読で上流へ再購読します。

<a id="takeuntildestroyed-pipe"></a>

### Angular/RxJS interop: `takeUntilDestroyed()` [pipe]

AngularのコンポーネントやDirectiveなど、指定した `DestroyRef` のスコープが破棄されたときに購読を完了します。手動subscribeをライフサイクルへ結び付けるために使います。注入コンテキスト内なら引数を省略でき、その場所の `DestroyRef` が使われます。`switchMap` 等の内部Observableも破棄時に解除したい場合は、通常それらより後ろへ置きます。

<a id="tap-pipe"></a>

### RxJS: `tap()` [pipe]

通知値を変更せず、ログ、計測、デバッグなどの副作用を差し込みます。値の変換には `map`、非同期処理の合成には各種 `*Map` を使います。`tap` 内でObservableを返しても購読・合成されず、そこで別途 `subscribe()` すると購読の寿命とerror処理が分断されるため避けます。callbackがthrowすればストリームはerrorになります。

```ts
source$.pipe(
  tap((value) => console.debug("received", value)),
  map((value) => transform(value)),
);
```

## NgRx（Store / SignalStore）の基本的な使い方

NgRx StoreとSignalStoreはどちらも共有状態を構造化しますが、操作の入口が異なります。StoreはActionをdispatchしてReducerで状態を変え、SignalStoreは公開メソッドから `patchState` する構成を基本にできます。アプリ全体で必ずどちらか一方に統一する必要はありません。

<a id="store-ngrx"></a>

### NgRx Store: `Store`

Storeはアプリケーション状態を保持し、`dispatch` で変更要求を送り、selectorで現在値や派生値を読みます。コンポーネントは「どう変更するか」ではなく「何が起きたか」をActionとして通知するため、状態遷移を追跡しやすくなります。

```ts
readonly users = this.store.selectSignal(selectUsers);

reload(): void {
  this.store.dispatch(UsersPageActions.reload());
}
```

<a id="action-reducer-ngrx"></a>

### NgRx Store: `Action → Reducer`

Actionはユーザー操作やAPI完了などの出来事を表す値です。Reducerは現在stateとActionから次stateを同期的かつ純粋に計算します。Reducer内でHTTP、Router、時刻取得などの副作用は実行せず、それらはEffectsへ分離します。

```ts
export const usersReducer = createReducer(
  initialState,
  on(UsersApiActions.loaded, (state, { users }) => ({
    ...state,
    users,
    loading: false,
  })),
);
```

<a id="selector-ngrx"></a>

### NgRx Store: `Selector` / `createSelector()`

SelectorはStoreから必要な状態を読み取り、派生値を計算する純粋関数です。複数stateから表示用データを作る処理はコンポーネントへ散らさず、`createSelector` で再利用します。Signalとして読みたい場合は `store.selectSignal(selector)`、Observableとして読みたい場合は `store.select(selector)` を使います。

```ts
export const selectVisibleUsers = createSelector(
  selectUsers,
  selectSearchText,
  (users, searchText) => users.filter((user) => user.name.includes(searchText)),
);
```

<a id="effects-ngrx"></a>

### NgRx Store: `Effects`

EffectsはActionを受けてHTTPやRouterなどの副作用を実行します。HTTP等では通常、結果を成功・失敗ActionとしてStoreへ戻しますが、Router遷移、ログ、通知などActionを返さない処理では `{ dispatch: false }` を指定します。状態を直接書き換える場所ではありません。非同期競合は用途に合う `switchMap` / `concatMap` / `mergeMap` / `exhaustMap` で明示します。

```ts
readonly loadUsers$ = createEffect(() => this.actions$.pipe(
  ofType(UsersPageActions.reload),
  switchMap(() => this.api.getUsers().pipe(
    map((users) => UsersApiActions.loaded({ users })),
    catchError((error) => of(UsersApiActions.loadFailed({ error }))),
  )),
));
```

class fieldで定義する場合、`createEffect` が参照する `actions$` やServiceはEffect fieldより前に初期化します。外側の `actions$.pipe(...)` に `catchError` や `take(1)` を置いて完了させると以後のActionを処理できないため、通常は上例のように内部Observableで処理します。

<a id="signalstore-ngrx"></a>

### NgRx SignalStore: `signalStore()` とprovider範囲

`signalStore()` は `withState`、`withComputed`、`withMethods` などのfeatureを組み合わせ、注入可能なStoreを定義します。`{ providedIn: "root" }` を指定するとアプリ全体で同じinstanceを共有し、コンポーネントの `providers` に置くと、そのコンポーネント配下だけで共有するinstanceになります。共有範囲は「SignalStoreだからroot」ではなく、providerを置く場所で決まります。

```ts
export const CounterStore = signalStore(
  { providedIn: "root" },
  withState({ count: 0 }),
);

// コンポーネントやServiceから利用する
readonly counterStore = inject(CounterStore);
```

画面を離れたときに状態を捨てたいなら、その画面のコンポーネントやRoute providerで提供します。ログインユーザー情報などアプリ全体で共有したい状態ならroot提供を検討します。

<a id="withstate-signalstore"></a>

### NgRx SignalStore: `withState()`

`withState` はSignalStoreが保持する初期状態を定義します。各プロパティはSignalとして公開されるため、利用側は `store.users()` のように現在値を同期的に読めます。SignalStoreのstateは既定で保護され、Store外から `patchState(store, ...)` できません。外部更新を許す `{ protectedState: false }` もありますが、通常は `withMethods` で公開した操作へ更新を集約します。

<a id="withmethods-signalstore"></a>

### NgRx SignalStore: `withMethods()` / `patchState()`

`withMethods` は状態を変更する公開操作を定義します。`patchState` には変更部分または現在stateから変更部分を作る関数を渡します。配列やオブジェクトは直接変更せず、新しい参照を返します。

```ts
export const CounterStore = signalStore(
  withState({ count: 0 }),
  withMethods((store) => ({
    increment: () => patchState(store, ({ count }) => ({ count: count + 1 })),
  })),
);
```

<a id="withcomputed-signalstore"></a>

### NgRx SignalStore: `withComputed()`

`withComputed` はStore内のstate Signalから読み取り専用の派生Signalを定義します。元状態が変わると必要時に再計算されるため、同じ表示用計算を各コンポーネントで繰り返さずに済みます。派生値を更新する専用メソッドは作らず、元状態を更新します。

```ts
withComputed(({ firstName, lastName }) => ({
  fullName: computed(() => `${firstName()} ${lastName()}`),
}));
```

<a id="withlinkedstate-signalstore"></a>

### NgRx SignalStore: `withLinkedState()`

`withLinkedState` は別のstateから初期化・再計算されつつ、Store内では `patchState` で手動更新もできるstate sliceを追加します。公開されるsliceは通常のstateと同じ `DeepSignal` であり、利用側が直接 `.set()` するものではありません。候補一覧が変わったら既定選択へ戻す一方、ユーザー自身も選択を変えられる、といった「派生する書き込み可能状態」に使います。常に元状態だけから決まる値なら `withComputed` を選びます。 ([NgRx][32])

```ts
export const OptionsStore = signalStore(
  withState({ options: [] as Option[] }),
  withLinkedState(({ options }) => ({
    selectedOption: () => options()[0] ?? undefined,
  })),
  withMethods((store) => ({
    select: (selectedOption: Option) => patchState(store, { selectedOption }),
  })),
);
```

<a id="rxmethod-signalstore"></a>

### NgRx SignalStore: `rxMethod()`

`rxMethod` はメソッド入力をRxJS pipelineへ接続し、debounce、HTTP、競合制御などをSignalStore内へまとめます。値を1回渡すことも、SignalやObservableを接続して変更のたびに実行することもできます。`rxMethod` は `@ngrx/signals/rxjs-interop`、`tapResponse` は別packageの `@ngrx/operators` からimportします。継続利用するため、errorは通常、内部Observableの `catchError` または `tapResponse` で処理します。

```ts
loadByQuery: rxMethod<string>(
  pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap((query) =>
      api.search(query).pipe(
        tapResponse({
          next: (users) => patchState(store, { users }),
          error: (error) => patchState(store, { error }),
        }),
      ),
    ),
  ),
);
```

上例のように内部Observableへ置いた `tapResponse` は `next` / `error` / `complete` / `finalize` の処理を分け、errorを捕捉して接続元の `rxMethod` を終了させません。SignalやObservableの接続は呼出元の注入コンテキスト（または第2引数の `injector`）の破棄時に解除されます。root提供のStoreから画面固有のSignal等を接続するなら、画面の注入コンテキスト内で呼ぶかその `injector` を渡します。戻り値の `destroy()` はその接続だけ、`rxMethod` 自体の `destroy()` はpipeline全体を終了します。

<a id="events-signalstore"></a>

### NgRx SignalStore: Events plugin / `withReducer()` / `withEventHandlers()`

Events pluginはSignalStoreでも出来事をeventとして明示し、ReducerやEffectに似たイベント駆動を選べる仕組みです。`withReducer` はeventに対する同期的な状態遷移、`withEventHandlers` はeventを受けた外部処理や別eventの返却に使います。単純な状態変更は `withMethods` で十分ですが、複数機能が同じ出来事へ反応する場合や、状態変更の理由を明確にしたい場合に有効です。handlerの未処理errorは購読を終了させるため、HTTP等の失敗は内部Observableでeventへ変換します。NgRx 21以降では旧名 `withEffects` ではなく `withEventHandlers` を使います。 ([Events][39])

## Angular Signal系の基本的な使い方

Signalは「現在値」を同期的に読み、依存関係に応じて派生値や副作用を更新する仕組みです。イベントをすべて順番に保存するキューではないため、各通知を落とさず処理する必要がある場合はObservableを使います。

`resource` 系、`debounced`、`toSignal` / `toObservable`、`effect` 系は通常、生成時の注入コンテキストと寿命を共有します。その外で生成する場合は各APIの `injector` オプションを渡し、どのスコープで破棄するかを明示します。

<a id="shared-service-state-angular"></a>

### Angular: `Service + signal()` による共有状態

複数コンポーネントでSignal状態を共有するには、Serviceのprivateな書き込み可能Signalと、公開する読み取り専用Signalを組み合わせます。`asReadonly()` は型として書き込みAPIを隠す仕組みなので、元の書き込み可能Signal自体を外部へ漏らさないことが前提です。状態変更はService methodへ集約すると、変更ルールを1か所に保てます。

```ts
@Injectable({ providedIn: "root" })
export class CounterService {
  private readonly countState = signal(0);
  readonly count = this.countState.asReadonly();

  increment(): void {
    this.countState.update((count) => count + 1);
  }
}
```

`providedIn: "root"` ならアプリ全体で同じService instanceを共有します。コンポーネントの `providers` にServiceを置けば、そのコンポーネント配下ごとに別instanceとなり、破棄時には状態も破棄されます。小規模な共有状態には簡潔ですが、Action履歴、複雑な状態遷移、開発ツールによる追跡が必要ならNgRxも検討します。

<a id="signal-angular"></a>

### Angular: `signal()` / `set()` / `update()`

`signal(initialValue)` は現在値を持つ書き込み可能Signalを作ります。値は `count()` のように読み、値を置き換えるなら `set`、現在値から次の値を作るなら `update` を使います。テンプレートからも `count()` として読み取れます。

```ts
const count = signal(0);

count.set(10);
count.update((current) => current + 1);
console.log(count()); // 11
```

<a id="computed-angular"></a>

### Angular: `computed()`

`computed` は他のSignalから読み取り専用の派生値を作ります。計算中に実際に読んだSignalが依存元になるため、条件分岐で読まなかったSignalはその実行時の依存にはなりません。依存値が変わった後、次に必要になった時点で再計算されます。計算は純粋に保ち、副作用を置きません。派生値を `effect` で別Signalへコピーするのではなく、まず `computed` で表せないか考えます。

```ts
const firstName = signal("Taro");
const lastName = signal("Yamada");
const fullName = computed(() => `${firstName()} ${lastName()}`);
```

<a id="signal-equality-angular"></a>

### Angular: Signalの`equal`オプション

Signalは更新前後を比較し、同じと判断した値では依存先へ変更を通知しません。`signal()` と `computed()` の既定比較は `Object.is` なので、オブジェクトや配列は通常、参照が変われば別の値として扱われます。内容に基づいて同一判定したい場合だけ `equal` 関数を指定します。

```ts
const selectedUser = signal<User | null>(null, {
  equal: (previous, current) => previous?.id === current?.id,
});
```

この例では同じIDのユーザーを設定しても通知されないため、名前など他のプロパティ変更も無視されます。不要な再計算を減らす利点と、必要な更新まで止める危険を比較して使います。また、同じオブジェクトを直接変更して同じ参照を再設定するのではなく、新しいオブジェクトや配列を作るのが基本です。

<a id="linkedsignal-angular"></a>

### Angular: `linkedSignal()`

`linkedSignal` は依存元から値を計算しつつ、利用側からも `set` / `update` できるSignalです。商品一覧が変われば先頭商品を選び直す一方、ユーザーも選択商品を変更できる場合などに使います。通常の `set` はlinkedSignal自身だけを更新し、依存元へ逆反映しません。Angular 22の `set` オプションを使えば、書き込みを依存元へ明示的に転送できます。手動変更が不要な純粋な派生値なら `computed` の方が適切です。 ([Angular][8])

```ts
const options = signal(["standard", "express"]);
const selected = linkedSignal(() => options()[0]);

selected.set("express"); // ユーザーによる上書きも可能
```

依存元が変わっても有効な選択を維持したい場合は、`{ source, computation }` 形式の `previous?.value` を使います。

<a id="resource-angular"></a>

### Angular: `resource()`

`resource` はSignalで表したparamsに応じて非同期の読み取りを実行し、結果・loading・errorをひとまとまりで管理します。`value()`、`isLoading()`、`error()`、`hasValue()` で状態を読みます。error状態の `value()` はthrowするため、テンプレート等では `hasValue()` でguardします。paramsが `undefined` ならidleとなり、paramsが変わると以前の読み取りへ中断が通知され、新しい読み取りが始まります。params変更による `loading` では以前の値を保持せず、`defaultValue` を省略していれば `value()` は `undefined` になります。同じparamsを `.reload()` した `reloading` では以前の値を保持します。

```ts
const userId = signal<string | undefined>(undefined);
const user = resource({
  params: () => userId(),
  loader: ({ params, abortSignal }) => fetchUser(params, abortSignal),
});
```

`abortSignal` は中断を通知するだけなので、実処理を止めるには `fetch(url, { signal: abortSignal })` のようにloader側のAPIへ渡します。`ResourceRef` の `.set()` / `.update()` でローカル値を設定するとstatusは `local` になりますが、Resourceは読み取り用であり、mutationの完了管理、楽観的更新、ロールバックの代替にはしません。

SSR結果をhydration時に再利用するには一意な `id` を指定します。値はHTMLへserializeされるため、HTMLが共有cacheされ得る画面のユーザー固有データでは `id` による再利用を避けます。 ([Angular][29])

<a id="resource-chain-angular"></a>

### Angular Resource: `params`の`chain()`

先行Resourceの結果が必要な読み取りでは、子Resourceの `params` が受け取るcontextから `chain(parentResource)` を呼びます。親が `resolved` / `local` なら値を返し、親のloading・reloading・idle・errorは子Resourceにも伝播してloaderを実行しません。`parentResource.value()` を直接読むより、親の状態を正しく子Resourceへ反映できます。

```ts
const orders = resource({
  params: ({ chain }) => chain(userResource),
  loader: ({ params: user }) => ordersApi.findByUser(user.id),
});
```

`chain()` はResource自身のmethodではなく、`params` のcontextから受け取る関数です。親の値自体が `undefined` になり得る場合、`chain(userResource)` を直接返せば子はidleになりますが、`{ user: chain(userResource) }` と包むとparamsは定義済みになりloaderが実行されます。複数の親をまとめる場合も、この `undefined` の扱いを明示してからオブジェクトを作ります。

<a id="rxresource-angular"></a>

### Angular/RxJS interop: `rxResource()`

`rxResource` はloaderの代わりにObservableを返す `stream` を使うResourceです。既存のRxJSベースServiceを使いながら、利用側では `value()` や `isLoading()` などResource共通の読み方をしたい場合に向きます。params変更時には以前のstreamからunsubscribeします。streamが1件も値を出さずcompleteすると `NG0991` になるため、`catchError(() => EMPTY)` で握りつぶしません。fallback値を返すとresolved扱いになって元のerrorが見えなくなる点にも注意します。 ([Angular NG0991][41])

```ts
const user = rxResource({
  params: () => userId(),
  stream: ({ params }) => usersApi.getById(params),
});
```

<a id="httpresource-angular"></a>

### Angular HTTP: `httpResource()`

`httpResource` はHttpClientベースの読み取りをResourceとして扱います。URL、headers、query parameters等をSignalから組み立てると、依存値の変更時に再取得され、以前の要求は中断されます。HttpClientのInterceptorも適用されます。自動再実行され得るため、状態変更を伴うmutationには使わず、主にGET等の読み取りへ使います。 ([httpResourceガイド][13])

```ts
const userId = signal("42");
const user = httpResource<User>(() => `/api/users/${userId()}`);
```

返される `HttpResourceRef` はResource共通のSignalに加えて `headers()` / `statusCode()` / `progress()` を持ちます。`<User>` はTypeScript上の型指定で実行時検証はしないため、外部応答を検証する場合は `parse` オプションを使います。Interceptorがerrorを `EMPTY` 等へ変えて応答なしでcompleteさせると `NG0991` になり得るため、errorを無通知で握りつぶしません。 ([Angular NG0991][41])

<a id="debounced-angular"></a>

### Angular: `debounced()`

`debounced(source, duration)` はsource Signalの変更が指定時間止まってから値を確定するResourceを返します。通常のSignalではないため、値は `result.value()`、待機中かどうかは `result.isLoading()` で読みます。待機中の `value()` は直前に確定した値を保持します。sourceの読み取りがthrowした場合は待機せずerror状態になります。Angular 22ではexperimentalなので、採用時は変更可能性を考慮します。

<a id="tosignal-angular"></a>

### Angular/RxJS interop: `toSignal()`

`toSignal` はObservableを購読し、その最新値をSignalとして公開します。作成時に即subscribeするため、同じObservableから何度も作らず、作成したSignalを再利用します。同期初期値がないObservableでは `initialValue` を指定するか、初回通知まで `undefined` になり得る型として扱います。`BehaviorSubject` 等の同期emitが契約なら `requireSync: true` を使えますが、`initialValue` とは同時指定できません。ObservableがerrorになるとSignalの読み取り時にthrowし、complete後は最後の値を保持します。購読は既定で作成元の注入コンテキストの破棄時に解除されます。

```ts
readonly user = toSignal(this.user$, { initialValue: null });
```

<a id="toobservable-angular"></a>

### Angular/RxJS interop: `toObservable()`

`toObservable` はSignalの現在値と以後の変更をObservableとして扱えるようにします。RxJS operatorでdebounceや非同期処理を組みたい場合に便利です。初回通知は同期・非同期のどちらもあり得るため、そのタイミングへ依存しないようにします。またSignalの連続更新は安定化後の最後の値だけが流れることがあるため、イベント履歴の配送には使いません。通常は注入コンテキスト内で作成し、外で作る場合は `injector` を指定します。

```ts
const query$ = toObservable(query).pipe(
  debounceTime(300),
  distinctUntilChanged(),
);
```

<a id="effect-angular"></a>

### Angular: `effect()`

`effect` は少なくとも1回実行され、実行中に読んだSignalを追跡して値の変化時に再実行します。Component Effectは対応componentの変更検知lifecycleで、root提供Service等のRoot Effectはmicrotaskとして実行されるため、同期実行を前提にしません。ログ、localStorage、外部ライブラリなど、Signalではない仕組みへ現在状態を反映する用途に使います。依存追跡は同期処理中のreadだけなので、`await` 後に初めて読んだSignalは依存になりません。派生状態は `computed`、手動更新できる派生状態は `linkedSignal` を優先します。effect内で依存Signalを書き換えると循環更新を起こし得るため、状態遷移はmethod等へ寄せ、依存にしたくない付随的なreadだけ `untracked` を使います。非同期処理は前回分を自動取消しないため、タイマーや購読等は `onCleanup` で後片付けします。SSRでも実行され得るため、`window` や `localStorage` はブラウザ環境を確認して使います。

```ts
effect((onCleanup) => {
  const value = draft();
  const timerId = setTimeout(() => saveDraft(value), 500);
  onCleanup(() => clearTimeout(timerId));
});
```

<a id="afterrendereffect-angular"></a>

### Angular: `afterRenderEffect()` / `afterNextRender()`

`afterRenderEffect` はAngularがDOMを更新した後に、依存Signalの変更へ反応してDOMの読み書きを行います。ChartやCanvasの更新、要素サイズの計測など、描画済みDOMが必要な処理に限定します。phaseは `earlyRead` → `write` → `mixedReadWrite` → `read` の順で、DOMの書き込みと読み取りを分けて不要なlayout再計算を避けます。phaseを省略すると `mixedReadWrite` になるため、可能なら `write` と `read` を明示して分離します。一度だけ描画後に初期化するなら `afterNextRender` を使います。SSR中はどちらも実行されず、clientでもcallback実行時にcomponentのhydration完了は保証されないため、直接DOM操作はその前提で行います。
