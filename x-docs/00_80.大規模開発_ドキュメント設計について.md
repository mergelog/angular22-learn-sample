## 大規模チーム開発では「全部を書く」をやめる

設計書を「種類」で考えるより、

人間が責任を持って維持すべき情報か、コード等から再生成できる情報か

で分けた方がよい

| 情報            | 推奨         | 理由                   |
| ------------- | ---------- | -------------------- |
| 業務ルール・用語定義    | 維持する       | コードから意図を復元しにくい       |
| システム境界・責務     | 維持する       | 大規模化すると非常に重要         |
| API・イベント契約    | 維持する／機械検証  | 他チームとの契約になる          |
| DB制約・重要データモデル | 維持または生成    | 障害影響が大きい             |
| 権限・認可         | 維持する       | コードだけでは全貌を追いにくい      |
| 重要なシーケンス      | 維持する       | 非同期・リトライ・例外・複数サービスなど |
| 単純CRUDシーケンス   | 原則作らない     | コードの二重管理になりやすい       |
| 画面遷移          | 複雑な業務フローだけ | 単純Routerまで図にすると二重管理  |
| UI部品仕様        | Storybook等 | 静的Excel設計書より現物の方が正確  |
| コンポーネント構成     | 必要なら自動生成   | ソースから取得可能            |
| Class図        | 原則自動生成     | 手書きするとすぐ古くなる         |
| OpenAPI       | コードと同期     | 人手による二重記述を避ける        |
| 詳細な処理ロジック     | 原則コード＋テスト  | 詳細設計との二重管理を避ける       |
| 「なぜそうしたか」     | ADR等で必ず残す  | コードから絶対に復元できない       |

特に、

「What / Why / Constraint は文書として残す」
「現在のHowはなるべくコードや自動生成から取る」

という境界です。

---

「この仕様が正なのか」
「このコードは過去の事情なのか意図された設計なのか」
「この例外処理は業務要件なのかバグ回避なのか」

は、ソースだけでは確定できません。

そこに、業務仕様、制約、責務、ADR、重要フロー、受入条件が整理されていると、人間のオンボーディング資料だった設計ドキュメントが、そのままAIエージェントのプロジェクト知識になります。 DORAも、AIを内部ドキュメントやコードベースへ安全につなぐ「AI-accessible internal data」をAI活用の基礎能力の一つとして挙げています。

---

質問の最初にあった

大規模案件ともなると、あそこどうだっけというのが頻繁に発生するので、ドキュメント整備は開発の要になる

これは2026年になって古くなった考えではありません。

変わりつつあるのは、

「全部を詳細設計書に書く」
から
「人間とAIが何度も参照する重要情報だけを正として残し、残りはコードから生成・検証・更新する」

という部分です。

---

ここまで調べると、今の大規模チーム開発でかなり強そうなのは、「設計書を作るか作らないか」ではなく、「どの情報を手書きの正本にし、どれを自動生成物にするか」を最初に設計することだと思います。

この考えをさらに詰めると、実案件で使える「大規模案件のドキュメント構成表」まで落とせます。たとえば要件定義・基本設計・Angular画面・API・Python/ClearML・DB・シーケンス・テスト・ADRについて、必須／条件付き／自動生成／不要の4分類にして、「この条件ならシーケンスを書く」という判断基準まで作ると、かなり実務的な設計標準になります。
