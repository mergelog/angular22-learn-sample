### ユーティリティ型　直接の比較サマリー

| ユーティリティ型        | 効果                            | 元の型との違い                   |
| --------------- | ----------------------------- | ------------------------- |
| `Partial<T>`    | すべてのプロパティをオプショナルにする           | プロパティはそのまま。すべてに `?` が付く   |
| `Required<T>`   | すべてのプロパティを必須にする               | プロパティはそのまま。`?` が外れる       |
| `Readonly<T>`   | すべてのプロパティを読み取り専用にする           | プロパティはそのまま。`readonly` が付く |
| `Pick<T, K>`    | 指定したプロパティだけを取り出す              | 指定したプロパティだけの型になる          |
| `Omit<T, K>`    | 指定したプロパティを除外する                | 指定したプロパティ以外の型になる          |
| `Record<K, T>`  | キーと値の型を指定してオブジェクト型を作る         | 既存の型を変換するというより、新しい型を組み立てる |
| `Exclude<T, U>` | Union型 `T` から `U` に該当する型を除外する | 型の候補が**減る**               |
| `Extract<T, U>` | Union型 `T` から `U` に該当する型だけを残す | 型の候補が**減る**               |

**覚え方**

* `Partial` / `Required` / `Readonly` → **プロパティは残して、性質を変える**
* `Pick` / `Omit` → **オブジェクトのプロパティを選別する**
* `Record` → **キーと値からオブジェクト型を作る**
* `Exclude` / `Extract` → **Union型の候補を選別する**

**対になる型**

* `Partial` ↔ `Required`
* `Pick` ↔ `Omit`
* `Exclude` ↔ `Extract`

### take()、first() の違い

first() がエラーになる条件: 値が1件も来ないまま、first() から見て Observable が complete した

```ts
// 値が来る前にコンポーネントが destroy されたら、takeUntilDestroyed() が購読を解除
source$.pipe(
  first(),
  takeUntilDestroyed()
)
// この場合、first() に「completeしたよ」という通知が来るわけではなく、単に unsubscribe されます。
// なので通常、first() の EmptyError は出ません
```

一方、順番が逆だと

```ts
/*
source$
   ↓
takeUntilDestroyed()
   ↓ destroyされたので complete
first()
   ↓
「1個も来てないのにcompleteした！」
   ↓
EmptyError
*/
source$.pipe(
  takeUntilDestroyed(),
  first()
)
```

となり得ます。

| 項目                         | `take(1)`    | `first()`    |
| -------------------------- | ------------ | ------------ |
| 最初の1件を取得                   | ○            | ○            |
| 1件取ったら complete            | ○            | ○            |
| 1件も来ずに元Observableがcomplete | そのままcomplete | `EmptyError` |
| 条件指定                       | ×            | ○            |
| デフォルト値                     | ×            | ○            |

[L00_初期etc/35_take()、first() の違い.md](./L00_初期etc/35_take()、first()の違い.md)

### debounceTime と debounce

debounceTime は待ち時間が固定です。たとえば 300ms なら、最後の入力から300ms何も来なければ、その値を流します。検索入力でよく使います。

debounce は値ごとに待ち時間を変えられます。例：1文字なら1秒、3文字以上なら300ms待つ、という制御ができます。通常は debounceTime を使います。

### - {dispatch: false} ※createEffect内  

action として Store に dispatch させない指定

型の中身まで追う必要はありません。実際に使うときは次の2つだけで足ります。

effect が action を返さず、URLの書き換えなどの副作用だけを行うときは {dispatch: false} を付ける  
付け忘れると Type '...' is not assignable to type 'Action<string>' のような型エラーが出る。このエラーが出たら、まず {dispatch: false} の付け忘れを疑う

### > catchError()

[L00_初期etc/32_catchError.md](./L00_初期etc/32_catchError.md)  

catchError は RxJS で、Observable の途中で発生したエラーを捕まえて、別の Observable に差し替えるためのオペレータ  
try catchと同じ考え。  
  * `catchError(() => of(...))`：エラー処理。エラーを正常値に置き換えて、その値を流す。
  * `catchError(() => EMPTY)`：もみ消し。エラーを飲み込み、何も流さずその処理を終了する。
  * `catchError(error => throwError(() => error))`：エラーを捕まえるが、処理せず再び上位へ投げる。
  * `catchError` の位置：`switchMap` の内側ならその1回の処理だけ失敗、外側なら Observable 全体が終了しやすい。

### withLatestFrom() concatLatstForm() 違い

  普通のRxJSなら withLatestFrom。EffectでStoreの値を足すなら concatLatestFrom。
  
  ```
  withLatestFrom → 相手の Observable を先に購読して、最新値を待っている
  concatLatestFrom → 元の値が流れてきた瞬間に、必要な Observable を取りに行く
  ```
  
  concatLatestFrom の大きな利点は、左側の値を使って「どの selector を読むか」を決められること

  |                   | `withLatestFrom` | `concatLatestFrom`   |
  | ----------------- | ---------------- | -------------------- |
  | 所属                | RxJS             | `@ngrx/operators`    |
  | 相手を購読するタイミング      | 先に購読             | 元データが来てから            |
  | 左側の値を使える          | 基本やりにくい          | `action => ...` と使える |
  | NgRx Effects      |1 使える              | **こちらを優先**           |
  | 普通の Observable 同士 | **よく使う**         | NgRx向け               |

### lastValueFrom() firstValueFrom()

  - firstValueFrom() / lastValueFrom() は、どちらも Observable を Promise に変換して await できるようにする関数です。
  - `lastValueFrom()` がスッキリするが重要な弱点があります。  
    一番大きいのは、**Observableの世界からPromiseの世界に出てしまう**ことです。
  - 結論: 単発処理なら `await lastValueFrom()` は読みやすい。ストリーム処理ならRxJSのまま。  
    → 重要; [./L00_初期etc/36_firstValueFrom,lastValueFrom,forkJoin.md](./L00_初期etc/36_firstValueFrom,lastValueFrom,forkJoin.md)

### forkJoin()

  - forkJoin：全員終了したら、最後の値を1回だけ
  - combineLatest：全員が最低1回流れた後、誰かが更新されるたび何度も流れる
  - forkJoin は、複数のHTTP APIを並列で呼んで「全部揃ったら次へ進む」が典型的な使いどころです。
  - 1つでも complete しないObservableがあると、forkJoin もずっと流れません。HttpClient は通常1回レスポンスを返して完了するので、forkJoin と非常に相性がいいです。

### distinctUntilChanged()

  - 前回と同値なら流さない
  - 離れて現れた同じ値は再び流れる。比較関数を省略すると `===` で比較するため、オブジェクトは内容が同じでも別の参照なら流れる。

| `startWith(x)` | 本来の値が流れる前に、最初に `x` を流す | `A → B` に `startWith('初期')` → `初期 → A → B` | 初期値を与える、最初から処理を動かす   |
| `skip(n)`      | 最初の `n` 個を無視する         | `A → B → C` に `skip(1)` → `B → C`          | 初期値を無視して、2回目以降だけ処理する |

```ts
this.searchText$.pipe(
  // まだ検索文字が入力されていなくても最初に空文字 '' を流して処理を開始する
  startWith('') 
)
```

```ts
this.value$.pipe(
  // 最初に流れてくる初期値は無視して、ユーザーが変更した後だけ処理する
  skip(1)
)
```

### pairwise()

  - Observable の「前の値」と「今の値」をセットで流す RxJS Operator
    ```
    of(10, 20, 35).pipe(
      pairwise()
    ).subscribe(([previous, current]) => {
      console.log(previous, current);
    });
    // 結果
    // 10 20
    // 20 35
    ```

### finalize()

  - Observableが終了したとき必ず処理する（ローディング解除、後片付け）

### delay()

  - 流れてくる値を指定時間だけ遅らせる「出すのを遅らせる」（演出、疑似通信、表示タイミング調整）

### timeout()

  - 一定時間値が来なければエラーにする「待ちすぎなら失敗」（API応答待ちの打ち切り）

### bufferTime()

  - 一定時間分の値を配列にまとめて流す「○秒分まとめる」（ログ・イベントのまとめ処理）
  ```ts
  source$.pipe(
    bufferTime(1000)
  )
  // 1秒間に、A → B → C 時たら
  // ['A', 'B', 'C']としてまとめて一回流す
  ```

### merge()、concat()、combineLatestWith()

  違いは?
  - merge() / concat() / combineLatestWith() → すでにある複数の Observable をどう組み合わせるか
  - mergeMap() / concatMap() → 流れてきた値から新しい Observable を作って、それをどう処理するか

  - `結果`を入れた表で比較

| 名前                    | 種類            | 何をする？                   | 結果                              | イメージ             |
| --------------------- | ------------- | ----------------------- | ------------------------------- | ---------------- |
| `merge()`             | RxJS **func** | 複数Observableを同時購読       | **各Observableの値が、来た順に1本へ流れる**   | AとBを同時に流す        |
| `concat()`            | RxJS **func** | Observableを順番に購読        | **Aの全値 → A完了 → Bの全値**           | Aが終わってからB        |
| `combineLatestWith()` | RxJS **pipe** | 複数Observableの最新値を組み合わせる | **`[最新A, 最新B]` のセット**           | どちらか更新されるたび最新セット |
| `mergeMap()`          | RxJS **pipe** | 各値からObservableを作り並行処理   | **内側Observableの結果が完了順・到着順に流れる** | APIを同時実行         |
| `concatMap()`         | RxJS **pipe** | 各値からObservableを作り順番に処理  | **1件目の結果 → 完了 → 2件目の結果…**       | APIを順番に実行        |

  - 例えば A と B がこう流れるとします。  
    `A$: 1 → 2 → 3`  
    `B$: a → b`  

    + `merge(A$, B$)` の結果はタイミング次第で、  
      `1 → a → 2 → b → 3`
      のようになります。
    + `concat(A$, B$)` なら必ず、  
      `1 → 2 → 3 → a → b`
      です。

    + `combineLatestWith()` はまったく違って、  
      `[1, a]`  
      `[2, a]`  
      `[2, b]`  
      `[3, b]`  
      のような **「最新値の組」** が結果になります。

  - 「結果」で覚える
      `merge` → バラバラの値が1本になる  
      `concat` → 前から順番に全部流れる  
      `combineLatestWith` → 最新値が配列になる  
      `mergeMap` → 作った処理の結果が並行で返る  
      `concatMap` → 作った処理の結果が順番に返る

  - [Lサンプルコード:00_初期etc/43_merge,concat.md](./L00_初期etc/43_merge,concat.md)

### effect()

  - Signal の変化を監視して副作用を実行する
  - NgRx の Effects とは別物。値の計算・状態伝播には `computed()` を使う
  - effect() の本質は「中で読み取った Signal が変わったら、その処理を再実行する」

  - this.countの変化を検知し effectが再実行される
  ```ts
  effect(() => {
    console.log('count:', this.count());
  });
  ```

#### onCleanUp()

  - effect() が再実行される前に、前回登録した onCleanup() が呼ばれる
  ```ts
  constructor() {
    effect((onCleanup) => {
      const value = this.inputValue();
  
      const timerId = setTimeout(() => {
        console.log(value);
      }, 1000);
  
      onCleanup(() => {
        clearTimeout(timerId);
      });
    });
  }
  ```

| 用途               | 使うもの          |
| ---------------- | ------------- |
| Signalから別の値を計算   | `computed()`  |
| Signalの変化を見て何か実行 | `effect()`    |
| Observableの値を加工  | `pipe()`      |
| Observableを購読    | `subscribe()` |
| effect再実行前の後片付け  | `onCleanup()` |

実務で effect() を見たときは、まず次の3点だけ確認するとコードリーディングが速くなります。

  - effect 内でどの Signal を () で読んでいるか
  - その Signal が変わったら何を実行しているか
  - onCleanup() が必要な処理か

  - 特に setTimeout、イベントリスナー、外部ライブラリとの同期などが出てきたら、onCleanup() を確認します。

### linkedSignal()

  - [Angular公式: linkedSignalによる派生状態](https://angular.jp/guide/signals/linked-signal)
  
  - [重要]前回の値を取得し、条件次第で処理を分岐する  
    [L00_初期Angular/03_linkedSignal.md](./L00_初期Angular/03_linkedSignal.md)  
  
    source: = 元になる値を指定する  
    computation: = その値から次の値を決める  
    ```ts
    readonly selectedUser = linkedSignal<User[], User | undefined>({
      source: () => this.users(),
      computation: (
        users,   // 今回の source の値
        previous // 前回の source と前回の linkedSignal 値
      ) => {
        const previousUser = previous?.value; // 前回の値を取る
        if (
          previousUser &&
          users.some(user => user.id === previousUser.id)
        ) {
          return previousUser; // 条件に一致すれば、前の情報を維持
        }
        return users[0]; // 一致しなければ、新情報を適用
      },
    });

    ```

  - signal()、computed()、linkedSignal() を並べます。

| API              | 自分で `.set()` | 他Signalから自動計算 | 用途                 |
| ---------------- | -----------: | ------------: | ------------------ |
| `signal()`       |            ○ |             × | 独立した状態（自分で管理する値）             |
| `computed()`     |            × |             ○ | 計算結果（他のSignalから自動計算する値）               |
| `linkedSignal()` |            ○ |             ○ | 依存関係があるが手動変更も必要な状態（他のSignalから自動計算する値） |

### signalまとめ

| やりたいこと                         | 基本                     |
| ------------------------------ | ---------------------- |
| A Signal から B の値を計算したい         | `computed()`           |
| A に依存するが、B を手動変更もしたい           | `linkedSignal()`       |
| A が変わったら別Signalへ `.set()` して伝播 | **原則 `effect()` にしない** |
| A が変わったら `localStorage` 保存     | `effect()`             |
| A が変わったらログ出力                   | `effect()`             |
| Signal → 別Signalへコピー    | 原則 `effect()` を使わない                |

  - ここでいう「Signal → 別Signalへコピー」は、例えばこういうコードです。  
    という「Signalの値を別Signalへ伝播」させています。  
    この用途に effect() を使うのは、Angular公式も避けるよう案内しています  
  ```ts
  readonly firstName = signal('Taro');
  readonly copiedName = signal('');
  
  constructor() {
    effect(() => {
      this.copiedName.set(this.firstName());
    });
  }

  // 上の例なら、copiedName を別状態として持つ必要がないので
  // 以下のように書く

  readonly firstName = signal('Taro');
  readonly copiedName = computed(() => {
    return this.firstName();
  });
  ```
