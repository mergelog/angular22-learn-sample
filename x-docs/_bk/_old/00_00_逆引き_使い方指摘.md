### **1. 表の構造と可読性**
#### **🔹 修正が必要な点**
- **「派生」行の重複**:
  - 「1つの値から別の値を作る」と「複数の現在状態から値を作る」は、どちらも `computed()` / `Selector` でカバーされるため、行を統合するか、区別を明確化してください。

### **3. 具体的な記述の修正**
#### **🔹 `concatLatestFrom` の解説**
- **現在の解説**:
  > `concatLatestFrom` は `withLatestFrom` と違ってObservable factoryを**遅延評価**することが本質です。

  これは正しいですが、**なぜ遅延評価が重要か**を追加してください。
  - 例:
    > `concatLatestFrom` は、Actionが来たタイミングで `factory` を呼び出し、その時点の状態を取得します。`withLatestFrom` は常に最新の値を保持するのに対し、`concatLatestFrom` はActionごとに参照先を再評価するため、Actionのコンテキストに依存する状態を取得できます。

#### **🔹 `forkJoin` の解説**
- **現在の解説**:
  > 全入力が「最低1回emit」して「complete」したら、各入力の最後の値をまとめて1回だけemitする。

  これは正しいですが、**失敗ケース**を追加してください。
  - 例:
    > 1つでもerrorになると、全体がerrorになり、他の入力からunsubscribeします。個々の失敗を結果として集めたい場合は、各入力の内側で `catchError` を使って値に変換します。

#### **🔹 `take(1)` vs `first()`**
- **現在の解説**:
  > `take(1)` は値が来れば1件取得し、値なしでsourceがcompleteしても正常終了します。`first()` は条件なしの最初の1件です。

  これは正しいですが、**`first()` が error になる条件**を明確化してください。
  - 例:
    > `first()` は、sourceが値を1つもemitせずにcompleteすると `EmptyError` を投げます。`first(predicate)` も条件を満たす値がないままcompleteすると `EmptyError` になります。

### **1. SignalStore vs Store (NgRx) の選択基準**
- **提案**:
  | 基準 | `Store` (従来) | `SignalStore` |
  |------|----------------|---------------|
  | 状態管理のパラダイム | Action駆動 | メソッド駆動 / イベント駆動 |
  | 学習コスト | 高い (Reducer/Effects) | 低い (Signalベース) |
  | 開発ツール | DevTools対応 | DevTools対応 (v22以降) |
  | 状態の同期性 | Observableベース | Signalベース |
  | 適した用途 | 大規模アプリ / 複雑な状態遷移 | 中小規模アプリ / ローカル状態 |

### **2. `effect()` vs `afterRenderEffect()` vs `rxMethod`**
- **提案**:
  | API | 用途 | 実行タイミング |
  |-----|------|----------------|
  | `effect()` | 外部API (localStorage, logging) への反映 | Signal変更後 (非同期) |
  | `afterRenderEffect()` | DOMの読み書き | 描画後にSignal変更に反応 |
  | `rxMethod` | RxJS pipelineを使った非同期処理 | Signal/Observableの変更に反応 |

### **3. `shareReplay` vs `computed()` vs `toSignal`**
- **提案**:
  | API | 用途 | 寿命管理 |
  |-----|------|----------|
  | `shareReplay` | Observableの購読共有 + 過去値の再生 | 手動 (refCount) |
  | `computed()` | Signalの派生値 (lazy評価 + memoize) | 自動 (依存Signal) |
  | `toSignal` | Observable → Signal (最新値をSignal化) | 自動 (注入コンテキスト) |

### 全体的な指摘事項

各関数の解説は綺麗にまとまっていますが、「どう動くか」ばかりで「どう間違うか（アンチパターン）」の視点が不足しています。以下のポイントを各項目の末尾に短い箇条書きで追記することを強く推奨します。

### 前半（生成・結合系）の指摘

* **`BehaviorSubject`**
* **指摘:** Angular 16以降の世界線において、単なるコンポーネント内の状態保持にこれを使うのはもはやレガシーです。
* **追記案:** `⚠️ Component内の単純な状態なら signal() を優先。`


* **`combineLatest` / `combineLatestWith**`
* **指摘:** 全てが揃うまで発火しないことは書かれていますが、「どれか1つでも値を出さずに完了（complete）すると、全体がそのまま死ぬ（何も出力せずに完了する）」という初心者が最もハマる罠が漏れています。
* **追記案:** `⚠️ 1つでも未発火のままcompleteすると、全体も無言でcompleteする罠に注意。`


* **`forkJoin`**
* **指摘:** これも同様です。エラーが起きた瞬間に他のリクエストもキャンセルされる仕様を警告すべきです。
* **追記案:** `⚠️ 1つでもエラーになると全体がエラーになり、他の並行処理も中断・破棄される。`


* **`zip` / `zipWith**`
* **指摘:** 「対応する順番が重要な場合」とありますが、**深刻なメモリリークの温床**になる事実が隠蔽されています。片方の通知が速く、もう片方が遅い場合、未処理の値が内部配列に無限に溜まり続けます。
* **追記案:** `⚠️ 発火頻度に差があるストリームを結合すると、遅い方に合わせて内部バッファが無限に肥大化しメモリリークする危険あり。`



### 中盤（マッピング・非同期制御系）の指摘

* **`switchMap`**
* **指摘:** 「古い結果を採用したくない読み取り処理に向く」という記述は完璧ですが、逆に言えば「書き込み処理（POST等）で使ってはいけない」という強い警告が必要です。
* **追記案:** `⚠️ データ更新（POST/PUT等）で使うと、通信はキャンセルされてもサーバー側で処理が続行され、データ不整合が起きる危険あり。`


* **`concatMap`**
* **指摘:** 待ち行列が増えることは書かれていますが、内部Observableがcompleteしない（例えば `interval` や無限ストリームを返してしまう）と、**次の処理が永久に実行されない**という詰み状態について触れるべきです。
* **追記案:** `⚠️ 内部Observableがcompleteしない限り、次の入力は永久に処理されない。`


* **`exhaustMap`**
* **指摘:** 送信ボタン連打対策の鉄板ですが、エラーハンドリングを間違えると「二度とボタンが押せなくなる」バグを生みます。
* **追記案:** `⚠️ 内部処理でエラーが発生した際、内部で catchError しないとストリーム全体が死に、以降の入力を一切受け付けなくなる。`


* **`withLatestFrom` / `concatLatestFrom**`
* **指摘:** 参照先が一度も値を出していないと、sourceが発火してもスキップされる罠（サイレントに無視される）をさらに強調すべきです。
* **追記案:** `⚠️ 参照先が初回発火を終えていない場合、sourceの通知自体が虚空に消える点に注意。`



### 後半（フィルタリング・エラー・ユーティリティ）の指摘 ※手抜きなし

* **`take(1)`**
* **指摘:** 「正常完了する」とありますが、値が出ないまま上流が待ち続けている場合、これも永久に待ち続けます。メモリリーク回避の銀の弾丸ではありません。
* **追記案:** `⚠️ sourceが値も出さずcompleteもしない場合、購読は残り続ける。必要なら timeout() 等を併用。`


* **`catchError`**
* **指摘:** 「ここで回復方針を決める」とありますが、読者が一番やるミスは **Effectの大外で `catchError` を書き、 `of(action)` を返してEffect自体を殺してしまう** ことです。上部の解説に頼らず、ここでも釘を刺すべきです。
* **追記案:** `⚠️ 外側のストリーム（Effectのトップレベル等）に置くと、エラー時に全体がcompleteしてしまい、以後のActionに反応しなくなる。必ず内部ストリームに配置すること。`


* **`retry`**
* **指摘:** 「最初から購読し直す」とありますが、それがもたらす副作用（APIコール以外のログ送信などの `tap` もすべて再実行される）に言及すべきです。
* **追記案:** `⚠️ 上流のパイプライン全体が再実行されるため、意図しない副作用の重複に注意。`


* **`takeUntilDestroyed`**
* **指摘:** 「指定した DestroyRef のスコープが破棄されたとき」とありますが、置く場所に依存して内部Observableが死なない罠を辞書部分でも書くべきです（上部で触れてはいますが）。
* **追記案:** `⚠️ switchMap等の「前」に置くと、コンポーネント破棄後も実行中の内部通信（HTTP等）がキャンセルされない場合がある。「後ろ」に置くのが鉄則。`


* **`tap`**
* **指摘:** 「デバッグなどの副作用を差し込みます」とありますが、ここで絶対にやってはいけない最悪のアンチパターンへの警告が必要です。
* **追記案:** `⚠️ 内部で subscribe() を呼ぶのは絶対NG（ネストした購読のアンチパターン）。非同期処理なら各種Map系へ繋ぐこと。`

下段の「基本的な使い方」を、RxJS冒頭から最後の `afterRenderEffect()` まで通して確認しました。結論としては、全面改稿は不要です。ただし、**3か所は修正必須、6か所は1行追記した方が記事として強くなる**と判断します。特に末尾のResource系まで確認しており、そこで実際に1つ重要な誤りがありました。  

1. **【修正必須】`Resource chain` の例は直した方がいいです。** 現在は `params: ({ chain }) => ({ user: chain(userResource) })` になっています。  Angular 22公式はここをかなり明確に注意しており、`chain()` の値をオブジェクトで包むと、親Resourceが `resolved/local` かつ値が `undefined` の場合にも、params自体は `{ user: undefined }` という「定義済みの値」になり、子loaderが実行され得ます。公式は **chainした値をparamsへ直接返す** ことを推奨しています。 ([angular.dev][1])
   ここは例を `params: ({ chain }) => chain(userResource)`、loader側を `loader: ({ params: user }) => ordersApi.findByUser(user.id)` の形にした方が安全です。説明も「親が値を持つときだけ」より、「親が `resolved/local` なら値を返し、`idle/loading/reloading/error` は子へ伝播する。値自体が `undefined` になり得る場合はオブジェクトで包まない」とした方が正確です。

2. **【修正必須】`withLinkedState()` の「`set` や `patchState` でも変更できる」は誤解を招きます。** 現在の文章では、Storeから公開された `store.selectedOption` に対して直接 `.set()` できるようにも読めます。  NgRx公式では、linked state sliceは通常のstate sliceと同様に `DeepSignal` としてStoreへ公開され、Store stateの更新方法として明記されているのは `patchState` です。一方、`withLinkedState` 内部で `linkedSignal()` や別の `WritableSignal` を返すこと自体はできます。 ([NgRx][2])

## A. 誤り・不正確（要修正）

**1. `throttleTime()` — 設定オブジェクトは第3引数**

現状「必要なら `{ leading: true, trailing: true }` を設定します」だけなので、読者は第2引数に渡して動かない。RxJS 7 のシグネチャは `throttleTime(duration, scheduler?, config?)`。

```ts
import { asyncScheduler } from "rxjs";
source$.pipe(throttleTime(300, asyncScheduler, { leading: true, trailing: true }));
```

**2. `withState()` — 「利用側から直接行わせず」は運用ルールではなく既定の型仕様**

NgRx Signals v18 以降、`signalStore` のstateは既定で **protected**。store外からの `patchState(store, ...)` はコンパイルエラーになります。「行わせない」ではなく「既定でできない／解除には `{ protectedState: false }`」と書くべきです。読者が「規律の問題」と誤解すると、`protectedState: false` を付ける移行コードを見たときに判断できません。

> 追記案：`withState` の状態はSignalStore外から `patchState` できません（既定 `protectedState: true`）。外部更新を許すには `signalStore({ protectedState: false }, ...)`。既存コードの移行schematicがこれを自動付与するため、既存プロジェクトでは付いていることがあります。

**3. `BehaviorSubject` — `asObservable()` は型上の保護**

「勝手に `next()` されるのを防げます」は言い過ぎ。`as Subject<T>` でキャストすれば破れます。「型として `next` を公開しない」に限定を。あわせて complete/error 後の挙動が抜けています。

> 追記案：complete後の購読は最後の値を受け取らず即complete。error後は購読即error、`.value` もthrow。`.value` の多用は命令的になりやすく、Angular 22なら `signal()` を第一候補に。

**4. `chain()` の説明が「値を返す関数」になっていて、伝播の仕組みが落ちている**

`chain` は**値が使えないときに status を throw して親の状態を子へ伝播させる**実装です。これが本質で、そこから実用上の制約が出ます。現行の「親が複数ある場合は、同じparams関数内でそれぞれを `chain()` して…まとめます」は、この制約を書かないと不正確です。

> 追記案（超箇条書きで可）：
> - `chain()` は値が無い間、status を throw して親の loading/idle/error を子へ伝播する
> - したがって `params` 関数内でのみ呼ぶ。`try/catch` で包むと伝播が壊れる
> - 複数 `chain()` は**最初にthrowした親の状態**が伝播し、以降は評価されない
> - `parentResource.value()` を直読みすると、親loading中に子が `idle` になり `isLoading()` が `false` を返す（これがchainの解決したい問題）

## B. 欠落していて実害が大きい（優先追記）

**1. NgRx Effects：`{ dispatch: false }` が一言も無い（最優先）**

Router遷移・toast・localStorage系のEffectは必須オプションで、忘れるとdispatchループか実行時エラーになります。逆引き辞書でこれが無いのは穴です。

> 追記案：Actionを返さないEffect（Router、toast、storage等）は `createEffect(() => ..., { dispatch: false })` を指定します。指定しないと戻り値がActionとしてdispatchされ、ループやエラーの原因になります。

**2. Effects/Storeのコード例：フィールド初期化順序**

`createEffect(() => this.actions$.pipe(...))` はフィールド初期化時に評価されるため、`inject(Actions)` の宣言が後ろだと `undefined`。実務で最頻出のハマりです。

> 追記案：`createEffect` はフィールド初期化時に実行されるため、`private readonly actions$ = inject(Actions);` は必ず先に宣言します。

**3. `combineLatest()` の節が「表の“通知タイミングに注意”」を回収していない**

`forkJoin` はあれだけ丁寧に契約を書いているのに、`combineLatest` は正常系しか書いていない。非対称です。

> 追記案：
> - 入力の1つが**一度もemitせずcomplete**すると、`combineLatest` 全体も値を出さずcompleteする
> - 1つがerrorになれば全体がerror
> - **同じ源から派生した複数Observableを合成すると中間状態（glitch）が出る**。A→B、A→CをcombineLatestすると、Aの1回の更新で2回通知され、途中に不整合な組が流れ得る。Store状態同士なら `createSelector` を優先する理由がこれ

**4. `zip()`：バッファ無制限**

`concatMap` では「待ち行列が増えます」と書いているのに、`zip` は書いていない。速度差があるとメモリが増え続けます。

> 追記案：速い側の値は相手が揃うまで内部バッファに保持され、上限はありません。速度差が続く入力同士には使いません。

**5. `shareReplay()`：error時のreset**

本文で「成功してcompleteした値のキャッシュは `refCount: true` でも残る」と書いているので、対になる既定を書くと閉じます。

> 追記案：既定は `resetOnError: true` / `resetOnComplete: false`。errorで終わった場合は次の購読で上流が再実行され、成功completeした場合は再実行されません。

**6. `Selector`：メモ化のサイズは1**

表に「Store selectorは既定でメモ化される」と書いた以上、限界も書かないと危険です。

> 追記案：`createSelector` のメモ化は直前の引数1組のみ。props付きselectorを複数コンポーネントが異なる引数で同時利用するとメモ化が毎回無効化されるため、selector factory（呼び出しごとに `createSelector` を生成）にします。

**7. `rxMethod()`：寿命・import・解除**

節が「便利機能」の説明で止まっており、契約が書かれていません。

> 追記案：
> - `rxMethod` はSignalStoreの生成時（注入コンテキスト）に作る
> - `tapResponse` のimport元は `@ngrx/operators`
> - 戻り値の関数は `unsubscribe()` を持ち、接続した購読を明示的に切れる

**8. SignalStore節の機能カバレッジ不足**

`withHooks` / `withEntities` / `withProps` / `_`プレフィックス が全く出てこないため、「SignalStoreの使い方」としては不完全です。各1行でいいので。

> 追記案（箇条書き）：
> - `withHooks({ onInit, onDestroy })`：初期ロード（`onInit` で `rxMethod` を起動）や後片付け
> - `withEntities()`：一覧の正規化管理。`addEntity` / `setAllEntities` / `selectId` を併用
> - `withProps()` / `withMethods` 内の `inject()`：Storeは注入コンテキストで生成されるため依存注入が可能
> - メンバー名を `_` で始めるとprivate扱いになり、store外から参照できない

**9. NgRx 22 の標準記法（`createActionGroup` / `createFeature`）が無い**

現行例は動きますが、読者は古い書き方だけを覚えます。各1行で十分。

> 追記案：Actionは `createActionGroup({ source: 'Users Page', events: { ... } })` でまとめられ、Reducer+Selectorは `createFeature` でfeature単位に束ねられます（`selectUsersState` 等が自動生成）。

**10. `effect()`：Signalへの書き込みは「できない」ではなく「できるがやらない」**

Angular 19で `allowSignalWrites` は不要になり、既定で書けます。記事は「代替computedとして使わない」と正しく書いていますが、根拠が「禁止されているから」と読まれないよう1行補強を。

> 追記案：`effect` 内でのSignal書き込みは技術的には可能（`allowSignalWrites` はAngular 19以降不要）ですが、依存の連鎖と再実行が追えなくなるため、派生値は `computed` / `linkedSignal` で表します。
