# RxJS / NgRx / Signal系 逆引き辞書

対象は Angular 22.1.x / RxJS 7.8.x / NgRx 22.x。
以下の「推奨」は用途に応じた選択指針です。`—` は直接対応するAPIを挙げていない意味であり、実現不可能という意味ではありません。

前提として、NgRx列では **`[Store]` = 従来の @ngrx/store + Effects**、**`[SignalStore]` = @ngrx/signals** と区別します。SignalStoreはNgRx製品ですが、Action駆動を必須としません。`withMethods` や `rxMethod` によるメソッド駆動が可能です。 ([NgRx][1])

本文の **Effect / Effects は NgRx の副作用処理**、**`effect()` は Angular のAPI**です。共有ServiceやSignalStoreの共有範囲・寿命はproviderの配置で決まり、Service化するだけでアプリ全体の単一状態になるわけではありません。 ([Angular][14])

RxJS欄では、Observableを作る関数を **`[func]`**、`source$.pipe(...)` に渡すoperatorを **`[pipe]`** と表記します。

## よくある誤解の訂正

まず `combineLatest` と `computed()` は別物です。

`combineLatest` は**時間軸上を流れる複数Observableを合流**します。一方 `computed()` は**現在存在するSignal状態から派生値を計算**します。NgRx Store内の状態Aと状態Bから状態Cを作るなら、Effect内でObservableを `combineLatest` するよりSelectorを合成するのが通常は適切です。外部ストリームや処理途中のObservableの結合には `combineLatest` 等を使います。これはNgRx ESLintルールが示すStore selectorの設計指針であり、あらゆるObservable結合をSelectorに置き換えるという意味ではありません。 ([NgRx][2])

`forkJoin` も正確に覚える必要があります。

> 全入力が「最低1回emit」して「complete」したら、各入力の最後の値をまとめて1回だけemitする。

です。

RxJS 7.8.xでは、1つでも**一度もemitせずcompleteすると、その時点で `forkJoin` 自体も値を出さずcomplete**します。`forkJoin([])` も値を出さず即completeします。空のままcompleteする入力もerrorになる入力もなければ、1つでも永久にcompleteしない限り待ち続けます。また1つがerrorになれば全体もerrorになり、他の入力からunsubscribeします。個々の失敗も結果として集めたい場合は、各入力の内側で `catchError` によって値へ変換します。 ([RxJS][3])

`take(1)` と `first()` も似ていますが契約が違います。`take(1)` は値が来れば1件取得し、値なしでsourceがcompleteしても正常終了します。条件で選ぶには `first(predicate)` を使い、該当値がないままsourceがcompleteすると、default値を指定していない限り `EmptyError` になります。`first()` は条件なしの最初の1件です。どちらもsourceが値を出さずcompleteもしなければ待ち続けるため、期限が必要なら `timeout` 等を組み合わせます。 ([RxJS][4])

## `concatLatestFrom` はこう覚える

```text
Actionが来た
  ↓
そのActionのタイミングで
factoryを評価して参照Observableを購読する
  ↓
参照先が同期的に値を出した場合のみ
その最新値とActionを組み合わせる
```

`withLatestFrom` と違ってObservable factoryを**遅延評価**することが本質です。

NgRx 18で `@ngrx/effects` からのexportは削除されたため、import元は、

```ts
import { concatLatestFrom } from "@ngrx/operators";
```

です。 ([NgRx][5], [v18移行ガイド][15])

`withLatestFrom` も参照先全てが少なくとも1回emitするまではsourceの通知を出力しません。その間のsourceの値は保留されず失われます。`concatLatestFrom` はsourceの通知ごとに参照先を購読するので、**その購読で同期emitしなければ、そのActionは後段へ流れません**。HTTP、`delay` 付きselector、初回通知前の `toObservable(signal)` などを渡しても値を待ってくれません。これは内部の `of(action).pipe(withLatestFrom(...))` という実装から分かります。 ([RxJS][16], [NgRx実装][17])

通常のStore selectorのように購読時に現在値を同期emitする参照先に使います。非同期処理の完了を待ちたい場合は、`switchMap` / `concatMap` 等の内側で処理し、必要なら結果をActionと組にします。

## 非同期競合・エラー処理で失敗しやすい点

`switchMap` が行うのは以前の内部Observableからのunsubscribeです。`HttpClient` は購読解除を進行中の通信の中断につなげますが、一般のPromiseや、解除処理を実装していないObservableの実処理まで止まる保証はありません。サーバーで既に実行された更新を元に戻す機能もありません。 ([RxJS][18], [Angular][19])

`concatMap` は内部Observableがcompleteしなければ次へ進まず、入力が速すぎると待ち行列が増えます。`mergeMap` は既定で同時実行数が無制限で、出力順も入力順とは限りません。`exhaustMap` が捨てる入力は後から再実行されず、抑制範囲も同じ購読内だけなので、サーバー側の重複実行対策の代わりにはなりません。 ([RxJS concatMap][20], [mergeMap][21], [exhaustMap][22])

継続してActionやメソッド呼び出しを処理したい場合、`take(1)` / `first()` / `catchError` の配置に注意します。

- NgRx Effectの外側に `take(1)` を置くとEffect全体がcompleteし、以後のActionを処理しなくなります。
- 外側の `catchError(() => EMPTY)` や `catchError(() => of(failureAction))` も、置き換えたObservableがcompleteするとEffect全体が終了します。通常はHTTP等の内部Observableで捕捉し、失敗Actionを返します。
- `rxMethod` でも未処理errorや外側のcompleteはそのメソッドの処理パイプラインを終了させます。内部Observableで `catchError`、または `@ngrx/operators` の `tapResponse` を使って処理を継続させます。 ([NgRx Effects][23], [rxMethod][24])

`retry` はerror時の**再購読**で、成功しない処理を自動的に成功させるものではありません。引数なしの `retry()` は無制限です。書き込みの再実行は重複更新を起こし得るため、回数・待ち時間・対象エラーに加えて冪等性も確認します。 ([RxJS][25])

## Resource系の整理

| API              | 主な用途                                          |
| ---------------- | ------------------------------------------------- |
| `resource()`     | AngularのResourceを作る基本API                    |
| `rxResource()`   | **Observableをデータ源**にしたResource            |
| `httpResource()` | `HttpClient` ベースのHTTP Resource                |
| `debounced()`    | debounceされた値を表す **Resource**。experimental |

`resource` / `debounced` は `@angular/core`、`rxResource` は `@angular/core/rxjs-interop`、`httpResource` は `@angular/common/http` からimportします。`rxResource` に渡すObservableのfactoryは、Angular 22では **`stream` オプション**です。 ([Angular rxResource][6], [RxResourceOptions][26], [httpResource][27], [debounced][28])

`resource()` の通常の `loader` は `PromiseLike<T>` を返しますが、それだけではなく、Signalベースのstreaming loader（`stream` オプション）もサポートしています。したがって、

> `resource = Promise`、`rxResource = Observable`

と完全に二分するのは不正確です。

正しくは、

> **既存ObservableをResourceとして扱いたい → `rxResource()`**

です。`resource` / `rxResource` / `httpResource` はAngular 22でstable、`debounced()` はexperimentalです。 ([Angular resource][7], [rxResource][6], [httpResource][27], [debounced][28])

Resource系は読み取り向けです。`resource()` はパラメータ変更時や破棄時に `abortSignal` へ中断を通知しますが、実際の通信等を中断するにはloader側でそのsignalを `fetch` に渡すなどの対応が必要です。`rxResource()` は以前のObservableの購読を解除し、`httpResource()` は以前のHTTP要求を中断します。POST/PUT等のmutationには `HttpClient` を直接使い、必要な競合制御を組み合わせます。 ([Angular resource][7], [Resourceガイド][29], [rxResource実装][30], [httpResourceガイド][13])

`httpResource()` は既定でHTTP GETを行う、リアクティブな読み取り向けAPIです。リクエスト設定で `method` や `body` も指定できますが、参照パラメータ変更による再実行・中断が起き得るため、mutationには使いません。

状態を読む際は次の契約に注意します。

- ロード状態を読むAPI名は `isLoading()`、結果は `value()`、エラーは `error()` です。
- `resource()` / `rxResource()` / `httpResource()` は `defaultValue` を省略すると、初期値などが `undefined` になり得ます。通常、パラメータ変更によるloading時は既定値（未指定なら `undefined`）へ戻り、`reload()` によるreloading時は以前の値を保持します。
- **エラー状態の `value()` は例外を投げます**。`hasValue()` で利用可能な値を確認してから読みます。`defaultValue` はエラー時の代替値を設定する機能ではありません。
- `params` が `undefined` なら読み取りを実行せずidleになります。`rxResource` の `stream` が値を一度も出さずにcompleteすると `NG0991` エラーになります。特に `catchError(() => EMPTY)` で握りつぶすとこの状態になり得ます。 ([Angular Resource][31], [Resourceガイド][29], [RxResourceOptions][26])

Angular 22ではResourceを順に依存させるため、子Resourceの `params` で受け取るコンテキストの `chain()` を使えます。`resource.chain()` というメソッドではありません。

```ts
const child = resource({
  params: ({ chain }) => ({ parent: chain(parentResource) }),
  loader: ({ params }) => loadChild(params.parent),
});
```

`chain(parentResource)` は親が `resolved` または `local` のときだけ値を返し、親のloading・idle・errorを子の状態へ伝播します。 ([Resourceガイド][29])

## `linkedSignal()` の位置

これは `computed()` と分ける必要があります。

```text
computed()
    ↓
元状態から自動的に決まる
    ↓
読み取り専用

linkedSignal()
    ↓
元状態から初期値・再計算値が決まる
    ↓
しかし自分でも set() できる
```

Angular公式も `linkedSignal` を「reactive computationによって初期化・リセットされる writable signal」と定義しています。 ([Angular][8])

NgRx 22ではSignalStoreに **`withLinkedState`** があり、計算関数または `linkedSignal` を返して派生と手動更新を両立できます。依存元変更時に以前の選択を維持したい場合は、`linkedSignal` の `source` / `computation` 形式で `previous` を使い、維持する条件を明示します。 ([NgRx][32])

Signalの `equal` の既定値は `Object.is` で、RxJSの `distinctUntilChanged()` の既定比較は `===` です。いずれもオブジェクトの深い比較ではありません。同じ参照のオブジェクトや配列を直接変更すると変更が伝わらない原因になるため、状態更新では新しい参照を作ります。 ([Angular][33], [RxJS][34])

`computed()` の計算中に例外が発生すると、その例外も計算結果と同様にメモ化されます。依存Signalが更新されて再評価されるまでは、何度読み取っても例外が再throwされます。RxJSのerrorによるストリーム終了とは異なり、依存Signalの変更後の再評価で復旧できます。

## `debounced()` はSignalそのものではない

表ではSignal系の列に置いていますが、

```ts
import { debounced, signal } from "@angular/core";

// コンポーネントやServiceのconstructor等、注入コンテキスト内。
const query = signal("");
const debouncedQuery = debounced(query, 300);

// 値は debouncedQuery() ではなく debouncedQuery.value() で読む。
```

の戻り値は `Signal<string>` ではなく、

```text
Resource<string>
```

です。

ここは分類上「Signalエコシステム」に置いているだけで、`debounceTime` と完全な一対一対応ではありません。待機中も `value()` は直前の確定値を返し、`isLoading()` / `status()` で待機状態を確認できます。experimental APIでもあります。 ([Angular][9])

## `toSignal()` / `toObservable()`

`toSignal()` は作成時に即subscribeします。同じObservableについて何度も `toSignal()` を作るべきではなく、生成したSignalを再利用します。同期emitが保証される `BehaviorSubject` などなら `requireSync: true` を利用できます。 ([Angular][10])

`initialValue` / `requireSync` を指定しない場合、初回emitまでは `undefined` です。`requireSync: true` は同期emitがなければ実行時エラーになります。sourceのerrorはSignalを読む際にthrowされ、sourceのcomplete後は最後の値を保持します。通常は作成時の注入コンテキストの破棄に合わせてunsubscribeされます。 ([Angular][10])

`toObservable()` は少し特殊です。

```text
subscribe
  ↓
既に値がReplaySubjectにあれば
初回は同期emitの場合がある

以降
  ↓
Signal変更
  ↓
effect
  ↓
非同期通知
```

そのため、

```text
set(1)
set(2)
set(3)
```

と同一安定化期間内に連続更新すると、途中の1と2ではなく最後の3だけがObservableへ流れます。 ([Angular][10])

イベントを1件ずつ必ず処理したい場合、この変換をイベントキューとして使わず、元のObservableやSubjectから処理します。`rxMethod` はSignalを直接受け取れ、通常のSignal変更に応じてreactive chainを実行します。ただしSignalはObservableやイベントキューと同じ意味で更新履歴を保存するものではありません。同一安定化期間内の連続更新も個別イベントとして必ず処理したい場合は、ObservableやSubjectなどのイベント源を使います。注入コンテキスト内で `store.load(query)` のように接続できます。`store.load(query())` なら、その時点の値を1回渡すだけです。 ([NgRx][24])

## 注入コンテキストと購読の寿命

`toSignal`（既定の自動cleanup使用時）/ `toObservable` / Resource系 / `effect` / `afterRenderEffect` は、通常、コンポーネントやServiceのフィールド初期化・constructor内で作成します。`ngOnInit` やクリックハンドラー自体は注入コンテキストではないため、そこで作成するなら事前に取得した `Injector` を対応するオプションへ渡します。 ([Angular interop][10], [DI][35], [Resource options][36], [Effect][37])

`takeUntilDestroyed()` の引数省略も注入コンテキストが前提です。外側で取得した `DestroyRef` を渡せば、その外でも使用できます。**購読を終えるのは、渡した `DestroyRef` のスコープが破棄された時**です。root Serviceの寿命は呼び出し元コンポーネントの寿命とは異なります。 ([Angular][38])

`rxMethod` にSignalやObservableを接続した購読は、SignalStore等の作成時に使われたInjectorの破棄に合わせてcleanupされます。したがって寿命は呼び出し元ではなく、どのInjectorに紐付いているかで決まります。 ([NgRx][24])

内部Observableも破棄時に解除するには、通常 `switchMap` 等の**後ろ**に置きます。前に置いた場合、sourceのcompleteだけでは内部Observableが終わらないことがあります。

```ts
// 事前に取得した destroyRef を使用する例。
source$
  .pipe(
    switchMap((value) => load$(value)),
    takeUntilDestroyed(destroyRef),
  )
  .subscribe();
```

これは `takeUntilDestroyed` が `takeUntil` で実装され、`switchMap` がsourceのcomplete後も内部Observableのcompleteを待つためです。 ([Angular実装][40], [RxJS実装][18])

## `effect()` と `afterRenderEffect()`

`effect()` はSignal変更に応じて外部副作用を行うためのものですが、**状態Aから状態Bを同期するための代替 `computed()` として使わない**のが基本です。

DOMを直接読む・書く必要がある処理には `afterRenderEffect()` があります。AngularがDOMを更新した**後**に実行され、追跡したSignalが変われば再実行されます。毎回の描画後に無条件で呼ばれるAPIではありません。一度だけの初期化なら `afterNextRender()` を使います。いずれもサーバーでは実行されず、hydrationの完了保証もありません。 ([Angular][11], [Effectガイド][37])

`afterRenderEffect()` は `earlyRead` → `write` → `mixedReadWrite` → `read` の順にphaseを実行します。DOMの書き込みは `write`、読み取りは `read` に分けるのが基本です。effect内で開始したタイマー・購読・イベントリスナー等は自動では片付かないため、`onCleanup` 等に解除処理を登録します。 ([Angular][37])

状態の派生には `computed()`、DOMを必要としない通常の外部副作用には `effect()` を使い、`afterRenderEffect()` はDOMの読み書きが必要な場合に限定します。

## `shareReplay` と `computed()` は対応させない

「共有・memoize」という印象が似ているだけで、両者の契約は異なります。

```text
shareReplay
  = Observable購読・上流処理を共有し
    過去のemitを後続subscriberへreplay

computed
  = Signal依存計算をlazyに評価しmemoize
```

`computed()` がmemoizedだからといって、`shareReplay` のSignal版ではありません。RxJS公式も `shareReplay` をReplaySubjectによるmulticast/replayとして定義しています。 ([RxJS][12])

RxJS 7.8.xの `shareReplay()` は既定でバッファ数が無制限、`refCount: false` です。`shareReplay(1)` でも `refCount` はfalseなので、購読者が0人になっても未完了の上流購読が残ります。購読者がいなくなったら未完了の上流も止めたい場合は、`shareReplay({ bufferSize: 1, refCount: true })` を使います。ただし、その後の再購読は上流処理を再実行します。 ([RxJS][12])

**成功してcompleteした値のキャッシュは `refCount: true` でも残ります**。`shareReplay` 自体はTTL、手動invalidate、stale-while-revalidate等を提供するキャッシュ機構ではありません。必要なら `share` のreset設定、Observableの再生成、Store、専用キャッシュ層等を組み合わせます。また、メソッド呼び出しごとに `http.get(...).pipe(shareReplay(...))` を作り直すと、呼び出し間では共有されません。同じ共有Observableを保持して再利用します。 ([RxJS][12])

## 最後に覚える判断軸

最初はここから逆引きするのが良いです。

| 問題                                             | まず考えるもの                                  |
| ------------------------------------------------ | ----------------------------------------------- |
| 「今の値」は何か                                 | `signal()` / Store / SignalStore                |
| 「今の値」から何を計算するか                     | `computed()` / Selector                         |
| 時間とともに通知が複数流れる                     | RxJS                                            |
| 非同期処理が重なったらどうするか                 | `switchMap()` / `mergeMap()` / `concatMap()` / `exhaustMap()`（すべて **[pipe]**） |
| Actionを中心に状態遷移を管理したい               | NgRx Store + Effects                            |
| Signalベースで構造化した状態管理が欲しい         | NgRx SignalStore                                |
| reactiveな読み取り + loading/value/errorが欲しい | Resource系                                      |
| Observable世界とSignal世界を接続したい           | `toSignal()` / `toObservable()` / `rxResource()` |

つまり最上位では、

**Signal系 = 現在値と依存関係**

**RxJS = 時間軸上の通知・非同期処理の合成と競合制御**

**NgRx Store = Actionを軸とするアプリ状態管理**

**NgRx SignalStore = Signalを軸とする構造化された状態管理**

この4つは排他的な選択肢ではありません。例えばSignalStoreで現在状態を持ち、`rxMethod` とRxJSで非同期競合を制御するなど、責務に応じて組み合わせます。SignalStoreもEvents pluginによるイベント駆動を選べます。 ([NgRx][24], [Events][39])
