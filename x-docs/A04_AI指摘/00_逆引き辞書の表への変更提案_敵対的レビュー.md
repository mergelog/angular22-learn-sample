1. 読者の「やりたいこと」から検索できる。

4. 1行に1つの主目的と判断軸を置ける。
5. 詳細なAPI仕様は既存解説へ委ね、表を目次化しない。

## 技術面と構成面の再精査

### 1. 表へ載せる基準を先に決める

提案されたAPIはすべて本文で解説済みである。

| 提案 | 既存の解説節 |
| ---: | --- |
| 1 `async` / `ngrxPush` | `Angular / NgRx: async / ngrxPush テンプレートpipe` |
| 2 `expand()` / `reduce()` | `RxJS: expand()`、`RxJS: reduce() / toArray()` |
| 3 `timer()` / `takeUntil()` / `takeWhile()` | 各operatorの解説節 |
| 4 `fromEvent()` / `from()` / `iif()` | 各Observable作成関数の解説節 |
| 5 `createActionGroup()` | `NgRx Store: createAction() / createActionGroup() / props()` |
| 6 `provideState()` / `provideEffects()` | `NgRx Store: provideStore() / provideState() / provideEffects()` |
| 7 SignalStore Events | `NgRx SignalStore: Events plugin` |
| 8 `firstValueFrom()` / `lastValueFrom()` | `RxJS: firstValueFrom() / lastValueFrom()` |

逆引き表は本文の全見出しを列挙する目次ではない。たとえば、`createActionGroup()` とSignalStore Eventsを別々の新規行にすると、既存の「状態変更の理由をイベントとして明示したい」と利用目的が重複する。API定義方法を増やすより、既存行のリンク先を具体化する方が引きやすい。

一方、ポーリングやObservableからPromiseへの変換は、現在の表から目的ベースで到達しにくく、停止条件や完了条件を誤ると実害が出る。この種の項目は新しい行を割く価値がある。

### 2. ポーリング案は技術的誤りではなく、行タイトルと選択肢の不一致

提案は次の略記を使っている。

```text
画面を離れるまで定期取得したい
timer(0, period) + takeWhile() / takeUntil(ofType(...))
ライフサイクル破棄なら takeUntilDestroyed() と区別する
```

既存本文には、正しい `switchMap()` と `takeUntil(actions$.pipe(ofType(...)))` の例、および処理結果で停止する `takeWhile()` の説明がある。そのため、略記だけを取り出して「operatorが不足している」「`takeUntil` の引数が不正」と断定するのは過剰だった。

ただし、逆引き表は単独で判断の入口になる。表へ `takeUntil(ofType(...))` という省略形をそのまま載せると、実際に渡す値がObservableであることが伝わらない。また、行タイトルは画面離脱だけを目的としているのに、選択肢には次の異なる停止契機が混在している。

- コンポーネント等の破棄: `takeUntilDestroyed()`
- Actionや別Observableの通知: `takeUntil(notifier$)`
- API結果等が条件を外れる: `takeWhile(predicate)`

追加する行は、停止方法の列挙ではなく、ポーリングそのものを主目的にする。

| やりたいこと | 判断基準 | RxJS / NgRxでの候補 |
| --- | --- | --- |
| 一定間隔でAPIを再取得したい | 前回要求を取り消すか、実行中のtickを捨てるか。停止契機は破棄・notifier・処理結果のどれか | `timer()` + `switchMap()` / `exhaustMap()`。停止は `takeUntilDestroyed()` / `takeUntil()` / `takeWhile()` |

これにより、`switchMap()` と `exhaustMap()` の競合方針も判断対象にできる。`mergeMap()` による並行実行や `concatMap()` による待ち行列は可能だが、定期取得では要求の増殖や古い結果の反映を招き得るため、既定候補として前面に出さない。

### 3. route providerの登録時機とNgRx登録の寿命を分ける

既存本文の次の記述は、そのままでは正しくない。

> routeが有効になると登録され、そのroute injectorの破棄時に解除されます。

問題は2点ある。

1. 登録は「routeが有効になった時」とは限らない。
2. route injectorを破棄しても、`provideState()` / `provideEffects()` によるNgRxへの登録が自動解除されるとは限らない。

#### 登録時機

`provideState()` と `provideEffects()` はEnvironment InitializerでNgRxへ登録する。したがって、登録時機はroute componentの表示時ではなく、routeの `EnvironmentInjector` が生成された時である。

導入済みの `@angular/router` 22.1.6では、Router preloaderもrouteの `providers` を見つけると `EnvironmentInjector` を生成する。preloadingを有効にした構成では、routeが画面へ表示される前にfeature stateやEffectsが登録され得る。

#### 登録解除

導入済みの `@ngrx/store` 22.0.1で最小実行確認した。`provideStore()` を持つroot `EnvironmentInjector` の子に `provideState({ name: "reviewProbe", reducer })` を持つ `EnvironmentInjector` を生成し、rootの `ReducerManager.reducers` を子injectorの生成前・生成後・破棄後に確認した結果は次のとおりだった。

```text
子EnvironmentInjector生成前: []
provideState()を持つ子EnvironmentInjector生成後: ["reviewProbe"]
子EnvironmentInjector破棄後: ["reviewProbe"]
```

`provideState()` はEnvironment Initializerで `ReducerManager.addFeatures()` を呼ぶが、子injectorの破棄時に対応する `removeFeatures()` を呼ばない。`StoreFeatureModule` には `ngOnDestroy()` でfeatureを削除する実装があるが、standalone APIの `provideState()` には同等の破棄処理がない。

`provideEffects()` もEnvironment Initializerでrootの `EffectSources` へeffect instanceを追加するが、NgRx 22.0.1の実装にはinjector破棄時にその登録を取り除く対称処理がない。したがって、「所有injectorが破棄されればfeature stateとEffectsも自動解除される」と説明してはいけない。

#### Angular Router側のcleanupとの関係

Angular 22では、非アクティブになったrouteの `EnvironmentInjector` を自動破棄する機能自体も `withExperimentalAutoCleanupInjectors()` によるオプトインである。導入済み実装では、このfeatureを指定したときだけ `ROUTE_INJECTOR_CLEANUP` が提供される。

ただし、このRouter featureでinjectorを破棄しても、それだけでNgRxの `ReducerManager` やrootの `EffectSources` から登録が除去されるわけではない。Angularのinjector寿命と、NgRxのグローバル登録寿命は別の問題である。

参考:

- [Angular: withExperimentalAutoCleanupInjectors](https://angular.dev/api/router/withExperimentalAutoCleanupInjectors)
- [Angular: Customizing route behavior](https://angular.dev/guide/routing/customizing-route-behavior)
- [NgRx 22.0.1: `provideState()` implementation](https://github.com/ngrx/platform/blob/22.0.1/modules/store/src/provide_store.ts)
- [NgRx 22.0.1: `provideEffects()` implementation](https://github.com/ngrx/platform/blob/22.0.1/modules/effects/src/provide_effects.ts)

既存資料では、次の関連箇所を訂正する必要がある。

- `provideStore()` / `provideState()` / `provideEffects()` 節
  - 登録はroute injector生成時であり、preloading時にも起こり得ると説明する。
  - route injector破棄時にNgRx登録が自動解除されるという説明を削除する。
- `signalStore()` とprovider範囲の節
  - component providerのSignalStoreとroute providerのSignalStoreを同じ寿命として扱わない。
  - route providerについて「画面を離れたときに状態を捨てられる」と断定しない。
  - custom `RouteReuseStrategy` がcomponentをdetachして保持する場合は、component providerも直ちに破棄されない。

逆引き表へ追加する場合は、次のように登録範囲と登録時機だけを示し、自動解除を保証しない。

| やりたいこと | 判断基準 | NgRx |
| --- | --- | --- |
| lazy routeの利用時にfeature stateとEffectsを登録したい | route injector生成時に登録され、preloadingでも生成され得る。画面離脱やinjector破棄によるNgRx登録の自動解除を前提にしない | rootは `provideStore()`、routeは `provideState()` / `provideEffects()` |

提案#6は採用できるが、既存の寿命説明を残したまま表だけ追加してはいけない。

### 4. `firstValueFrom()` と `lastValueFrom()` は、誤りではなく曖昧さを除く

提案の「必ずcomplete条件を判断基準にする」は、両APIへcompleteを要求する文とも、completeの要否でAPIを選ぶ文とも読める。既存の詳細節は次の違いを正確に説明している。

- `firstValueFrom()` は最初の値でresolveしてunsubscribeする。sourceのcompleteは不要。
- `lastValueFrom()` は最後の値を確定するため、sourceのcompleteが必要。
- 値なしでcompleteすると、`defaultValue` 未指定時はrejectする。
- 値、complete、errorのいずれも発生しないsourceではPromiseが決着しない。

したがって、技術的誤りとして扱うのではなく、表の判断基準を曖昧さのない文へ直す。

| やりたいこと | 判断基準 | RxJS |
| --- | --- | --- |
| ObservableをPromiseとして待ちたい | 最初の通知なら `firstValueFrom()`。complete時の最後の通知なら `lastValueFrom()`。終了しないsourceに注意 | `firstValueFrom()` / `lastValueFrom()` |

1つの利用目的に対する二択なので、必ずしも2行へ分割する必要はない。

### 5. `async` / `ngrxPush` は内容を直すのではなく、表から到達可能にする

既存の詳細節はすでに次の優先順位を示している。

- 新規導入ではAngular標準の `AsyncPipe` とzoneless change detectionを先に検討する。
- `@ngrx/component` はmaintenance modeである。
- 既存の `ngrxPush` は、挙動を理解したうえで維持・移行を判断する。

そのため、新たな技術訂正は不要である。逆引き表へリンクを追加し、既存説明へ到達できるようにすればよい。既存コード内の使用数は、この判断に不要なので根拠として用いない。

参考:

- [Angular: Zoneless](https://angular.dev/guide/zoneless)
- [NgRx: Push Pipe](https://ngrx.io/guide/component/push)

追加行では、`async` と `ngrxPush` を無条件に同格とせず、新規導入と既存資産の判断を短く示す。

### 6. 全ページ取得は、限定的だが逆引き価値がある

`expand()` + `reduce()` は汎用的な状態管理APIではないが、「next cursorがなくなるまで取得する」という目的からAPI名を推測しにくい。さらに、終了条件を誤ると処理が終わらず、`reduce()` はsourceがcompleteしなければ結果を出さない。このため、逆引き行を追加する価値がある。

判断基準には次を置く。

- 次ページがなければ `EMPTY` を返して終了できるか。
- ページ順を維持する必要があるか。
- 全件をメモリへ蓄積してよいデータ量か。
- 途中失敗時に全体を失敗とするか、部分結果を扱うか。

### 7. Observable作成関数4種を1行へまとめない

次のAPIは、すべてObservableを返すという共通点しかない。

- DOMイベントをObservable化する: `fromEvent()`
- 時刻を起点に通知する: `interval()` / `timer()`
- PromiseやIterableをObservable化する: `from()`
- 購読時に購読先を選ぶ: `iif()`

特に `iif()` は発生源そのものというより、購読時の分岐である。また、`from(array)` は配列要素を順に通知し、`of(array)` のように配列を1件通知するものではない。

4目的を1行へ詰め込むと「1行に1つの主目的」という基準を満たさない。個別節はすでに存在するため、利用頻度や誤用事例が明確になるまでは詳細節だけでよい。

### 8. ActionとSignalStore eventは既存行を強化する

既存表には、すでに次の利用目的がある。

> 状態変更の理由をイベントとして明示したい

ここへ次のリンクを統合すれば、提案#5と#7を新しい行へ分ける必要はない。

- NgRx Store: `createActionGroup()` → Action → Reducer
- SignalStore: `eventGroup()` / `injectDispatch()` → Events plugin

定義方法と発火方法は詳細節へ委ねる。逆引き表では「Action / Eventを使う理由」という設計判断を入口に保つ。

### 9. 既存行への追記案を整理する

| 提案 | 判定 | 理由 |
| --- | --- | --- |
| `retryWhen()` はdeprecated | 詳細節に残す | 移行情報であり、「やりたいこと」の判断基準ではない |
| 値ごとに待機時間を変えるなら `debounce()` | `debounceTime()` 行へ統合 | 同じ「入力が止まるまで待つ」という目的内の選択肢である |
| Actionや別Observableの通知まで継続するなら `takeUntil()` | 新規行にする | `takeUntilDestroyed()` とは停止契機が異なり、誤用時の影響も大きい |
| `Subscription.add()` + `ngOnDestroy` | 詳細節に残す | 新規コードの推奨ではなく、既存コードの手動管理である |

`takeUntil()` の追加行は次の形がよい。

| やりたいこと | 判断基準 | RxJS |
| --- | --- | --- |
| 別Observableの通知時に処理を停止したい | notifierが値を通知すると停止する。notifierのcompleteだけでは停止しない | `takeUntil(notifier$)` |

## 再指摘に対する再判定

追記された再指摘は、そのまま採用せず次のように判定した。

| 再指摘 | 判定 | 反映内容 |
| --- | --- | --- |
| 結論と判定表が矛盾している | 採用 | 一括反対ではなく、追加・統合・見送りを件数付きで明示した |
| ポーリングの技術指摘は既存本文を無視している | 一部採用 | 既存本文が正しい点を認め、問題を「行タイトルと略記の不一致」へ限定した |
| route injectorの指摘は訂正ではなく注記で足りる | 不採用 | 実行確認により、`provideState()` は子injector破棄後もReducerManagerへ残ると判明した。既存文は注記だけでなく訂正が必要である |
| route injectorの根拠が薄い | 不採用 | Angular 22.1.6、NgRx 22.0.1の実装確認と `provideState()` の最小実行確認で根拠を補強した |
| Promise変換の提案は誤読されている | 一部採用 | 技術的誤りという評価を撤回し、両義的な判断基準の校正へ変更した |
| `ngrxPush` の件数は再現不能で結論に不要 | 採用 | 件数を根拠から削除した |
| 表へ載せる価値を先に問うべき | 採用 | 採用基準を新設し、#4を見送り、#5と#7を既存行への統合に変更した |
| 逆引き表は39行 | 不採用 | 現在のデータ行は40行である |

## 実施する場合の変更順序

1. `provideState()` / `provideEffects()` の登録時機と登録寿命、およびSignalStoreのprovider寿命を訂正する。
2. 既存のAction / Event行へ `createActionGroup()`、`eventGroup()`、`injectDispatch()` のリンクを統合する。
3. `debounceTime()` 行へ `debounce()` の選択基準を統合する。
4. `async` / `ngrxPush`、全ページ取得、ポーリング、lazy route登録、ObservableからPromiseへの変換を追加する。
5. `takeUntil()` を `takeUntilDestroyed()` とは別の停止契機として追加する。
6. 表だけを読み、1行だけで誤ったコードや寿命保証を推測できないか再レビューする。

`fromEvent()`、`from()`、`timer()`、`iif()` をまとめた「Observableの発生源」行、`retryWhen()` の移行情報、`Subscription.add()` の手動管理は、今回の逆引き表には追加しない。
