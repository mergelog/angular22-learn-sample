# 探索戦略と読む順序

どこから読み始め、どこで読むのをやめるか。この二つを決めるのが探索戦略である。
戦略を持たない読みは、import を辿るたびに枝分かれし、深さも幅も制御できなくなる。

## 1. 三つの読み方

プログラム理解の研究では、読み手の行動が三つの型に分かれることが繰り返し観察されている。
どれが正しいということはなく、状況によって使い分ける。

| 型 | 進み方 | 向く場面 | 失敗の仕方 |
| --- | --- | --- | --- |
| 上から下へ | 全体の構造を仮定し、細部で確かめる | 構造の規約が分かっている（Angular、NgRx など） | 仮定した構造が実装と違うと、全部やり直しになる |
| 下から上へ | 個々のコードを読み、まとめて構造を組む | 規約が分からない、または壊れている | 大規模では組み上がる前に記憶が尽きる |
| 機会的 | 手がかりが出た方向へ進む | 不具合調査、実行時の観測がある場合 | 記録しないと、辿った経路が消える |

実務では機会的な読みが中心になる。
ただし、機会的な読みは経路が非線形なので、記録を取らないと成果が残らない。
記録の型は [10_記録](10_記録と資料化の型.md) にある。

上から下への読みを選べるかどうかは、フレームワークの規約がどれだけ守られているかで決まる。
本リポジトリは Angular と NgRx の規約に沿っているので、
「Action → Reducer → Selector → 画面」「Component → Template → 子 Component」という
構造を仮定してよい。仮定が成り立つぶん、上から下へ読める。

## 2. 仮説を立てて潰す

### 2-1. 反証を先に決める

仮説を立てたら、それを**否定する**観測を一つ決めてから調べに行く。
支持する観測を探しに行くと、大規模なコードベースではどんな仮説にも支持証拠が見つかる（[01](01_大規模コードリーディングで苦労する点.md) E3）。

| 仮説 | 支持を探す（遅い） | 反証を探す（速い） |
| --- | --- | --- |
| 「一覧の更新は Effects が API を叩いて行う」 | Effects を読み進める | DevTools で API 呼び出しを止め、それでも一覧が変わるか見る |
| 「この値は Store から来る」 | Selector を辿る | Store の値を DevTools で書き換え、画面が変わるか見る |
| 「この分岐は通らない」 | 呼び出し元を全部読む | ログポイントを置いて操作する |

反証のほうが速い理由は、反証が一回の観測で決まるからである。
支持は、いくつ集めても「他の経路が無い」ことを示さない。

### 2-2. 仮説の粒度

仮説は、一回の観測で真偽が決まる大きさにする。
「実験名の変更の仕組みはこうなっている」は大きすぎて検証できない。
「`(blur)` のハンドラが `tasks.service.ts` の `edit` を呼ぶ」なら、ブレークポイント一つで決まる。

## 3. 六つの探索戦略

目的に応じて選ぶ。併用してよい。

### 3-1. 一本線追跡

開始地点から処理対象まで、**分岐に立ち入らず一本だけ**辿る。
分かれ道に来たら、実際に通る側だけを選び、選ばなかった側はメモに積む。

使う場面は「この操作がどこへ届くのか」という問い。
本リポジトリにはこの形式の資料がすでに複数ある（`ngbi-*.md`）。
作り方は `bulletin` スキルとして実装されている。

速い理由は、読む量が経路の長さに比例するだけで、分岐の数に比例しないからである。
`experiments.component.ts` は 866 行あるが、一本線では数十行しか読まない。

### 3-2. 境界法

中身を読まず、境界（入出力）だけを読む。
「この層に何が入り、何が出るか」が決まれば、中身を読まずに先へ進める。

本リポジトリでの境界は次のとおり。

| 境界 | 読むもの | 読まなくていいもの |
| --- | --- | --- |
| 画面とサーバ | `business-logic/api-services/*.service.ts` のメソッド名と引数型 | メソッドの本体（生成物） |
| Component 間 | `input()` / `output()` の宣言行 | Component の本体 |
| 状態と画面 | Selector の宣言 | Reducer の本体 |
| Effect の内外 | `ofType(...)` と最後の `map(...)` が返す Action | パイプの中間 |

### 3-3. 差分法

「いま動いているもの」と「動いていないもの」、あるいは「変更前」と「変更後」の差だけを読む。
差が小さければ、差の中に原因がある。

本リポジトリでは fork 元との差分が使える。
`x-ClearML_公式とカスタマイズ済み比較.md` に既存の比較がある。
取得手順は [09_履歴と差分](09_履歴とフォーク差分から読む.md) §2。

### 3-4. テスト法

テストコードから読む。テストは、対象の使い方と期待される結果を、実行可能な形で書いた仕様である。

```bash
# 対象クラスのテストを探す
find src -name "*.spec.ts" | xargs grep -l "ExperimentsComponent"
```

本リポジトリの spec は 78 本あり、`src/app` の 1,569 ファイルに対して薄い。
テストがある箇所は運がいい、という程度に扱う。
自作機能（`features/data-catalog/`、`features/quality-pipeline/`）は
`src/tests/features/` に同じ構造でテストが置かれているので、ここは例外的に厚い。

E2E（`e2e/*.spec.ts`、6 本）のほうは画面の操作手順が書かれているので、
「この画面で何ができるか」を知るには使える。

### 3-4-1. テストを書いて読む

テストが無い箇所では、読むためにテストを一本書く手がある。
挙動を仮説として書き、通れば仮説が正しく、落ちれば実際の値が表示される。
落ちたときのメッセージが、そのまま「実際はこうである」という観測になる。

```bash
pnpm run test:unit
```

読みのためのテストは、通すことが目的ではない。挙動を固定して見ることが目的である。
仮説を確かめ終えたら消してよい。残すなら、[10_記録](10_記録と資料化の型.md) の対象にする。

同じことをブレークポイントでもできる（[05_実行時観測](05_実行時観測で読む.md) §3）。
テストのほうが向くのは、再現に手操作が何段も要る場合と、
同じ観測を何度も繰り返す場合である。

### 3-5. 実行法

読む前に動かす。詳細は [05_実行時観測](05_実行時観測で読む.md)。
静的な読みで 30 分かかることが、ブレークポイント一つで 2 分になる場面が多い。

判断の目安は、「実行して確かめられるか」を先に問うことである。
確かめられるなら、読む前に確かめる。

### 3-6. 逆引き法

結果から原因へ遡る。画面に出ている文字列、DOM のクラス名、API のリクエストパスなど、
観測できるものを検索語にする。

```bash
# 画面の文言から（UI は英語なので、見えている英語で引く）
rg -n -t ts -t html "Clear filters" src
# DOM のクラス名から
rg -n -t html 'class="[^"]*selected' src
# API のパスから
rg -n -t ts "tasks\.get_all" src
# テストIDから（テンプレートに data-id が振られている箇所がある）
rg -n -t html 'data-id="Delete Option"' src
```

画面の文言は英語である。日本語で検索しても当たらない。

## 4. 読む順序の定石

同じ量を読むなら、順序で理解の速さが変わる。

**型・データ構造を先、処理を後。** 処理は、扱うデータの形が分かっていないと意味が取れない。
本リポジトリなら `business-logic/model/` の型、あるいは Reducer の `State` インターフェースを先に読む。

**外側を先、内側を後。** 呼び出し元の文脈を知らずに実装を読むと、
なぜこの引数なのかが分からず、余計な仮説を立てることになる。

**宣言を先、本体を後。** メソッドの一覧とシグネチャだけ先に通し読みして、必要な一つに戻る。
2,331 行の `tasks.service.ts` は、この順序でしか読めない。

**現在を先、歴史を後。** 「なぜこうなっているか」は、「どうなっているか」が分かってから問う。
逆順にすると、歴史の側に説明を求めすぎて時間が溶ける。

## 5. 終了条件の書き方

調査を始める前に、終了条件を外形的な形で書く。書けないなら、問いがまだ大きすぎる。

書き方は「〜を書き出せる」の形にする。

| 悪い終了条件 | 良い終了条件 |
| --- | --- |
| 実験一覧の仕組みを理解する | 一覧データが Store に入るまでの、ファイルと行番号を 5 つ以内で並べられる |
| バグの原因を突き止める | 期待値と実測値が最初に食い違う行を、一つ指させる |
| この画面の状態管理を把握する | この画面が読む Selector を全部挙げ、それぞれの更新元 Action を言える |

終了条件を満たしたら、まだ読めそうでも閉じる。
残った疑問はメモに積む。積んだものが本当に要るなら、次の調査として立て直す。

## 6. 読まないと決める

読む量を減らす最大の手段は、読まないと決めることである。
次の四つは、目的に直結していない限り開かない。

| 対象 | 本リポジトリでの量 | 読まない理由 |
| --- | --- | --- |
| 生成された API モデル | `business-logic/model/` 584 ファイル | スキーマの写しであり、設計意図が無い |
| 生成された API クライアント本体 | `api-services/*.service.ts` の本体 | メソッド名と引数だけで足りる |
| スタイル | `*.scss` 376 ファイル | 見た目の問題を追っているときだけ開く |
| ベンダー取り込みの内部実装 | `webapp-common/angular-notifier/` など | 外部ライブラリと同じ扱いでよい |

「読まない」は「無いことにする」ではない。境界（何が入って何が出るか）は読む。
中身を読まないだけである。

## 7. 深さの制御

import を辿る深さには上限を決める。目安は 3 である。

3 段潜って答えが出ないときは、経路の選び方が間違っている。
いったん浮上して、別の入口（§3-6 の逆引き、§3-5 の実行）から入り直したほうが速い。

潜る前に、浮上できるように印を残す。
本リポジトリのファイルを開くときは、パスと行番号を `src/app/…/foo.ts:123` の形でメモに一行足す。
これだけで、3 段潜ってから戻る操作が確実になる。
