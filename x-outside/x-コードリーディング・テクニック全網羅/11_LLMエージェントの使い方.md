# LLMエージェントの使い方

コードリーディングに LLM を使うと速くなる作業と、遅くなる作業がある。
区別しないまま全部を投げると、検証に読む以上の時間がかかる。

## 1. 向く作業と向かない作業

| 作業 | 向き | 理由 |
| --- | --- | --- |
| 検索語の候補出し | 向く | 「この症状ならどんな名前が付いているか」の候補を広く出せる |
| 大きいファイルの要約 | 向く | 1,078 行の Effects から `ofType` の一覧を出す程度は確実 |
| 経路の一本線追跡 | 向く | 手順が定型で、検証もしやすい |
| 定型の資料化 | 向く | Bulletin、シーケンス図、コメント付与 |
| 生成コードの仕分け | 向く | 読む価値の無いファイルを先に除ける |
| 「なぜこうなっているか」 | **向かない** | 履歴に無い意図は、もっともらしい作り話になる |
| 正確な行番号・件数 | 条件付き | 自分でコマンドを走らせた結果なら正確。記憶から答えると誤る |
| 実行時の挙動の断定 | **向かない** | 動かさずに書かれた答えは仮説にすぎない |

判定の基準は一つである。
**その答えが、コマンド一つで検証できる形か。**
できるなら任せてよい。できないなら、答えを仮説として扱う。

## 2. コンテキストの与え方

### 2-1. 範囲を先に絞る

「ClearML のコードを読んで」では範囲が広すぎる。
`src/app` だけで 1,569 ファイルあり、全部を見ることはできない。
先に層を指定する。

```
src/app/webapp-common/experiments/ の中で、一覧データを取得する経路を追って
```

### 2-2. パスと行で指す

`experiments.component.ts` ではなく
`src/app/webapp-common/experiments/experiments.component.ts:554` と書く。
同名ファイルが多い（`models.ts` は 17 個）ので、ファイル名だけでは一意に決まらない。

### 2-3. 既知の事実を先に渡す

すでに分かっていることを渡すと、同じ調査を繰り返させずに済む。

```
分かっていること:
- 行クリックは dispatch していない（highlited Signal を直接更新している）
- experiments.component.ts:554 で update している
知りたいこと: この highlited が最終的にどの DOM 属性になるか
```

## 3. 聞き方の型

### 3-1. 答えの形を指定する

```
次の形で答えて:
1. ファイルパス:行番号
2. そこで何が起きるか（1行）
を経路順に、5地点以内で
```

形を指定しないと、説明が長くなり、検証すべき主張がどれか分からなくなる。

### 3-2. 検証手段を一緒に出させる

```
その答えを確かめるコマンドも一緒に出して
```

`rg` の検索式、ブレークポイントを置く場所、DevTools で見る箇所のいずれかが返る。
それを自分で実行する。実行できない答えは、そこで捨てる。

### 3-3. 反証を聞く

```
この仮説が誤りだとしたら、どこで分かる？
```

支持する証拠より、反証の観測を一つ得るほうが速い（[03](03_探索戦略と読む順序.md) §2-1）。

## 4. 答えの検証

LLM の答えのうち、次の三つは必ず自分で確かめる。

| 主張 | 確かめ方 |
| --- | --- |
| 「〜というファイルがある」 | `ls` か `rg -l` で存在を確認 |
| 「〜行目で〜している」 | その行を開く |
| 「〜は使われていない」 | `rg -l` で参照数を数える |

行番号は特にずれる。ファイルが変更されていれば当然ずれるし、
変更されていなくても推測で書かれていることがある。

件数（「〜は 12 箇所ある」）は、コマンドの出力として提示されていれば信用してよい。
根拠のコマンドが示されていなければ、自分で数える。

## 5. このリポジトリで使えるスキル

コードリーディングに直接使えるものが四つある。

| スキル | 呼び方 | 出力 |
| --- | --- | --- |
| 一本線追跡 | `/bulletin {処理内容}` または `/ngbi {処理内容}` | `ngbi-*.md`（結論・全体図・N地点） |
| 同上（JSON） | `/bulletin-json {処理内容}` | `ngbi-*.json` |
| コンポーネント関係ツリー | `/ngmaze {コンポーネント名}` | `ng-maze-*.md` |
| 参照元の逆引き図 | `/madge-to {パス}` | `madge-rdeps-*.md` |

`ngmaze` と `madge-to` は、内部でコマンドを実行して結果を整形する。
出力が実測なので、LLM の推測が入らない。この二つは検証の手間が少ない。

`bulletin` は LLM がコードを読んで書くので、§4 の検証が要る。
`--code` を付けると、資料からリンクした実コード行に注記が入るので、
資料と実コードの対応が後から確認しやすくなる。

チャットの接頭辞も定義されている（`CLAUDE.md`）。

| 接頭辞 | 動作 |
| --- | --- |
| `az {パス}` | そのファイルの全文に末尾解説コメントを付けた `{パス}.code.md` を作る |
| `sq {パス}` | シーケンス図を `x-sequense/` に作る |
| `cm lv{n} {パス}` | コードにコメントを追加（lv1 クラス・メソッド、lv2 メンバーまで、lv3 具体的に） |
| `rv {文字列}` | 敵対的レビューを実施し、指摘を即時適用 |

`az` は、初めて読む大きいファイルで使う。
全文が残るので、コメントだけ信用せずに済む。

## 6. 失敗の型

| 型 | 症状 | 対処 |
| --- | --- | --- |
| もっともらしい作り話 | 存在しない関数名・行番号が返る | §4 の検証。存在確認を先に打つ |
| 範囲外の一般論 | Angular 一般の説明が返り、このコードの話にならない | パスで範囲を指定し直す |
| 網羅への逸脱 | 聞いていない周辺まで説明される | 答えの形を指定する（§3-1） |
| 古い前提 | Angular の旧 API（`@Input()` など）で説明される | 版を明示する。Angular 22・NgRx 22・TypeScript 6 |
| 検証不能な断定 | 「〜のはずです」で終わる | 「確かめるコマンドは」と聞き返す |

四つ目は本リポジトリで実際に起きやすい。
`input()` 934 箇所に対して `@Input()` 153 箇所という混在状態なので、
どちらの前提で説明されているかを毎回確かめる。

## 7. 任せる範囲の決め方

LLM に任せる作業は、**検証が実行より安い**ものに限る。

| 作業 | 実行の手間 | 検証の手間 | 任せるか |
| --- | --- | --- | --- |
| 1,078 行の Effects から `ofType` 一覧を出す | 5分 | `rg` 1回 | 任せる |
| ある Action の dispatch 元を全部挙げる | 3分 | `rg` 1回 | 任せる（自分でやっても同じ速さ） |
| 経路を一本追う | 40分 | 地点ごとに開く（10分） | 任せる |
| 「なぜこの設計か」 | — | 検証不能 | 任せない |
| 不具合の原因の断定 | — | 再現で確かめる必要がある | 仮説として受け取る |

二行目のように、自分でやっても同じ速さの作業は、任せる意味が薄い。
`rg` 一回で済むことを頼むと、往復のほうが長くなる。

## 8. 記録との接続

LLM に追わせた経路も、記録しなければ残らない。
`/bulletin` の出力はファイルとして残るので、この点で有利である。
チャットの中だけで完結した調査は、閉じれば消える。

形式は [10_記録](10_記録と資料化の型.md) に合わせる。
