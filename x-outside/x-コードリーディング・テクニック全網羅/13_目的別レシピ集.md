# 目的別レシピ集

調査の目的ごとに、手順・道具・終了条件を並べる。
各レシピは他の章を参照するので、手順だけ追えば済むようにしてある。

所要時間の目安は、このコードベースに慣れた状態での値である。初回はこの 2〜3 倍かかる。

---

## R1. 画面の不具合の原因を特定する

**所要** 20〜60分　　**終了条件** 期待値と実測値が最初に食い違う行を一つ指させる

| 段 | やること | 道具 |
| --- | --- | --- |
| 1 | 再現手順を確定する。何をすると必ず起きるか | 手操作 |
| 2 | バックエンドが生きているか確かめる | `pnpm run backend:status` |
| 3 | Network タブを開いて操作する。リクエストが出るか、ペイロードとレスポンスは期待どおりか | DevTools |
| 4 | Redux DevTools で流れた Action を見る。期待する Action が出ているか | Redux DevTools |
| 5 | 出ていなければ dispatch 元、出ていれば Reducer の diff を見る | Redux DevTools |
| 6 | Store に正しい値が入っていれば、画面側（Selector・テンプレート・Signal）を見る | Angular DevTools |

3 から 6 は、[08](08_バックエンド境界とAPIの読み方.md) §4 の五段と同じ切り方である。
各段が一つの観測で決まるので、コードを読む前にこれを通す。
通し終えると、読む範囲が一段ぶんに絞れる。

**先に疑うもの** — 永続化（localStorage の 6 キー、[12](12_時間を溶かす罠とアンチパターン.md) §2-4）、
購読が切れていない箇所（`takeUntilDestroyed` が無い `.subscribe(`）、
`mergeMap` による順序の入れ替わり（252 箇所）。

## R2. 「この値はどこから来るか」を調べる

**所要** 10〜30分　　**終了条件** 値の出所から画面までの鎖を、4 地点以内で並べられる

| 段 | やること |
| --- | --- |
| 1 | 画面で値を右クリックして Elements で要素を選ぶ。`sm-` で始まる祖先タグを探す |
| 2 | そのタグ名でコンポーネントを特定（`rg -n -t ts "selector: 'sm-…'" src`） |
| 3 | テンプレートで、その値がどの式から来るか見る |
| 4 | クラスで式の宣言を開く。`computed()` なら上流へ、`input()` なら親へ、`toSignal()` なら Observable へ |
| 5 | Observable に出たら Selector を特定し、Reducer と Action へ |

置き場所の判定に迷ったら [07](07_状態と非同期の読み方.md) §2 の表を使う。
リロードして残れば永続化、URL を変えて変われば URL である。

## R3. 「この操作はどこへ届くか」を調べる

**所要** 30〜60分　　**終了条件** 一本線の経路を、ファイルと行番号で並べられる

| 段 | やること |
| --- | --- |
| 1 | 操作の直前に Redux DevTools をクリアし、操作して流れた Action を全部見る |
| 2 | Action を一つ選び Trace タブで dispatch 元の行を取る（`trace: true` が有効） |
| 3 | Action 名を素のまま検索して、定義・Reducer・Effect をまとめて出す |
| 4 | Effect の `ofType` と、最後に返す Action だけ読む。中間のパイプは飛ばす |
| 5 | Network タブで、その経路で出たリクエストのパスを取る |
| 6 | パスで `business-logic/api-services/` を検索して到達点を確定する |

```bash
rg -n -t ts "setSelectedExperiments" src            # 段3
rg -n -t ts "tasks\.get_all_ex" src                 # 段6
```

資料にするなら `/bulletin {処理内容}` を使う。既存の例が 3 本ある。

## R4. 機能を追加する前の下調べ

**所要** 60〜120分　　**終了条件** 触るファイルの一覧と、それぞれの変更内容を一行ずつ書ける

| 段 | やること |
| --- | --- |
| 1 | 似た機能を一つ選び、R3 でその経路を通す |
| 2 | その機能が触っているファイルを層ごとに分類する（routes / providers / actions / reducer / effects / component / template / api） |
| 3 | 境界規則を確認する。`web-boundaries.json` と `node scripts/web-boundaries.mjs report` |
| 4 | 置き場所を決める。取り込み層（`webapp-common/`）には足さない |
| 5 | 既存の設計資料を引く。`docs/phase7_チーム開発標準/61_アーキテクチャ規約.md` |

段 4 の原則は明示されている。
`web-boundaries.json` に「共有するものは `src/app/shared` へ置く。
`webapp-common` はベンダー由来の凍結領域なので足さない」とある。

Effects の置き場所についても指定がある。更新対象 state の feature 配下に置く。

## R5. 変更の影響範囲を調べる

**所要** 20〜40分　　**終了条件** 影響を受けるファイルを列挙し、それぞれに理由を付けられる

| 段 | やること | 道具 |
| --- | --- | --- |
| 1 | 型で結ばれた参照を出す | VS Code の「参照の検索」（Shift+F12） |
| 2 | 型で結ばれていない参照を出す | `rg` で Action 名・セレクタ名・文字列キー |
| 3 | 図にする | `node .claude/skills/madge-to/scripts/madge-to.mjs {パス}` |
| 4 | テンプレートでの使用を出す | `rg -n -t html "<sm-…" src` |
| 5 | 循環に入っていないか見る | `npx madge … --circular src/app` の出力を引く |

段 2 を飛ばすと漏れる。
このコードベースでは、DI・Action・テンプレート・`pTemplate` の四つが型の外で結ばれている。

## R6. 差分を読む（レビュー前）

**所要** 15〜40分　　**終了条件** 各変更について「何を変えたか」と「なぜそれで足りるか」を言える

| 段 | やること |
| --- | --- |
| 1 | `git diff --stat` で規模と層を見る。取り込み層に差分があれば理由を確認する |
| 2 | 変更されたファイルの層を分類する（自作 / 取り込み / 生成 / 設定 / 資料） |
| 3 | 設定とビルドの差分を先に読む（`angular.json`、`*.providers.ts`、`tsconfig*`）。挙動全体に及ぶ |
| 4 | 次に境界の差分（API サービス、Action 定義、Selector）。ここは他へ波及する |
| 5 | 最後にコンポーネント内部。波及しない |
| 6 | 検査を走らせる |

```bash
pnpm run verify:web     # Angular 側の検査一式
pnpm run web:boundaries # 依存境界
pnpm run web:lint:baseline
```

読む順序を 3→4→5 にするのは、波及の大きい順に読むためである。
逆順に読むと、コンポーネントの差分を読んでいる最中に前提が変わる。

## R7. 上流の更新を取り込む前に差分を読む

**所要** 30〜90分　　**終了条件** 取り込むか見送るかの判断と、その理由を書ける

| 段 | やること |
| --- | --- |
| 1 | 上流が進んだか検査する（`pnpm run upstream:status`） |
| 2 | 上流を取得する（`git fetch upstream --filter=blob:none --tags`） |
| 3 | 記録済みコミットから現在までの差分を見る（`git log v2.5..upstream/master --oneline`） |
| 4 | 手元で触っているファイルと重なるか見る |
| 5 | 判断し、`upstream.json` の `recorded` を書き換える |

段 5 の書き換えは「見た」という記録であり、取り込んだという記録ではない。
この区別は `upstream.json` の `$comment` に明記されている。
判断の基準は `docs/phase1_上流設計/03_方式設計書.md` §4.15 にある。

## R9. 遅い理由を調べる

**所要** 30〜60分　　**終了条件** 時間を使っている箇所を、通信・描画・計算のどれかに特定できる

| 段 | やること | 道具 |
| --- | --- | --- |
| 1 | 通信か描画かを切り分ける | Network タブの時間と、操作から反映までの体感の差 |
| 2 | 通信なら、本数と順序を見る。二段取得になっていないか | Network タブ |
| 3 | 描画なら、変更検知の回数を見る | Angular DevTools のプロファイラ |
| 4 | 再計算が多いなら、`computed()` の依存を見る | コード |
| 5 | 一覧が重いなら、仮想スクロールとページングの実装を見る | `docs/sequense/02_状態保持/02-06_スクロールIDとページング.md` |
| 6 | バンドルが大きいなら | `pnpm run bundle-report` |

段 3 で `mergeMap`（252 箇所）が絡んでいると、同じ取得が重複していることがある。

## R11. 大きいファイルを読む

**所要** 20〜60分　　**終了条件** そのファイルの役割と、目的に関係する一塊を特定できる

対象は 500 行を超えるファイル（`tasks.service.ts` 2,331 行、
`common-experiments-view.effects.ts` 1,078 行、`experiments.component.ts` 866 行など）。

| 段 | やること |
| --- | --- |
| 1 | 先頭 30 行を読む。import の顔ぶれで、どの層と関わるかが決まる |

```bash
rg -n "ofType\(" src/app/webapp-common/experiments/effects/common-experiments-view.effects.ts
rg -n "^\s+(public |protected |private )?[a-zA-Z]+\(" src/app/webapp-common/experiments/experiments.component.ts
```

## R12. 見た目の崩れを調べる

**所要** 15〜40分　　**終了条件** 効いているスタイル宣言を一つ指させる

見た目の問題は、TypeScript を読んでも出てこない。DevTools から入る。

| 段 | やること |
| --- | --- |
| 1 | Elements で要素を選び、Computed で実際に効いている値を見る |
| 2 | Styles で、その値を書いている宣言と、上書きされて消えた宣言を見る |
| 3 | 宣言のファイル名から、コンポーネントの `.scss` か共通スタイルかを判定する |
| 4 | 共通スタイルなら `webapp-common/styles/` を見る |
| 5 | PrimeNG 由来なら、テーマの定義を見る（`webapp-common/styles/prime.preset.ts`） |

スタイルの置き場所は三層ある。

| 層 | 場所 | 数 |
| --- | --- | --- |
| コンポーネント固有 | `*.component.scss` | 315 |
| 共通スタイル | `webapp-common/styles/`（`layout.scss`、`clearml-palette.scss`、`mixins/` ほか） | — |
| PrimeNG のテーマ | `webapp-common/styles/prime.preset.ts`（`app.config.ts` の `providePrimeNG` で登録） | 1 |

自作側の上書きは `src/app/shared/custom-styles.scss` にある。
取り込み層の `.scss` を直す前に、こちらで済まないかを見る。
