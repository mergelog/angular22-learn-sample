# 大規模コードリーディングで苦労する点

苦労は分散していない。いくつかの型に偏っている。
型が分かれば、詰まったときに「いま何の型に嵌まっているか」を判定でき、そこから出口のファイルへ直行できる。

この章は、その型を七つの原因系に分けて並べる。
各項は、症状（読み手に何が起きるか）・機構（なぜそうなるか）・本リポジトリでの実例・出口の順で書く。
実例はすべて、この fork の実コードから取っている。
E（読み手の側で起きる詰まり）には実例を置いていない。コードの側に現れる現象ではないからである。
F（情報環境）には機構を置いていない。原因がそのまま症状になっており、説明する段が無い。

## A. 規模そのものが生む詰まり

### A1. 入口が分からない

**症状** — リポジトリを開いたが、最初に開くファイルが決まらない。
ディレクトリ名から当たりを付けて開き、数ファイル読んで、また別の当たりを付ける。これを繰り返す。

**機構** — 大規模コードベースには入口が複数ある。起動の入口（`main.ts`）、画面の入口（ルート定義）、
データの入口（API クライアント）、操作の入口（イベントハンドラ）が別々の場所にあり、
「何を知りたいか」によって正しい入口が変わる。目的を決めずに開くと、どの入口も正しく見えない。

**実例** — 本リポジトリには `src/main.ts`（起動）、`src/app/app.routes.ts`（画面）、
`src/app/business-logic/api-services/`（API）、`src/app/features/*/…routes.ts`（機能ごとの画面）の
四系統の入口がある。「実験一覧が出るまで」を追うなら二番目から、
「実験名の変更がサーバへ届くまで」を追うなら四番目から入る。一番目から入ると遠回りになる。

**出口** — 目的を一文に書いてから入口を選ぶ。入口の対応表は [02_全体地図](02_全体地図の作り方.md) §2 にある。

### A2. 全体像が持てない

**症状** — 個々のファイルは読めるのに、読み終えても「で、全体はどうなっているのか」が言えない。

**機構** — 人が同時に保持できる項目は数個である。
30 ファイルを順に読んでも、読み終えた時点で頭に残るのは最後の数ファイルだけになる。
構造を保持しているのは記憶ではなく、外部に書いた図や表である。

**実例** — `src/app` 配下の 1,569 ファイルは、読んで覚える対象ではない。
覚えるのは「`webapp-common` が取り込み元の本体（77,967 行、全体の 66%）、
`features` がその上書き層（6,510 行、5.5%）、`business-logic` が生成された API 層（27,139 行）」という
三つの比率だけである。この三つを持っていれば、開いたファイルのパスから役割が即座に決まる。

**出口** — 読みながら図を書く。書かずに読むと残らない。[10_記録](10_記録と資料化の型.md) §2。

### A3. 打ち切り基準がない

**症状** — 答えは出たはずなのに、確信が持てず読み続ける。あるいは、どこまで読めば確信できるのかが分からない。

**機構** — 「理解した」は主観であり、そのままでは終了条件にならない。
終了条件は、読む前に外形的な形で決めるしかない。決めていないと、終わりは疲労でしか訪れない。

**実例** — 「実験名の変更が一覧に反映される経路」を追う調査なら、終了条件は
「入力欄の `(blur)` から `tasks.service.ts` の `update` 呼び出しまで、
中継するファイル名と行番号を順に書き出せる」と書ける。書けた時点で閉じる。
効果として速くなる理由は、途中で現れる周辺（バリデーション、楽観更新、エラー処理）へ
立ち入らずに済むからである。

**出口** — [03_探索戦略](03_探索戦略と読む順序.md) §5 に、終了条件の書き方を置いた。

### A4. 同名ファイル・同名シンボルの衝突

**症状** — エディタのファイル検索に同じ名前が並び、どれを開けばいいか決まらない。

**機構** — 層を分けた設計では、同じ役割のファイルが層ごとに同じ名前で置かれる。
名前は役割を表すので、層が増えると必然的に重複する。ファイル名だけでは層を判別できない。

**実例** — `models.ts` はこのリポジトリに 17 個ある。`tasks.service.ts` は 2 個
（`business-logic/api-services/`（生成された API クライアント）と、`webapp-common/tasks/` 配下）。
`login.service.ts` は 3 個ある。

**出口** — ファイル名ではなくパスで検索する。手順は [04_静的探索](04_静的探索の道具と手順.md) §3。

### A5. 生成コードと手書きコードの混在

**症状** — 丁寧に読んだファイルが、実は機械生成で、読む価値がほとんどなかった。

**機構** — 生成コードは人間向けに書かれていない。
命名も構造も生成器の都合で決まっており、そこから設計意図を読み取ろうとしても何も出てこない。
にもかかわらず見た目は普通の TypeScript なので、開いた時点では区別がつかない。

**実例** — `src/app/business-logic/model/` の 584 ファイルは ClearML の API スキーマからの生成物である。
`tasks.service.ts` の 2,331 行も同様で、リポジトリ最大のファイルだが、読むべきは
「どのメソッドがあるか」だけであり、本文を読む意味はない。

**出口** — 生成物の一覧を先に把握する。[14_地形図](14_ClearML地形図.md) §3 に境界を書いた。

## B. 間接性が生む詰まり

間接性は、静的な読みで追えるつながりを切る。切れ方が六通りある。

### B1. 呼び出し元が静的に辿れない

**症状** — あるメソッドの中身は読めたが、誰がいつ呼ぶのかが分からない。

**機構** — DI、イベント、コールバック、フレームワークによる呼び出しでは、
呼び出し側のコードに呼び出し先の名前が現れない。参照検索が空振りする。

**実例** — Effects クラスのメソッドはどこからも呼ばれていない。
`provideEffects([...])` に登録された結果、NgRx が Action の流れに応じて起動する。
`src/app/core/core.providers.ts` に 7 個、`src/app/features/experiments/shared/experiments.providers.ts` に
さらに複数が登録されており、登録場所を見ないと起動主体が分からない。

**出口** — 登録側から探す。手順は [07_状態と非同期](07_状態と非同期の読み方.md) §4。
実行時に確定させる手段は [05_実行時観測](05_実行時観測で読む.md) §3。

### B2. 文字列による結合

**症状** — 定義へジャンプできない。文字列が一致するはずなのに、検索結果に定義が出てこない。

**機構** — 型で結ばれていない結合は、エディタの参照解決の対象外になる。
文字列の一致は実行時にしか成立しない。

**実例** — NgRx の Action は型名ではなく文字列で識別される。本リポジトリには `createAction` が 666 個ある。
さらに、同じ名前の定数が別の値で複数定義されている箇所がある。

| 定数名 | 定義場所 | 値 |
| --- | --- | --- |
| `EXPERIMENTS_INFO_PREFIX` | `webapp-common/experiments/actions/common-experiments-menu.actions.ts:8` | `'[EXPERIMENTS INFO] '` |
| `EXPERIMENTS_INFO_PREFIX` | `webapp-common/experiments/actions/common-experiments-info.actions.ts:41` | `'[Experiments Info ]'` |
| `MODELS_PREFIX` | `webapp-common/models/actions/models-info.actions.ts:10` | `'MODELS_INFO_'` |
| `MODELS_PREFIX` | `webapp-common/models/actions/models-view.actions.ts:12` | `'MODELS_'` |
| `MODELS_PREFIX` | `webapp-common/models/actions/models-menu.actions.ts:5` | `'[MODELS_MENU] '` |

名前が同じで値が違うため、定数名で当たりを付けると誤ったファイルに着地する。

**出口** — [04_静的探索](04_静的探索の道具と手順.md) §4 に、文字列結合を追う検索式を置いた。

### B3. 実行時に組み立てられる識別子

**症状** — DevTools に出ている文字列でリポジトリを検索しても、一件も当たらない。

**機構** — 識別子がテンプレートリテラルで組み立てられていると、ソース上にその文字列は存在しない。

**実例** — `` createAction(`${SELECT_MODEL_PREFIX} set models`) `` のような書き方が 23 箇所ある。
`SELECT_MODEL_PREFIX` の値は `'[select model]'` なので、DevTools には
`[select model] set models` と表示される。この文字列で検索しても 0 件である。

**出口** — 前半（プレフィクス）を捨て、後半の固定部分だけで検索する。
`rg -n -t ts "set models" src` なら当たる。[04_静的探索](04_静的探索の道具と手順.md) §4-2。

### B4. ビルドによる差し替え

**症状** — 読んだコードが、本番では実行されていない。あるいはその逆。

**機構** — ビルド構成がファイルを丸ごと差し替えると、ソースツリー上の見た目と実行内容が一致しなくなる。
差し替えの宣言はビルド設定側にあり、差し替えられるファイル自身には何も書かれていない。

**実例** — `angular.json` の `fileReplacements` により、本番ビルドでは
`src/app/build-specifics/index.ts` が `index.prod.ts` に差し替わる。
前者は Redux DevTools を登録し、後者は空配列である。
`src/environments/environment.ts` も同様に差し替わる。

**出口** — `angular.json` の `fileReplacements` を最初に読む。[12_罠](12_時間を溶かす罠とアンチパターン.md) §2-1。

### B5. 差し込み口（シーム）の層

**症状** — `features` 側のクラスを開いたら中身が空だった。あるいは、共通実装を読んだが、
実際に呼ばれているのは `features` 側の包み込み実装だった。

**機構** — 上流を fork して上書きする設計では、上書きのための空き場所を先に用意する。
用意された空き場所は、この版では埋まっていないことがある。
埋まっている場合も、継承ではなく委譲（共通実装をコンストラクタで受け取って包む）で書かれていると、
クラス名からは親子関係が読み取れない。

**実例** — `features` 配下 103 ファイルのうち 25 ファイルが 15 行未満である。
`features/experiments/effects/experiments-info.effects.ts` は 6 行で、
コンストラクタが空のクラスが一つあるだけだが、`experiments.providers.ts` の
`provideEffects([...])` にはしっかり登録されている。
`features/experiments/actions/experiments-info.actions.ts` に至っては 0 行である。

埋まっている側の例が `features/experiments/shared/services/experiment-converter.service.ts` で、
これは `CommonExperimentConverterService` を継承せず、コンストラクタで受け取って
`convertCommonExperiment()` を呼んだ結果に加工を足す。
providers には両方が並んで登録されており（`ExperimentConverterService` と
`CommonExperimentConverterService`）、片方がもう片方を置き換えているわけではない。
`extends Common*` の形は 4 箇所しかなく、その 4 件はすべて State のインターフェースである
（`ProjectsState` `ExperimentInfoState` `ViewState` `CommonProjectReadyForDeletion`）。
クラスの継承による上書きは 0 件である。

**出口** — クラス名の一致から親子関係を推測しない。providers の登録内容と、
コンストラクタ引数を読む。手順は [06_Angular固有](06_Angular固有の読み方.md) §6。

### B6. 動的コンポーネント生成

**症状** — 画面に出ている部品が、テンプレートを検索しても見つからない。

**機構** — `createComponent` や `ViewContainerRef` で組み立てた部品は、
どのテンプレートにもタグとして現れない。

**実例** — `createComponent` の呼び出しが 57 箇所ある。
加えて `ngTemplateOutlet` が 49 箇所、`pTemplate` が 32 箇所あり、
テンプレートの実体と表示位置が別ファイルに分かれている。

**出口** — 実行時に DOM から逆引きする。[05_実行時観測](05_実行時観測で読む.md) §4。

## C. 時間軸が生む詰まり

### C1. 履歴が潰れている

**症状** — `git blame` を打っても、全行が同じ一つのコミットを指す。変更の理由が取れない。

**機構** — fork を取り込むときに履歴を潰すと、取り込み前の変更履歴が消える。
残るのは「取り込んだ」という一点だけになる。

**実例** — 本リポジトリのコミットは 23 個しかない。
`webapp-common/experiments/experiments.component.ts`（866 行）の履歴は
`9c545f9 change directory` の一件だけで、実装の意図は何も取れない。

**出口** — 上流のリポジトリを取得し、そちらで履歴を引く。
`upstream` リモートは登録済みだが未取得なので、取得が先に要る。
手順は [09_履歴と差分](09_履歴とフォーク差分から読む.md) §2。

### C2. 由来が分からない

**症状** — このコードを直していいのか、上流由来だから触らないほうがいいのかが判断できない。

**機構** — 取り込んだコードと自作コードが同じツリーに同居していると、パスだけでは判別できない。
判別できないと、読むときの注意の配分（設計意図を探すのか、上流の都合として受け入れるのか）も決まらない。

**実例** — 本リポジトリでは `webapp-common/` が取り込み由来の凍結領域、
`features/` `core/` `shared/` `layout/` が自作側という切り分けになっている。
この切り分けは `web-boundaries.json` の規則の記述に書かれている。

**出口** — [09_履歴と差分](09_履歴とフォーク差分から読む.md) §4 に、由来の判定手順を置いた。

### C3. 死んだコードが生きて見える

**症状** — 読んで理解したコードが、実際には一度も実行されない。

**機構** — 到達不能なコードは、構文上は正しいままそこに残る。
参照数を確認しない限り、読んでいる間は生きているコードと区別がつかない。

**実例** — `src/app/features/experiments/shared/experiment-shared.config.ts` は
`EXPERIMENT_CONFIG_TOKEN` と providers 一式を定義しているが、これを import しているファイルは無い。
実際に使われているのは、ほぼ同じ内容を持つ `experiments.providers.ts` のほうである。
同じトークン名が二箇所に定義されているため、名前で検索すると死んだ側に当たる可能性がある。

もう一件、`CustomReuseStrategy` が `app.config.ts` で登録されているが、
このクラスは `route.data.reuse` が真のときだけ経路を保持する実装であり、
`data: {reuse: true}` を指定したルートはリポジトリ内に一つも無い。登録されているが働いていない。

**出口** — 読む前に参照数を数える。[04_静的探索](04_静的探索の道具と手順.md) §5-2。

### C4. コメントとドキュメントの腐敗

**症状** — コメントの説明どおりに動かない。

**機構** — コメントはコンパイルされないので、コードが変わっても機械的には壊れない。
壊れないものは直されない。

**実例** — `webapp-common/core/router-reuse-strategy.ts` の JSDoc には
"I believe the boolean is indicating to a controller whether or not to fire this.store" とある。
書き手自身が推測で書いており、仕様の記述ではない。

**出口** — コメントは仮説として扱い、コードで裏を取る。[12_罠](12_時間を溶かす罠とアンチパターン.md) §3。

### C5. 命名が実態と合っていない

**症状** — 名前から想像した役割と、中身が違う。

**機構** — 名前は最初の設計時点の役割を指しており、後から役割が増えても名前は変わらないことが多い。

**実例** — `business-logic/` は、名前に反してビジネスロジックを持たない。
中身は API クライアントと生成モデルである（607 ファイル中 584 が生成モデル）。
`webapp-common/` の `common` は「共通部品」ではなく「取り込み元の本体」を指す。

**出口** — 名前ではなく中身の実測で地図を作る。[02_全体地図](02_全体地図の作り方.md) §3。

## D. 実行時性が生む詰まり

### D1. 状態の置き場所が複数ある

**症状** — 値がどこから来たのか分からない。更新したのに画面が変わらない、またはその逆。

**機構** — 同じ画面の状態が複数の場所に分散していると、
どこを読めばいいかは「その値がどの置き場所に属するか」を知らないと決まらない。
置き場所の一覧を持っていない読み手は、全部を疑うことになる。

**実例** — 本リポジトリの状態は五箇所に分かれている。

| 置き場所 | 典型 | 見分け方 |
| --- | --- | --- |
| NgRx Store | 一覧データ、選択、フィルタ | `store.select(...)` が 928 箇所 |
| Component の Signal | ハイライト、開閉、一時的な編集値 | `signal()` 125 箇所、`computed()` 328 箇所 |
| URL | プロジェクトID、タブ、一部のフィルタ | ルート定義とクエリパラメータ |
| localStorage | 画面をまたいで残る設定 | `_saved_*_state_` の 5 キー |
| サーバ側のユーザ設定 | 列構成、並び順 | `UserPreferences` 経由 |

`_saved_experiment_state_` などの localStorage への保存は meta-reducer が行っており、
Reducer を読んでも保存処理は出てこない。

**出口** — [07_状態と非同期](07_状態と非同期の読み方.md) §2。

### D2. 非同期の順序が読めない

**症状** — コードの上下と、実行の順序が一致しない。

**機構** — Observable のパイプは、定義の順序ではなく購読と発火の順序で動く。
`switchMap` と `mergeMap` では並行性が違い、前者は前の処理を打ち切る。
コードを目で追うだけでは、どちらの意味で書かれているかは分かっても、実際にどちらが起きたかは分からない。

**実例** — `.pipe(` が 1,060 箇所、`switchMap` 340、`mergeMap` 252、`withLatestFrom` 61。
Effects の中でこれらが連なっており、最大は `common-experiments-view.effects.ts` の 1,078 行である。

**出口** — 実行時に確定させる。[05_実行時観測](05_実行時観測で読む.md) §2。読み方は [07_状態と非同期](07_状態と非同期の読み方.md) §5。

### D3. 変更検知のタイミング

**症状** — 値は変わっているのに画面が更新されない。またはその理由が説明できない。

**機構** — Angular の再描画は代入の瞬間ではなく、変更検知が走った時点で起きる。
Signal と Observable と素のフィールドで、検知のされ方が違う。

**実例** — 本リポジトリは Signal ベースの入出力（`input()` 934 箇所、`output()` 385 箇所）と、
旧来のデコレータ（`@Input()` 153 箇所）が混在する。`toSignal` による変換も 76 箇所ある。
同じコンポーネントの中で両方が使われていることがあり、更新の伝わり方が項目ごとに違う。

**出口** — [06_Angular固有](06_Angular固有の読み方.md) §5。

### D4. 通りうる経路と、実際に通る経路の混同

**症状** — 分岐を全部読んで疲れる。読み終えても、実際に通った経路が分からない。

**機構** — 静的な読みは、通りうる経路をすべて等しく扱う。
実際の入力では大半の分岐が通らないが、読んでいる間はその区別がつかない。

**実例** — `webapp-common/experiments/effects/common-experiments-view.effects.ts` には
`ofType(` が 28 箇所ある。つまり 28 種類の Action に反応しうる。
一覧を開くという一つの操作で実際に動くのはそのうち数本であり、
残りは別の操作のためのものである。28 本すべてを読むと、
そのほとんどが目的の症状と関係しないまま時間が過ぎる。

**出口** — ブレークポイントかログで、実際に通る経路だけを確定してから読む。
[05_実行時観測](05_実行時観測で読む.md) §2。

## E. 読み手の側で起きる詰まり

### E1. 目的の喪失

**症状** — 三段潜ったところで、何を調べていたのか思い出せない。

**機構** — 潜るたびに新しい問いが生まれ、元の問いを押し出す。
押し出された問いは、書いていなければ戻ってこない。

**出口** — 調査の冒頭に一行で問いを書き、開いたまま置く。[10_記録](10_記録と資料化の型.md) §3。

### E2. 中断からの復帰コスト

**症状** — 昼休みや会議から戻ると、再構築に 15 分かかる。

**機構** — 頭の中に組み上げた構造は、中断で失われる。外に出していなければ、組み直すしかない。

**出口** — 中断の前に、いま分かっていることを三行で書く。書く時間は 1 分で、復帰は 1 分になる。

### E3. 最初の仮説に固執する

**症状** — 仮説に合う証拠ばかり集め、合わない箇所を例外として処理し続ける。

**機構** — 仮説を立てた直後は、それを支える証拠のほうが目に入りやすい。
大規模なコードベースでは、どんな仮説にも支持証拠が見つかるので、この傾向が抑制されない。

**出口** — 仮説を立てたら、それを**否定する**観測を一つ決めてから調べに行く。
[03_探索戦略](03_探索戦略と読む順序.md) §2-1。

### E4. 深追い

**症状** — 本筋と関係のない実装の細部に 40 分使った。

**機構** — 個々のコードは、それ自体として面白い。面白さは、目的との距離を測らない。

**出口** — 時間を区切る。逸れた先は「あとで読む」として別に積む。[15_読解の管理](15_読解の管理と習熟.md) §2。

### E5. 読んだつもり

**症状** — 理解したと思っていたが、説明しようとすると言葉が出ない。

**機構** — コードを目で追う作業は、内容を再構成する作業より負荷が低い。
負荷が低い作業は、進んでいる感覚だけを与える。

**出口** — 読み終えたら、図か三行の要約を書く。書けなければ読めていない。[10_記録](10_記録と資料化の型.md) §2。

### E6. 記憶の劣化

**症状** — 二週間前に調べた経路を、また最初から調べている。

**機構** — 一度きりの探索で得た知識は、参照されなければ数日で使えなくなる。

**出口** — 経路を資料として残し、次の調査でその資料から入る。[10_記録](10_記録と資料化の型.md) §4。

## F. 情報環境が生む詰まり

### F1. 検索ノイズ

**症状** — 検索結果の大半が `node_modules` や `dist` で、目的の行が埋もれる。

**実例** — 本リポジトリのルート直下には `node_modules`（437 パッケージ）、`dist`、`build`、
`.angular`、`.venv`、`reports`、`test-results` がある。
`.vscode/settings.json` の `search.exclude` でこれらは除外済みだが、
シェルから `grep -r` を打つと除外は効かない。

**出口** — `rg` を使い、対象を `src` に限る。[04_静的探索](04_静的探索の道具と手順.md) §2。

### F2. 道具の不在と誤用

**症状** — 参考記事にあるコマンドが、この環境では動かない。

**実例** — この環境には `rg`・`madge`・`tree`・`node`・`pnpm` がある。
`ast-grep`・`jq`・`fd`・`fzf`・`ctags`・`semgrep` は無い。
`sg` は存在するが、これは `ast-grep` ではなく Linux の `setgroups` コマンドであり、混同すると事故になる。

**出口** — 使える道具の一覧は [04_静的探索](04_静的探索の道具と手順.md) §1 にある。

### F3. 既存資料の散在

**症状** — 調べたい内容が、すでに誰かの資料にあるのに気付かない。

**実例** — 本リポジトリには、コードリーディングの成果物がすでに複数系統ある。
`docs/sequense/`（44 本、状態保持とテンプレート投影の経路）、`x-sequense/`（操作単位の追跡、7 本）、
`x-QA/`（実装技術の調査）、`ngbi-*.md`（一本線追跡）、
`ng-maze-*.md`（コンポーネント関係ツリー）、`madge-rdeps-*.md`（参照元の逆引き）。

**出口** — 調査の前に既存資料を検索する。一覧は [14_地形図](14_ClearML地形図.md) §7。

## G. ドメイン知識の欠落と外部依存

コードの読み方の問題ではなく、コードの外にある知識が足りないために止まる型である。
探索の技術では解けないので、別の手を打つ。

### G1. 層ごとに語彙が違う

**症状** — 画面に出ている言葉でコードを検索しても、実装が出てこない。
出てきたコードも、画面で見たものと対応が取れない。

**機構** — UI の語彙と、データモデルの語彙が別々に決まっている。
製品の呼び名は後から変わるが、API とデータの名前は互換のために据え置かれる。
結果として、同じものが層ごとに違う名前で呼ばれる。

**実例** — ClearML では、画面の「Experiment」がデータ上は `task` である。
`src/app/shared/constants/non-common-consts.ts` の `EntityTypeEnum` が、この対応をそのまま定義している。

```ts
export enum EntityTypeEnum {
  experiment = 'task',
  dataset = 'version',
  openDataset = 'dataset',
  controller = 'pipeline run',
  ...
}
```

`business-logic/api-services/` に `experiments.service.ts` は無い。
`webapp-common/experiments/` の Effects は、すべて `ApiTasksService`（`tasks.service.ts`）を注入している。
URL にもその痕跡があり、`features/datasets/datasets.routes.ts` には
`{path: 'experiments', redirectTo: 'tasks'}` という転送が残っている。

もう一つ大きいのが `events` である。
ClearML の `events.*` API（`events.service.ts`、1,181 行）は UI のイベントではなく、
スカラー指標・プロット・ログ・デバッグ画像を指す
（`events.get_scalar_metric_data`、`events.get_task_log`、`events.debug_images` など）。
「イベント処理」を探してここに来ると、一度誤読する。

**出口** — 用語の対応表を先に持つ。[14_地形図](14_ClearML地形図.md) §5 に置いた。

### G2. ドメインの前提を知らない

**症状** — 個々のコードの意味は分かるが、「なぜこの処理が要るのか」が分からない。

**機構** — 実装はドメインの概念を前提に書かれている。
前提を共有していない読み手には、処理の存在理由が見えない。
コードをいくら読んでも、コードの外にある前提は出てこない。

**実例** — 実験の「Queue へ投入する」「Agent が実行する」「Dataset Version を固定する」
「モデルを昇格する」といった操作は、MLOps の運用手順に由来する。
この手順を知らないと、`workers-and-queues` や `model_lifecycle` の実装は、
意味の取れない状態遷移の集まりに見える。

**出口** — コードではなく、ドメインの資料を読む。
本リポジトリでは `README.md`（§リモート学習、§学習Pipeline、§モデルの昇格とrollback ほか）と
`docs/phase3_ML固有/` が対応する。15 分の読書が、数時間の誤読を防ぐ。

### G3. 外部ライブラリの挙動が読めない

**症状** — 自分たちのコードは全部読んだのに、挙動が説明できない。

**機構** — 画面の振る舞いの一部は、取り込んだ UI ライブラリが決めている。
そのコードはリポジトリに無いので、検索しても出てこない。

**実例** — PrimeNG 22 と Angular Material 22 を併用している。
`pTemplate`（32 箇所）は PrimeNG の仕組みで、名前でテンプレートを拾う。
どの名前が有効かは PrimeNG 側の実装で決まっており、こちらのコードには書かれていない。

**出口** — ライブラリの型定義を直接読む。`rg` に対象を明示すれば読める。

```bash
rg -n "pTemplate" node_modules/primeng/ -g '*.d.ts' | head
```

それでも分からなければ、実行時に DOM と DevTools で確かめる（[05_実行時観測](05_実行時観測で読む.md)）。
