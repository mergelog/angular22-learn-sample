# 実行時観測で読む

静的に読んで 30 分かかることが、実行して 2 分で決まる場面がある。
分岐が多い箇所、間接呼び出し、非同期の順序、`any` の実体がその典型である。
この章は、動かして読む手段を並べる。

## 1. 動かして読むと速くなる条件

静的な読みは、通りうる経路をすべて等しく扱う。
実際の入力では大半の分岐が通らないので、読んだ量のうち役に立つのは一部にとどまる。
実行時の観測は、実際に通った経路だけを返すので、読む量がそこに絞られる。

次の四つに当たったら、読むのをやめて動かす。

| 状況 | 静的に読む場合 | 動かす場合 |
| --- | --- | --- |
| 分岐が多い | 全分岐を読む | 通った分岐だけ見える |
| 呼び出し元が分からない（DI・イベント） | 登録箇所を全部探す | コールスタックに出る |
| 非同期の順序が読めない | 演算子の意味から推論する | 発火順がそのまま見える |
| 型が `any` | 推測するしかない | 実際の値の形が見える |

逆に、動かさないほうが速い場面もある。
「この関数が何をしているか」「この型は何か」は、読んだほうが速い。

## 2. 起動する

```bash
# 家庭内LANからも見る場合（AGENTS.local.md の指定）
ng serve --host 0.0.0.0 --port 4200
```

開発構成では `optimization: false`、`sourceMap: true` が効いている。
最適化が無効なので、DevTools に出る関数名とソースの関数名が一致する。
本番ビルドを読んでも名前が潰れているので、読むために動かすなら必ず開発構成を使う。

API は `proxy.config.mjs` により `/service/1/api` が `http://localhost:8008` へ転送される。
Network タブに出るパスと、コード上の API パスが食い違って見えるのはこの転送のためである。

バックエンドが落ちていると画面が組み上がらない。先に確認する。

```bash
pnpm run backend:status
```

## 3. ブレークポイントとログポイント

### 3-1. 条件付きブレークポイント

一覧の行ごとに 200 回止まるブレークポイントは使えない。条件を付ける。

VS Code またはブラウザの DevTools で、行番号を右クリックして条件式を入れる。

| 条件の型 | 例 | 用途 |
| --- | --- | --- |
| 値の一致 | `experiment.id === 'abc123'` | 特定の 1 件だけ止める |
| 回数 | ヒットカウント `> 5` | 2 回目以降の挙動を見る |
| 状態 | `this.tableMode() === 'compare'` | 特定のモードだけ見る |

### 3-2. ログポイント

止めずに記録だけ取る。非同期の順序を知りたいときは、止めると順序が変わるので、
ブレークポイントよりログポイントのほうが正確である。

DevTools の Breakpoint 設定で "Logpoint" を選び、`経路A: {experiment.id}` のように書く。
コードを書き換えないので、消し忘れがビルドに残らない。

### 3-3. どこに置くか

一本線追跡（[03](03_探索戦略と読む順序.md) §3-1）では、経路の端から二点に置く。
出発点（イベントハンドラ）と到達点（API 呼び出し）である。
両方に止まれば、その間は必ず通っている。片方しか止まらなければ、間に分岐がある。
二分探索で中間に置き直せば、数回で分岐点が出る。

## 4. 誰が呼んだかを確定させる

### 4-1. コールスタック

ブレークポイントで止めたときのコールスタックが、いちばん確実な「呼び出し元」である。
DI やイベントで結ばれた呼び出しも、スタックには出る。

Angular のフレームワーク内部のフレームが大量に挟まるので、
DevTools の "Ignore listed frames"（旧 blackboxing）で `node_modules` を折り畳む。

### 4-2. Action を誰が dispatch したか

Redux DevTools が使える。開発ビルドでは `provideStoreDevtools({maxAge: 100, trace: true, traceLimit: 50})`
が登録されている（`src/app/build-specifics/index.ts`）。
本番ビルドでは `index.prod.ts` に差し替わり、空になる。

`trace: true` により、各 Action に**dispatch 時点のスタックトレース**が付く。
DevTools で Action を選び Trace タブを開けば、どのファイルの何行目が dispatch したかがそのまま出る。
`dispatch(` は 1,026 箇所あるので、これを検索で絞るより桁違いに速い。

Redux DevTools でできることは他にもある。

| 操作 | 読むときに分かること |
| --- | --- |
| Action の一覧 | 1 操作で何個の Action が流れるかが分かる |
| State の diff | その Action が State のどこを変えたかが、キー単位で出る |
| Jump / Skip | 特定の Action を無効化して、画面への影響を確かめられる（反証に使う） |
| Dispatch | 手で Action を流して、Reducer と画面の対応を単独で確かめられる |

### 4-3. Effect の発火

Effect は Action を受けて Action を出す。Redux DevTools の並びを見れば、
`getExperiments` の直後に `setExperiments` が来る、という対応がそのまま読める。
`ofType(` は 293 箇所あるが、実際に反応した Effect は並びから特定できる。

## 5. 画面の部品からコードへ

### 5-1. Angular DevTools

ブラウザ拡張の Angular DevTools を入れると、コンポーネントツリーが見える。
要素を選ぶと、そのコンポーネントの入力・出力・プロパティの現在値が出る。
変更検知のプロファイルも取れる。

### 5-2. コンソールから触る

開発ビルドではグローバルに `ng` が生える。要素を選んでから、

```js
// DevTools の Elements で要素を選択したあと
ng.getComponent($0)        // その要素のコンポーネントインスタンス
ng.getOwningComponent($0)  // その要素を持つ親コンポーネント
ng.applyChanges($0)        // 手で変更検知を走らせる
```

`ng.getComponent($0)` の戻り値をコンソールで展開すれば、
クラスのフィールドとその実際の値が一覧で出る。
`: any` が 683 箇所ある本リポジトリでは、型から読めない値の形をこれで確定させる。

### 5-3. 文言から辿る

画面に出ている文言で検索する（[04](04_静的探索の道具と手順.md) §4）。
検索で当たらない場合は、DevTools の Elements で要素を選び、`sm-` で始まる祖先タグを探す。
そのタグ名でコンポーネントを特定できる（`selector:` 記述 379 件のうち 345 件が `sm-` 接頭辞）。
`sm-` で始まる祖先が無い場合は、取り込んだ通知ライブラリ（`notifier-*`）か `al-drawer` である。

## 6. 通信を見る

Network タブで、画面の操作とリクエストの対応を取る。
読む前にこれをやると、「どの API を叩いているか」が決まり、
`business-logic/api-services/` の該当メソッドに直行できる。

| 見るもの | 分かること |
| --- | --- |
| リクエストのパス | どの API サービスのどのメソッドか |
| ペイロード | 画面の入力がどう変換されたか。変換処理の場所の手がかりになる |
| レスポンス | Reducer に入る前の生のデータ形状 |
| Initiator | どのコードが発行したか（スタック付き） |
| 発行の順序と本数 | 1 操作で何回叩くか。二段取得になっているか |

レスポンスの形は、`business-logic/model/` の生成型と対応する。
型定義を読むより、実際のレスポンスを見たほうが速い場合が多い。

## 7. E2E を観測装置として使う

Playwright が入っている（`e2e/` に 6 本）。
手で操作を再現するのが面倒な調査では、E2E を一本書いて、そのトレースを読む。

```bash
pnpm run e2e
```

トレースには、各ステップの DOM スナップショット、ネットワーク、コンソールが入る。
同じ操作を何度も再現する必要がある調査（間欠的な不具合、順序依存）では、
手操作より速くなる。

## 8. 一時的にコードを変えて読む

観測装置を入れるためにコードを変えるのは、読むための正当な手段である。
条件は一つで、**確実に元へ戻せること**である。

| 手 | 目的 | 戻し方 |
| --- | --- | --- |
| `console.log` を挟む | 値と到達を確かめる | `git checkout -- {パス}` |
| 条件を反転させる | その分岐が原因かを確かめる | 同上 |
| 処理を丸ごと飛ばす | その処理が症状に効いているかを確かめる | 同上 |
| 二分して半分を無効化する | 長い処理のどこで壊れるかを詰める | 同上 |
| `switchMap` を `concatMap` に替えてみる | 並行性が原因かを確かめる | 同上 |

戻し忘れを防ぐ手順は二つある。
調査を始める前に作業ツリーを綺麗にしておき（`git status` が空）、
終わったら `git status` で変更が残っていないことを確かめる。

```bash
git status --short          # 調査前: 空であること
git diff                    # 調査後: 何を入れたか確認
git checkout -- src/app/... # 戻す
```

ログポイント（§3-2）で足りる場面では、そちらを使う。
コードを変えないので、戻し忘れが起きない。
コードを変えるのは、ログポイントでは書けない操作（分岐の反転、処理の無効化）をするときだけにする。

二分して詰める手は、長い Effect のパイプで使える。
`common-experiments-view.effects.ts` は 1,078 行あり、読んで原因を探すより、
半分を無効化して症状が消えるかを見るほうが速い場面がある。

## 9. 観測の記録

実行時の観測は消える。閉じれば残らない。
分かったことは、その場でメモに一行書く。形式は [10_記録](10_記録と資料化の型.md) §3。

最低限残すのは三つである。

- 操作（何をしたか）
- 観測（何が出たか。Action 名、リクエストパス、値）
- 場所（`src/app/…/foo.ts:123`）

この三つがあれば、同じ観測を再現できる。無ければ、また同じ操作から始めることになる。
