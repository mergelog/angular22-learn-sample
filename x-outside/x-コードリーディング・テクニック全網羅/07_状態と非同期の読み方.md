# 状態と非同期の読み方

値がどこから来て、どこで変わり、いつ画面に届くか。
この三つを追えるようになると、画面まわりの調査の大半が片付く。

## 1. 規模

| 要素 | 件数 |
| --- | --- |
| `createAction` | 666 |
| `createSelector` | 517 |
| `store.dispatch(` | 1,026 |
| `store.select(` | 928 |
| `ofType(` | 293 |
| Action ファイル | 48 |
| Reducer ファイル | 41 |
| Effects ファイル | 46 |

Effects の最大は `webapp-common/experiments/effects/common-experiments-view.effects.ts` の 1,078 行である。
この規模のファイルは通し読みしない。`ofType(` で区切って、該当の一塊だけ読む。

## 2. 状態の置き場所は五つある

値の出所が分からないときは、まずどの置き場所かを決める。決まれば読む先が決まる。

| 置き場所 | 何が置かれるか | 見分け方 | 読む先 |
| --- | --- | --- | --- |
| NgRx Store | 一覧、選択、フィルタ、詳細 | テンプレートが Selector 由来の値を読む | Reducer と Selector |
| Component の Signal | ハイライト、開閉、編集中の値 | `signal()` / `computed()` の宣言がクラスにある | そのコンポーネントだけ |
| URL | プロジェクトID、タブ、一部のフィルタ | アドレスバーが変わる | ルート定義と Router 関連の Effect |
| localStorage | 再読み込みしても残る設定 | リロードで復活する | meta-reducer（§4） |
| サーバ側のユーザ設定 | 列構成、並び順 | 別の端末でも同じ | `UserPreferences` |

判定は実行時に取るのが速い。
リロードして残れば localStorage かサーバ側、URL を変えて変われば URL、
Redux DevTools の State に出れば Store、どこにも出なければコンポーネント内部である。

## 3. Store の構成を読む

ルートの状態は `src/app/core/core.config.ts` の `reducers` オブジェクトに列挙されている。
`auth` `router` `messages` `recentTasks` `views` `users` `login` `rootProjects`
`commonSearch` `colorsPreference` などが並ぶ。

機能ごとの状態は `provideState(キー, reducers, 構成トークン)` で後から足される。
キーは定数になっている。

| キー | 定数 | 定義場所 |
| --- | --- | --- |
| `experiments` | `EXPERIMENTS_STORE_KEY` | `webapp-common/experiments/experiment.consts.ts:6` |
| `models` | `MODELS_STORE_KEY` | `webapp-common/models/models.consts.ts:21` |
| `experimentsCompare` | `COMPARE_STORE_KEY` | `webapp-common/experiments-compare/experiments-compare.providers.ts:24` |

Redux DevTools の State ツリーの第一階層は、このキーの一覧と一致する。
DevTools を開いてキーを見れば、どの機能の状態が今読み込まれているかが分かる。

## 4. localStorage への保存は Reducer に書かれていない

再読み込みしても状態が残る仕組みは meta-reducer にある。
Reducer を読んでも保存処理は出てこないので、探す場所を間違えやすい。

保存キーは六つある。

| キー | 仕掛け場所 |
| --- | --- |
| `_saved_state_` | `core/core.config.ts` |
| `_saved_experiment_state_` | `features/experiments/shared/experiments.providers.ts:26` |
| `_saved_models_state_` | `webapp-common/models/models.providers.ts:14` |
| `_saved_compare_state_` | `webapp-common/experiments-compare/experiments-compare.providers.ts:30` |
| `_saved_endpoints_state_` | `webapp-common/serving/serving.providers.ts:24` |
| `_saved_pipeline_state_` | `webapp-common/pipelines/pipelines.providers.ts:19` |

`core.config.ts` の `syncedKeys` には、保存対象のパスが文字列で列挙されている
（`rootProjects.showHidden`、`views.tableCardsCollapsed` など）。
保存されるのはここに挙がったキーだけである。

調査で「初期値がおかしい」となったら、この保存を疑う。
DevTools の Application タブで該当キーを消してから再現するのが確実である。

## 5. Action から画面までを一本で追う

順序は決まっている。この順に一つずつ確かめる。

```
操作 → dispatch → (Effect) → Reducer → Selector → テンプレート
```

### 5-1. 操作から Action へ

テンプレートのイベントバインド（`(click)` など）からクラスのメソッドを開き、
`store.dispatch(` を探す。Action 名が取れる。

実行時なら、Redux DevTools で操作の直後に流れた Action を見るほうが速い。
`trace: true` が有効なので、Action を選んで Trace タブを開けば dispatch 元の行が出る。

### 5-2. Action から定義へ

素の Action 名で検索する。修飾を付けない。

```bash
rg -n -t ts "setSelectedExperiments" src
```

一回で、`createAction`（定義）・`on(...)`（Reducer）・`ofType(...)`（Effect）・`dispatch(`（発行元）が
まとめて出る。経路の全段が一回の検索で揃うのは、この形だけである。

Reducer は `on(actions.setSelectedExperiments, ...)` のように名前空間付きの別名で書かれているので、
`on(setSelectedExperiments` では当たらない。

### 5-3. Effect を読む

Effect の読み方は三点だけ見る。

| 見る箇所 | 分かること |
| --- | --- |
| `ofType(...)` | 何に反応するか |
| 中間のパイプ | 何を取りに行き、何と突き合わせるか |
| 最後に返す Action | 次に何が流れるか |

中間のパイプを最初から読まない。入口と出口だけ取れば、経路はつながる。
中身が要るのは、その Effect 自体を直す時か、中で例外が起きている時だけである。

### 5-4. Reducer を読む

`on(アクション, (state, action) => ...)` の対応だけ見る。
State のどのキーが書き換わるかが分かれば足りる。
Redux DevTools の diff を見れば、読まずに同じ情報が取れる。

### 5-5. Selector からテンプレートへ

Selector は `createFeatureSelector` でキーを取り、`createSelector` で合成する。
517 個あるので、Selector 名で検索して使用箇所を見つける。

```bash
rg -n -t ts -t html "selectSelectedExperiment" src
```

`store.select(...)` の結果が `toSignal()` で Signal に変換されていることが多い（76 箇所）。
そこから先は Signal の世界なので、[06_Angular固有](06_Angular固有の読み方.md) §5 に続く。

## 6. RxJS を読む

`.pipe(` が 1,060 箇所ある。全部を演算子の意味から追うのは割に合わない。
読むときは三つの問いに絞る。

**いつ流れるか。** 上流が何か。`ofType` か、`store.select` か、DOM イベントか。

**何本並行するか。** ここは演算子の選択で決まる。

| 演算子 | 件数 | 前の処理がまだ走っているとき |
| --- | --- | --- |
| `switchMap` | 340 | 前を打ち切って新しいほうに乗り換える |
| `mergeMap` | 252 | 打ち切らず並行して走らせる |
| `concatMap` | 5 | 前が終わるまで待つ |
| `exhaustMap` | 8 | 新しいほうを捨てる |

一覧の再取得が二重に走る、古い結果が新しい結果を上書きする、といった症状は
この選択と対応している。`mergeMap` で書かれている箇所は、順序が保証されない。

**いつ止まるか。** `takeUntilDestroyed`（168 箇所）が付いていれば、コンポーネントの破棄で切れる。
付いていなければ、`take(1)` などの完了演算子があるか、`ngOnDestroy` で切っているかを確かめる。

`withLatestFrom`（61 箇所）は、上流が流れた瞬間の他の値を取る。
他の値が変わっても流れない。「更新したのに反映されない」の原因になりやすい箇所である。

## 7. 非同期の順序を確定させる

コードから順序を推論しない。観測する。

Redux DevTools の Action 一覧が、そのまま実際の順序である。
1 回の操作で何個の Action が流れるか、どの順かが並びで出る。
Effect が Action を出す構造なので、Effect の連鎖も並びに現れる。

ネットワークの並びも併せて見る。
操作 1 回に対してリクエストが 2 本出る場合、一覧取得と詳細取得の二段になっている。
既存の解析が `docs/sequense/04_バックエンド経路/04-04_詳細パネルの二段取得.md` にある。
