# 全体地図の作り方

初見のコードベースで最初に作るのは、詳細の理解ではなく地図である。
地図とは「開いたファイルのパスを見た瞬間に、それが何の層の何であるかが決まる状態」を指す。
これがあると、以後の調査で開くファイル数が減る。無いと、毎回ディレクトリを漁ることになる。

この章は地図の作り方を手順として書く。
本リポジトリについて作成済みの地図は [14_ClearML地形図](14_ClearML地形図.md) にあるので、
結果だけ要るならそちらを読む。ここは、その地図を自分で作り直す、または別のリポジトリへ移すための手順である。

## 1. 地図が答える四つの問い

| 問い | 答えの形 | 所要 |
| --- | --- | --- |
| どこに何があるか | ディレクトリと役割の対応表 | 15分 |
| どこが大きく、どこが小さいか | 行数・ファイル数の分布 | 10分 |
| どこが自作で、どこが取り込みか | 由来の境界線 | 10分 |
| どこから始まるか | 入口の一覧 | 15分 |

四つ揃って 50 分である。この 50 分を惜しむと、以後の調査ごとに 10 分ずつ払い続けることになる。

## 2. 入口を数える

「入口」は一つではない。知りたいことによって正しい入口が変わる。
先に入口の系統を並べ、目的と対応づけておく。

| 知りたいこと | 入口 | 本リポジトリでの場所 |
| --- | --- | --- |
| アプリが起動して最初に何をするか | ブートストラップ | `src/main.ts` → `src/app/app.config.ts` |
| 画面 URL とコンポーネントの対応 | ルート定義 | `src/app/app.routes.ts` と `features/*/[名前].routes.ts` |
| サーバとの通信 | API クライアント | `src/app/business-logic/api-services/` |
| 状態の全体構成 | ストア登録 | `src/app/core/core.providers.ts`、各 `*.providers.ts` |
| 画面部品の構造 | 最上位コンポーネント | `src/app/app.component.html`、`layout/` |
| ビルドと環境の違い | ビルド設定 | `angular.json`（特に `fileReplacements`） |
| 依存の禁止規則 | 境界定義 | `web-boundaries.json` |

入口の探し方は、フレームワークが決まっていれば規約で決まる。
Angular なら `main.ts` と `angular.json` の `browser`/`main` 指定から辿れば必ず見つかる。
規約が分からないリポジトリでは、`package.json` の `scripts` を読むのが最短である。

```bash
node -e "const p=require('./package.json'); console.log(Object.keys(p.scripts).join('\n'))"
```

本リポジトリではこの出力が 90 行を超える。数が多いときは、`start` `build` `test` `lint` の
四つだけ先に読む。残りは運用手順であり、地図作りには要らない。

## 3. 大きさを測る

役割の推測は名前から始めるが、名前は当てにならない（[01](01_大規模コードリーディングで苦労する点.md) C5）。
行数の分布は嘘をつかないので、こちらを先に取る。

```bash
# 層ごとのファイル数と行数
cd src/app
for d in core features layout shared webapp-common business-logic build-specifics; do
  printf "%-16s %4s files %7s lines\n" "$d" \
    "$(find $d -name '*.ts' | wc -l)" \
    "$(find $d -name '*.ts' -exec cat {} + | wc -l)"
done
```

```bash
# 大きいファイルから 25 件
find src -name "*.ts" -exec wc -l {} + | sort -rn | sed -n '2,26p'
```

大きいファイルの一覧は、それ自体が地図になる。
理由は、大きいファイルが二種類に分かれるからである。
一つは生成物（読まなくていい）、もう一つは設計の中心（必ず読む）。
この二種類の判別は、先頭 20 行を見れば付く。生成物にはヘッダコメントか、
同じ形のメソッドが並ぶ構造がある。

## 4. 由来の境界を引く

fork したリポジトリでは、取り込みコードと自作コードが同じツリーに同居する。
この境界を引かないと、「なぜこうなっているか」を取り込み元の都合に帰せるかどうかが判断できない。

境界の手がかりは三つある。

**明示された規約** — `web-boundaries.json` の規則の説明文に、
「`webapp-common` はベンダー由来の凍結領域」と書かれている。これが一次情報である。

**依存の向き** — 取り込み層は、自作層を名前で参照できない。
参照するとしたらエイリアス経由の差し込み口になる。実際、`webapp-common` からの `~/` 参照は
`business-logic`（566）・`shared`（105）・`app`（32）・`core`（26）に向いており、
`features` への参照は 0 件である。

```bash
grep -rho "from '~/[a-z-]*" src/app/webapp-common --include="*.ts" | sort | uniq -c | sort -rn
```

**追跡記録** — `upstream.json` に、fork 元のリポジトリ・バージョン・確認済みコミットが記録されている。
詳細は [09_履歴と差分](09_履歴とフォーク差分から読む.md)。

## 5. エイリアスの解決表を作る

パスエイリアスは、地図の座標系である。これが頭に入っていないと、import 文を読むたびに
実ファイルの位置を考えることになる。`tsconfig.json` の `paths` から作る。

| 書き方 | 実体 | 何の層か |
| --- | --- | --- |
| `~/*` | `src/app/*` | 差し替え可能な層（自作側） |
| `@common/*` | `src/app/webapp-common/*` | 取り込み元の本体 |
| `@features/*` | `src/app/features/*` | 機能ごとの上書き・追加 |
| `@environments/*` | `src/environments/*` | 環境設定 |

使用頻度は `@common/` 2,520、`~/` 895、`@features/` 364 である。
import 文の先頭を見ただけで、その行がどの層を指しているかが決まる。

`~/` と `@features/` が両方 `src/app` 配下を指している点に注意が要る。
`~/features/...` と `@features/...` は同じ場所を指す。二通りの書き方が混在している。

## 6. 依存グラフを一度だけ取る

構造は、import の依存グラフで確かめられる。本リポジトリには `madge` が入っている。

```bash
# 循環依存の一覧（3〜5分かかる）
npx madge --ts-config tsconfig.json --extensions ts --circular src/app
```

本リポジトリでは 35 件の循環が出る。
循環の大半は「Action ファイルが Component を import し、その Component が Action を import する」形である。
循環があると、読み方が変わる。循環している対は、片方だけ読んで全体を決められないからである。

逆方向（誰がこれを使っているか）を図にするには、リポジトリ内のスキルが使える。

```bash
node .claude/skills/madge-to/scripts/madge-to.mjs src/app/.../xxx.component.ts
```

出力は `madge-rdeps-{クラス名}.md` としてプロジェクト直下に出る。既存の例が
`madge-rdeps-InlineEditComponent.md` にある。

## 7. 60分の型

時間を区切らないと、地図作りが調査に化ける。次の配分で打ち切る。

| 経過 | やること | 成果物 |
| --- | --- | --- |
| 0–10分 | `package.json` の scripts、`README` の見出し、`tsconfig.json` の paths | エイリアス解決表 |
| 10–25分 | 層ごとのファイル数・行数、大きいファイル 25 件 | 規模の分布表 |
| 25–35分 | 由来の境界（依存の向き、`web-boundaries.json`、`upstream.json`） | 境界線の一文 |
| 35–50分 | 入口の一覧（bootstrap、routes、API、providers） | 入口の対応表 |
| 50–60分 | ここまでを 1 ファイルに書く | 地図 |

最後の 10 分を省かない。書いていない地図は残らない。

## 8. 地図の更新

地図は古くなる。ただし、古くなり方には偏りがある。
層の構成と由来の境界はほとんど変わらないが、行数の分布と入口は変わる。
更新は、§3 のコマンドを再実行して数字だけ差し替えれば足りる。
半年に一度、あるいは上流を取り込んだ直後に行う。
