# 記録と資料化の型

読解時間を最も大きく縮めるのは、探索の速さではなく記録の習慣である。
理由は単純で、同じ経路を二度たどらなくなるからである。
40 分かけた調査を記録せずに閉じると、二週間後に同じ 40 分を払う。
記録に使う時間は 5 分なので、一度でも再訪があれば元が取れる。

この章は、何を・いつ・どの形で残すかを決める。

## 1. 記録の三階層

粒度の違う記録を混ぜると、どれも使えなくなる。三つに分ける。

| 階層 | 寿命 | 置き場所 | 何を書くか |
| --- | --- | --- | --- |
| 作業メモ | その調査のあいだ | 手元の一時ファイル | いま追っている問い、開いたファイル、次の一手 |
| 経路の資料 | 数か月〜 | `ngbi-*.md`、`x-sequense/`、`x-QA/` | ある操作が通る経路。再現できる形 |
| 設計の記述 | 長期 | `docs/phase*/` | なぜその構成かの判断 |

上の階層ほど頻繁に書き、下の階層ほど少なく書く。
作業メモは毎回、経路の資料は調査が一段落したとき、設計の記述は判断したときだけである。

## 2. 作業メモの型

調査を開始したら、最初に四行書く。これだけで目的の喪失（[01](01_大規模コードリーディングで苦労する点.md) E1）が防げる。

```
問い: 実験名の変更はどこでサーバへ届くか
終了条件: 入力欄のイベントから API 呼び出しまで、ファイルと行番号を順に並べられる
仮説: InlineEditComponent の output → ExperimentsComponent → Effect → tasks.service
反証: ブレークポイントを Effect に置いて、止まらなければ仮説が誤り
```

以降、開いたファイルを一行ずつ足す。形式は `パス:行 — 分かったこと` に揃える。

```
src/app/webapp-common/experiments/experiments.component.ts:554 — highlited を update するだけ。dispatch していない
src/app/webapp-common/experiments/effects/common-experiments-menu.effects.ts:... — ofType(...) で受けている
```

この形式に揃える理由は、VS Code で `パス:行` がそのまま開けるからである。
行番号が無いメモは、次に開くときにもう一度探すことになる。

枝道に逸れそうになったら、本文ではなく末尾の「あとで」欄に積む。
積んだものは、いまの問いを閉じてから取り出す。

## 3. 中断するとき

中断の直前に三行書く。書く時間は 1 分で、復帰が 15 分から 1 分になる。

```
いま分かっていること: Effect は反応している。dispatch までは届いている
次に確かめること: Effect の switchMap の中で API が呼ばれているか
そのための手: common-experiments-menu.effects.ts の 300 行付近にログポイント
```

## 4. 経路の資料（Bulletin解析）

調査が一段落したら、経路の資料にする。
本リポジトリにはこの形式がすでにあり、スキルとして実装されている。

```
/bulletin 実験管理画面で実験名を変更して一覧に新しい名前を反映する
```

出力は `ngbi-{連番}-{処理内容}.{日付}.md` としてプロジェクト直下に出る。既存が 3 本ある。

構成は三つである。

| 節 | 内容 | なぜ要るか |
| --- | --- | --- |
| 30秒で分かる結論 | 担当・技術・役割の表と、一文の要点 | 次に開く人が、読むかどうかを 30 秒で決められる |
| 全体図 | Mermaid の flowchart。段階ごとに subgraph で括る | 構造を記憶に頼らず保持できる |
| コードを追うN地点 | 通過点ごとに、パス・行・コード断片・説明 | 同じ経路を再現できる |

`--code` を付けると、資料からリンクした実コードの行にも `[ngbi:{資料番号}-{注記番号}]` の
注記が入る。コード側からも資料へ戻れるようになる。

JSON で出す版（`/bulletin-json`）もある。
地点ごとに `trigger` / `implementation` / `componentOverview` / `process` / `effects` を持つ配列になる。
機械で処理したいときはこちらを使う。

### 4-1. なぜ一本線か

網羅的な説明ではなく、**一本の経路**に限るのが要点である。
理由は二つある。

網羅的な資料は書くのに時間がかかり、書き終わる前に古くなる。
それと、読む側が「自分の問いに関係する部分」を探す手間が、コードを読む手間と変わらなくなる。

一本線なら、書くのは 30 分、読むのは 3 分で済む。

## 5. 図の使い分け

| 図の種類 | 何を表すか | 道具 |
| --- | --- | --- |
| フローチャート | 処理の経路 | Mermaid `flowchart`（Bulletin の全体図） |
| シーケンス図 | 登場人物の間のやりとりと順序 | Mermaid `sequenceDiagram`（`docs/sequense/`、`x-sequense/`） |
| コンポーネントツリー | 部品の親子関係 | `ngmaze` スキル |
| 依存の逆引き | 誰がこれを使っているか | `madge-to` スキル |

シーケンス図は、登場人物が 3 人以上いて順序が問題になるときに使う。
2 人なら文章のほうが速い。

生成できる図（`ngmaze`、`madge-to`）は、自分で描かない。
`ng-maze-ExperimentsComponent-20260917-161335.md` は 53KB あり、手では書けない量である。

## 6. どこに置くか

本リポジトリには置き場所の規約がある。

| 内容 | 置き場所 | 命名 |
| --- | --- | --- |
| 一本線の経路追跡 | プロジェクト直下 | `ngbi-{連番}-{内容}.{日付}.md` |
| 操作単位のシーケンス図 | `x-sequense/{連番}_{操作}/` | `{連番}_{観点}.md` |
| 体系的なシーケンス図 | `docs/sequense/{連番}_{分類}/` | `{分類}-{連番}_{内容}.md` |
| 実装技術の調査 | `x-QA/` | `{2桁連番}_{タイトル}.md` |
| 設計資料 | `docs/phase{n}_{分類}/` | `{番号}_{タイトル}.md` |
| 引き継ぎ | `x-handoff.md` | — |

迷ったら `x-QA/` に置く。分類は後から移せるが、書かなかったものは戻らない。

## 7. 書かないもの

記録が使われなくなる原因は、量が多すぎることである。次は書かない。

| 書かないもの | 理由 |
| --- | --- |
| コードの逐語訳 | コードを読めば分かる。変更されると嘘になる |
| 生成コードの説明 | 設計意図が無い |
| 「調べ中」のまま放置された断片 | 読む側が真偽を判断できない |
| 網羅的な一覧（全 Action、全コンポーネント） | 作った瞬間から古くなる。必要なら検索で出す |

一覧が要るときは、資料に書かずにコマンドを書く。
コマンドは古くならない。

## 8. 記録が古くなったとき

資料には、書いた時点のコミットか日付を入れる。
`ngbi-*.md` のファイル名に日付が入っているのはこのためである。

古い資料は消さない。ただし、実際と食い違っていることが分かったら、
その一行を資料の冒頭に足す。

```
> 2026-10-01 時点で §3 の経路は変わっている。Effect が別ファイルへ移動した。
```

消すより速く、読む側の誤読も防げる。

## 9. 既存資料の探し方

調査の前に、同じことがすでに書かれていないかを確かめる。

```bash
# 資料の全文検索
rg -n -t md "実験名" docs/ x-QA/ x-sequense/ ngbi-*.md
```

既存の系統は [14_地形図](14_ClearML地形図.md) §7 に一覧がある。
