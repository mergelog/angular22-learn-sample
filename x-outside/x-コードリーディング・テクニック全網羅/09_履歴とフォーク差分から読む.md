# 履歴とフォーク差分から読む

「なぜこうなっているか」は、コードを読んでも出てこない。
出てくるのは「どうなっているか」だけである。理由は履歴の側にある。

ただし本リポジトリでは、通常の履歴考古学がほとんど効かない。
効かない理由と、代わりに何を使うかを先に書く。

## 1. なぜ `git blame` が効かないか

本リポジトリのコミットは 23 個しかない。
fork 元のコードは `86e6dbd first commit` としてまとめて取り込まれており、
それ以前の履歴は無い。

```bash
git log --oneline -- src/app/webapp-common/experiments/experiments.component.ts
# → 9c545f9 change directory  の 1 件だけ
```

866 行の実装に対して、得られる情報は「ディレクトリを移動した」だけである。
`git blame` を打っても同じで、全行が同じコミットを指す。

したがって、取り込み層（`webapp-common/`、全体の 66%）については、
このリポジトリの履歴から意図を取ることはできない。上流を見るしかない。

自作層（`features/` `core/` `shared/` `layout/`、および `docs/` `scripts/` `ml/` `services/`）については、
23 個のコミットが本物の履歴である。こちらは通常どおり使える。

## 2. 上流を取得する

`upstream` リモートは登録済みだが、取得されていない。
このまま `git log upstream/master` を打つと
`unknown revision` で止まる。先に取得する。

```bash
# blob を遅延取得にして軽くする
git fetch upstream --filter=blob:none

# fork 基点のタグも要る
git fetch upstream --tags
```

取得後にできることが増える。

| コマンド | 分かること |
| --- | --- |
| `git log upstream/master -- <パス>` | そのファイルの本来の変更履歴 |
| `git log -S "検索語" upstream/master` | ある文字列が入った／消えたコミット |
| `git log -G "正規表現" upstream/master` | 変更差分が正規表現に一致するコミット |
| `git show <commit>` | 変更の全体と、コミットメッセージ（意図の一次情報） |
| `git diff v2.5 upstream/master -- <パス>` | fork 後に上流で何が変わったか |

`git log -S` は、ある行がいつ入ったかを一発で出す。
`blame` が使えない状況でも、上流側でなら使える。

## 3. fork 基点と現状を確かめる

`upstream.json` に、fork の基点と最後に確認した上流の状態が記録されている。

| 項目 | 値 |
| --- | --- |
| 上流リポジトリ | `https://github.com/clearml/clearml-web.git` |
| fork 基点 | `refs/tags/v2.5` / `48b61702f703` / 2.5.0 |
| 最後に確認した上流 | `067b48519563` / 2.5.0 / 2026-09-13 |

`recorded` は「見た」という記録であって、「取り込んだ」という記録ではない。
この区別は `upstream.json` の `$comment` に明記されている。

上流が進んだかどうかは検査できる。

```bash
pnpm run upstream:status
```

版数では検知できない（上流の `master` は tag `v2.5` より先だが、
`package.json` の `version` はどちらも `2.5.0` のままである）ため、
commit を比べる作り方になっている。

## 4. 由来を判定する

読んでいるコードが取り込み由来か自作かで、読み方を変える。

| 由来 | 読み方 |
| --- | --- |
| 取り込み（`webapp-common/`、`business-logic/`） | 設計意図を探さない。上流の都合として受け入れ、外形（入出力）だけ取る |
| 自作（`features/` `core/` `shared/` `layout/`） | 設計意図がある。コミットメッセージと `docs/` を併せて読む |

判定の根拠は三つある。

**規約の記述** — `web-boundaries.json` の規則説明に
「`webapp-common` はベンダー由来の凍結領域なので足さない」とある。

**依存の向き** — `webapp-common` から `~/features` への参照は 0 件である。
取り込み層は自作層を知らない。

**コミット** — 自作層のファイルは、`86e6dbd first commit` 以降のコミットで触られている。

```bash
# あるファイルが first commit 以降に触られたか
git log --oneline 86e6dbd..HEAD -- src/app/features/experiments/
```

## 5. 差分で読む

上流との差分は、「このプロジェクト固有の事情」を抽出する道具になる。
差分に出たファイルは、必ず誰かが理由を持って触った箇所である。

```bash
# fork 基点との差分（ファイル名だけ）
git diff --stat v2.5 HEAD -- src/app/webapp-common/
```

取り込み層に差分が出ていたら、それは「凍結領域に手を入れた」ことを意味する。
理由が必ずあるので、該当コミットを読む。

既存の比較資料が `x-ClearML_公式とカスタマイズ済み比較.md`（29KB）にある。
自分で差分を取る前に、これを先に読む。

## 6. コミットメッセージから読む

本リポジトリのコミットメッセージは短い（`task[4]`、`settings`、`解析中` など）。
意図の一次情報としては薄い。

代わりに、意図は `docs/` に書かれている。
`docs/README.md` §2 に、要件から運用までを 12 本でたどる順序が定義されている。
「なぜこの構成か」を知りたいときは、`git log` ではなく
`docs/phase1_上流設計/03_方式設計書.md` を引く。

この分担は意識的なものである。
`upstream.json` の `$comment` も、`scripts/*.mjs` のヘッダコメントも、
「判断とその理由」を記述の側に置いている。

## 7. コードのコメントを一次情報として扱わない

コメントはコンパイルされないので、コードが変わっても壊れない。壊れないものは直されない。

`webapp-common/core/router-reuse-strategy.ts` の JSDoc には
"I believe the boolean is indicating to a controller whether or not to fire this.store" とある。
書き手自身が推測で書いており、仕様ではない。

一方で、意図が正確に書かれたコメントもある。
`app.config.ts` の `provideHttpClient(withInterceptorsFromDi())` に付いた注記
（これが無いと Interceptor だけが黙って無効になる）は、実際にそのとおりである。

見分け方は書き手である。
自作層（`features/` `core/` `shared/` `app.config.ts` `scripts/`）のコメントは信用度が高い。
取り込み層のコメントは、上流の書き手のものであり、確認しないまま信用しない。

## 8. 履歴を読むときの打ち切り

「なぜこうなっているか」は、答えが無いことがある。
取り込み層について 15 分探して出なければ、出ないと判断してよい。

そのとき残すのは「探したが出なかった」という記録である。
これを残さないと、次の人（あるいは二週間後の自分）が同じ 15 分を払う。
